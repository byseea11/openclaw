# 核心目标

三个核心挑战：

- 挑战一：重新定义“记忆” (Define it)
  在飞书企业环境下，什么是真正有价值的“个人/团队记忆”？
  是 CLI 的高频命令？是飞书文档里的架构设计？是群聊里的审批习惯？还是用户的隐式偏好？
- 挑战二：构建记忆引擎 (Build it)
  如何设计一套系统（Memory Engine），实现记忆的提取、存储、检索、更新和遗忘？
  如何保证这套系统在 CLI 和飞书中无缝流转？
- 挑战三：证明它的价值 (Prove it)
  你怎么证明你的系统真的“记住了”，并且“产生了实际效能”？
  你需要自己设计一套评测用例和指标，来跑通你的逻辑。

- 方向 B：飞书项目决策与上下文记忆（偏项目管理）
  - 场景描述：在飞书项目群聊或文档讨论中，经常出现“之前我们决定用方案 B 而不是 A”、“上周五确认了截止日期是 5 号”等决策性信息。设计记忆系统，从对话/文档中自动提取决策、理由、反对意见、结论，并建立与项目阶段、时间点的关联。当后续讨论触及相关话题时，主动推送“历史决策卡片”，避免重复争论或遗忘。
  - 记忆特征：结构化记忆（决策-理由-结论）+ 时序关联 + 主动检索与推送

## 解决办法

### 挑战1

1. 确认重新定义“记忆” ：方向 B：飞书项目决策与上下文记忆（偏项目管理）
2. 确认需要支持飞书的哪些功能：https://github.com/larksuite/cli中支持的飞书功能

3. 难点：支撑跨会话、跨文档、跨工具、跨工作状态条件下的连续协作。

   这不是一个“把更多消息存下来”就能解决的问题，而是一个真实的企业协作语义恢复问题。企业内部的真实上下文通常被分散在多个地方：

   - 会话里只出现一句“看文档”“按表里的口径执行”“审批还没过”
   - 真正的目标、约束、截止时间、风险和决策理由却写在文档正文、知识库节点、表格记录、任务详情里
   - 同一个事实还可能在主群、thread、文档、任务、表格里出现不一致、滞后同步和局部真相

   因此，这个项目的难点不是单纯“做一个聊天机器人”，而是要解决下面几个真实问题：

   - 跨会话连续性：同一个项目状态会分散在不同时间、不同群、不同 thread 中，系统需要把它们重新拼回一个连续上下文，而不是只看当前一轮消息。
   - 跨文档连续性：关键目标和决策常常只在文档正文里，聊天里只是提到文档标题或链接。系统如果只记住“有人发过一个链接”，但拿不到正文，就无法真正理解项目事实。
   - 跨工具连续性：企业协作不是只发生在 IM 中，还发生在文档、知识库、任务、表格等工具中。系统需要把这些对象中的关键信息重新接地到对话语境里。
   - 跨工作状态连续性：一个项目不是静态的，状态会从 `planning -> blocked -> at risk -> in progress -> done` 持续变化，而且不同工具上的状态更新时间也不同，系统需要识别“当前最新事实”而不是盲目叠加历史。

   这一点已经通过真实飞书 -> OpenClaw 链路验证出来：

   - 当用户在群里 `@byseeasopenclaw` 并引用一篇飞书文档时，OpenClaw 最外层真实收到的是“消息文本 + mention 结构 + 文档链接”。
   - OpenClaw 当前的 Feishu chat ingress 不会自动把文档正文展开进来。
   - 也就是说，如果关键信息只存在于文档正文、知识库页面、表格记录或任务详情中，而没有被人工同步成聊天摘要，那么当前主链实际上是“看不见”这些事实的。

   这可以视为当前 OpenClaw 在企业协作场景中的一个真实边界，也是本项目需要解决的核心问题之一：

   - 当前 OpenClaw 默认擅长消费对话型输入，但还没有原生解决“消息中引用的企业对象如何自动解析并进入记忆”的问题。
   - 它能知道“这里有一个文档链接”，但并不会自动知道“这个文档正文到底写了什么”。
   - 因而它能记住“有人提过某个对象”，却不一定能记住“对象内部的真实内容和当前有效状态”。

   所以，这个项目后续真正要补的不是简单的聊天存档，而是两层能力：

   - 第一层：消息入口后的对象解析能力。也就是当群聊中出现文档、知识库、表格、任务等引用时，系统能够继续把对象正文或结构化内容拉出来。
   - 第二层：把拉出来的对象内容变成可持续维护的 memory / graph，而不是一次性工具读取后就丢失。

   换句话说，这个项目要解决的是：

   > 企业协作中的关键事实并不天然存在于对话消息本身，而是隐藏在被对话引用的对象正文里；系统需要跨越“消息入口”和“对象内容”之间的语义断层，才能真正支撑连续协作。
4. 创建企业真实数据集
   4.1. 已知条件：在真实企业内部能够：员工表（信息， 权限， 职务， 上下级）
