架构设计：
raw evidence
  -> 识别主对象
  -> 抽出一个或多个 event
  -> event 入 event_records
  -> 根据 event patch state
  -> 根据 event 建 / 关 edge
1. 目标：谁负责，状态是什么，为什么是这个状态，下一步怎么做
系统能够围绕协作对象回答四类核心问题：
-  谁负责 
-  当前状态是什么 
-  为什么是这个状态 
-  下一步做什么

补充：三类类型定义
对象类型
表示实体是什么，比如我要查询一个东西，那么查询的东西就是对象
根据支持的，对象有：
1. task：任务（FEISHU-231）
2. approval：审批（AP-778）
3. person：人员（Alice、xzy、Bob）
4. blocker：阻塞对象（finance_issue、legal_approval）

事件类型
owner_changed：负责人变更 
stage_changed：阶段变化 
approval_status_updated：审批状态更新 
blocked：任务被阻塞 
unblocked：任务解除阻塞 
next_action_set：设置下一步动作

状态槽位
current_owner：当前负责人 
current_stage：当前阶段 
approval_status：当前审批状态 
current_blocker：当前阻塞项 
next_action：当前下一步动作

2.1 Evidence records：核心证据表，类似session transcripts
evidence_records证据层。由 transcript batch 生成，保存 content_text、content_json、source_locator_json。 使用 evidence_fingerprint 幂等去重。
2.2 event_type_registry：受控事件类型注册表
event_type_registry受控事件类型注册表。当前固定 owner_changed、stage_changed、approval_status_updated、 blocked、unblocked、next_action_set。
2.3 event_records_v2：唯一事实层
append-only，通过 event_fingerprint 去重。 subject_ref / actor_ref / object_ref 都是 typed business key。
一条信息里面可以抽取多条event，比如 feishu-283 本来今天结项，结果换了负责人，审批还在进行，需要推迟到后天结项。这里就可以抽出3条event
2.4 workflow_state_view_v2：当前 workflow 状态视图
只能由 event slot patch/upsert 得出， 维护 owner、stage、approval、blocker、next_action、slot_versions_json。

3.3 图谱建立:evidence->event->state->graph entity->graph edge
1. owner_changed
消息：
Alice有事，把 FEISHU-231 负责人改给 xzy
事件表里会有
- event_type_code = owner_changed
-  主对象：task:FEISHU-231
图谱层怎么建
先确保两个实体存在：
- task:FEISHU-231
- person:xzy 或更好 person:ou_xxx
然后建立边：
task:FEISHU-231 --assigned_to--> person:xzy
同时把旧的 assigned_to 边失效。

---
2. approval_status_updated
消息：
AP-778 还在 pending，关联 FEISHU-231
图谱层怎么建
确保实体存在：
- approval:AP-778
- task:FEISHU-231
建立边：
task:FEISHU-231 --depends_on--> approval:AP-778
approval:AP-778 --approval_for--> task:FEISHU-231
你可以只选一个方向，或者双向都建。

---
3. blocked
消息：
FEISHU-231 卡在 AP-778
图谱层怎么建
建立边：
task:FEISHU-231 --blocked_by--> approval:AP-778
如果 blocker 不是审批，而是“财务问题”，那就是：
task:FEISHU-291 --blocked_by--> blocker:finance_issue

---
4. unblocked
消息：
AP-778 过了，FEISHU-231 可以继续了
图谱层怎么建
把之前的：
task:FEISHU-231 --blocked_by--> approval:AP-778
这条边标记为：
- is_active = false
- valid_to = event_time

---
5. next_action_set
消息：
Bob 先补材料再提
图谱层怎么建
可以建立一个边：
task:FEISHU-231 --next_action_owner--> person:Bob
同时状态表里更新：
- next_action_json = { assignee: Bob, action: 补材料再提 }

---
6. stage_changed
消息：
FEISHU-231 进入法务审批阶段
这个更多是 patch 状态，不一定非要建边。
 但如果你以后有“belongs_to_stage”这种需求，也可以建。

例子：一条消息怎么走完
用一句更完整的话：
Alice有事，FEISHU-231 负责人改给 xzy；目前卡在 AP-778，Bob 先补材料再提。
这条消息可以拆成 3 个 event：

---
event 1：owner_changed
{
  "event_type_code": "owner_changed",
  "primary_entity_type": "task",
  "primary_entity_ref": "FEISHU-231",
  "payload_json": {
    "old_owner": "Alice",
    "new_owner": "xzy",
    "reason": "Alice有事"
  }
}
patch state：current_owner = xzy
update edge：assigned_to -> xzy

---
event 2：blocked
{
  "event_type_code": "blocked",
  "primary_entity_type": "task",
  "primary_entity_ref": "FEISHU-231",
  "payload_json": {
    "blocker_ref": "approval:AP-778",
    "reason": "审批未完成"
  }
}
patch state
- current_blocker = approval:AP-778
- current_stage = blocked
update edge
- blocked_by -> approval:AP-778

---
event 3：next_action_set
{
  "event_type_code": "next_action_set",
  "primary_entity_type": "task",
  "primary_entity_ref": "FEISHU-231",
  "payload_json": {
    "assignee": "Bob",
    "action_text": "补材料再提"
  }
}
patch state
- next_action_json = {assignee: Bob, action: 补材料再提}
update edge
- next_action_owner -> Bob

---
最终 workflow_state_view
{
  "entity_type": "task",
  "entity_ref": "FEISHU-231",
  "current_owner": "xzy",
  "current_stage": "blocked",
  "approval_status": "pending",
  "current_blocker": "approval:AP-778",
  "next_action_json": {
    "assignee": "Bob",
    "action": "补材料再提"
  }
}

---
最终 graph_edges
task:FEISHU-231 --assigned_to--> person:xzy
task:FEISHU-231 --blocked_by--> approval:AP-778
task:FEISHU-231 --next_action_owner--> person:Bob
