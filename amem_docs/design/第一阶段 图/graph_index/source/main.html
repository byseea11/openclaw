课题二：企业级长程协作 Memory 系统

一、课题定位

面向企业跨部门、跨周期协作中智能体"记不住、接不上、说不清"的核心瓶颈，依托飞书 OpenClaw、飞书 CLI 及大模型能力，构建具备持续接入、统一建模、可信恢复三大核心能力的企业级长程协作 Memory 系统。

系统的差异化定位在于：从"记忆片段召回"升级为"协作状态维护"——使智能体不仅能够"记住信息"，更能够维护状态、恢复过程、解释结论，支撑跨会话、跨文档、跨工具、跨工作状态条件下的连续协作。

二、现有基础与关键不足

OpenClaw 已具备 transcript、daily/long-term memory、Active Memory、memory flush、dreaming 等机制；memory-wiki、memory-lancedb-pro 等扩展进一步增强了记忆抽取、结构化整理与长期召回能力。但面向企业级长程协作需求，现有体系仍停留在"抽取—召回—注入"范式，三项关键能力缺位：

# 现有能力 所擅长的 关键短板
1 memory-core 跨轮次上下文恢复 缺少面向协作流程的强结构化状态建模，任务阶段、责任人、阻塞点、审批状态、下一步动作等业务字段无统一显式模型
2 memory-wiki claim-evidence 型知识沉淀 偏知识层组织，回答"哪些事实成立"；不适合作为回答"谁负责、卡在哪、下一步做什么"的主工作状态层
3 memory-lancedb-pro 长期记忆分层存储与择优召回 本质为 memory items 的事后注入，难以保证系统中存在一份持续更新、字段明确、可直接查询的当前状态对象
小结：现有能力是本课题的重要底座，但不足以直接支撑企业长程协作对连续状态管理、过程可追溯、结论可解释的刚性要求。

三、核心难点

难点一 · 多源协作信息持续接入难
信息分散在会话、文档、工具调用、审批、项目管理、代码平台等多类载体,且状态持续变化。传统单轮抽取或事后汇总难以及时捕获负责人变更、审批推进、阻塞出现与解除、下一步切换等关键信号,导致信息遗漏、状态滞后、协作断层。

难点二 · 工作状态统一建模难
企业协作既要记录"发生过什么",又要维护"当前是什么状态",还要刻画"对象之间是什么关系"。通用记忆方案多停留在事实召回层,难以形成面向任务、项目、审批、会议、文档等对象的统一状态底座。

难点三 · 协作结论可信恢复难
企业场景要求回答五要素——谁负责 / 何时改 / 为何改 / 当前状态 / 证据来源。仅依赖相关片段召回,易出现结论分散、冲突难解释、主结论不突出、证据链断裂,难以满足可解释性与责任可追踪要求。

五、三项核心技术

技术点① 多源协作信息统一采集与增量更新技术

所解决问题：协作变化如何持续、稳定、不遗漏地进入系统。

技术内核：以会话、工具结果、文档变化及外部系统信号为统一输入,构建"增量检测 → 批量抽取 → 事务一致性写入 → 可恢复更新"四步闭环。核心不在被动保存信息,而在持续感知"哪里发生了变化",并将变化可靠纳入统一记忆链路。

关键创新：面向协作变化的事件化采集机制、跨源信号的时间一致性对齐、写入失败可回溯重放。

技术点② 工作状态图谱一体化建模技术

所解决问题：进入系统的信息如何沉淀为统一、可查询、可更新的协作状态。

技术内核：构建"事件账本 + 状态视图 + 知识图谱"三位一体的建模结构:

  • 事件账本——记录所有过程性变化,保证可追溯;
  • 状态视图——维护每个协作对象的当前主状态,保证可查询;
  • 知识图谱——组织对象间关系(任务—责任人—项目—审批—文档),保证可关联。

在此之上构建面向工作流的权威状态层,对任务阶段、责任人、阻塞点、审批状态、下一步动作等关键槽位进行统一沉淀。

关键创新：

  • 相比 memory-wiki 的 claim-evidence schema,提出面向协作流程的状态-事件-关系三元结构;
  • 相比 memory-lancedb-pro 的 item 择优召回,形成持续更新的"当前唯一真相"。

技术点③ 证据组织与链条化恢复技术

所解决问题：沉淀后的状态如何恢复为可解释、可验证的协作结论。

技术内核：按问题类型构建规划式召回机制——状态查询 / 列表查询 / 时间线查询 / 阻塞原因查询——将图谱关系、状态视图、历史事件按问题需要分组、排序、链条化组织,并显式保留冲突证据、新鲜度信息、支撑依据。

关键创新：从"相关片段召回"升级为"结构化证据链输出",系统默认回答五要素(谁/何时/为何/当前/来源),冲突证据显式呈现而非被覆盖。

三项技术的逻辑闭环

层次 解决问题 核心输出
① 采集层 协作变化如何持续进入系统 稳定、连续、不中断的增量信号流
② 图谱层 信息如何沉淀为统一工作状态 可查询、可追溯的协作状态底座
③ 恢复层 状态如何恢复为可信结论 结构化、可解释、可验证的结论输出

三者协同后,系统具备从多源信号接入 → 状态统一沉淀 → 证据化恢复输出的全流程能力,支撑企业跨部门、跨会话、跨文档、跨工具、跨工作状态的连续协作 Memory 引擎建设。

六、预期创新点

  1. 范式创新：从 memory 召回范式迈向协作状态维护范式,填补现有智能体记忆体系在企业长程协作场景的空白。
  2. 建模创新：提出事件-状态-关系三位一体的协作状态建模结构,替代单一的 claim-evidence 知识 schema。
  3. 恢复创新：提出五要素证据链恢复机制,显式处理冲突证据与新鲜度,使协作结论具备业务级可解释性与可追溯性。
  4. 工程价值：为飞书生态提供面向跨部门、跨会话、跨文档、跨工具场景的企业级长程协作 Memory 引擎底座。

七、初步实验验证（前期基础）

为验证本课题“状态图谱建模 + 证据链条恢复”方案相对于传统“记忆片段召回”范式的实际效果，项目组已在 LoCoMo 长程对话记忆基准上完成对照实验，初步证实技术路线的可行性与有效性。

7.3 机制分析

Native 失败路径
Native 将记忆视为等权重片段集合，更容易被出现更早、出现更频繁的活动性陈述牵引，因此把“过程”误判成“最终事件”。
1 召回阶段优先命中“筹备 / 准备 / 建设”等高频早期片段。
2 系统缺少对“同一对象状态跃迁”的显式建模，无法区分过程性活动与最终完成事件。
3 最终把结论锚定到早期错误日期，导致答案偏差。
Graph 成功路径
Graph 方案先维护“对象状态”，再按问题类型组织证据，因此能够从零散片段中恢复出最新、最关键、可追溯的状态结论。
1 Layer 2 状态图谱将“店铺”作为统一协作对象，把“筹备中 → 已开业”识别为同一对象的状态跃迁。
2 Layer 3 证据链条恢复针对“开业日期”这一状态查询型问题，按“最新明确状态事件”原则规划召回，优先选取显式开业声明。
3 系统将该声明所在 Session 的时间戳显式纳入证据链，从而保证结论可解释、可追溯。

7.4 结论

本样本验证出的三项关键结论
路线可行：状态图谱建模能够有效区分“活动”与“事件”，避免片段召回带来的早期锚定偏差。
效果显著：F1 提升 60%，说明从“召回”升级为“状态维护”是真实、可量化的精度来源。
性能友好：延时反降 20.1%，表明结构化召回并非以效率为代价，反而可因减少无关片段注入而加速推理。
阶段性结论:该对照实验为本课题技术路线提供了已验证的可行性证据。后续将扩展至完整 LoCoMo 基准、多跳推理子集以及企业真实场景(飞书跨部门协作、审批链恢复、项目阻塞追溯),对三项核心技术开展更大规模、多维度的系统评测。
