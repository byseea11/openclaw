# V1 决策记忆：上下文不完整处理实现说明

生成日期：2026-04-27

## 1. 这次实现解决了什么问题

这次实现解决的是 V1 决策记忆里一个非常现实的问题：

> 企业群聊中的很多消息本身并不完整，只有结合上文、thread root、父消息，或者当前已有状态，才能知道它到底在说什么。

典型例子：

- “这个先别对外说死”
- “那就按刚才的来”
- “这个风险还没解”
- “那个日期还不能确认”

如果只把这一条消息孤立地送给 extractor，它通常会遇到两个风险：

1. 看不懂指代对象，最后只能 `abstain`
2. 误把旧上下文重新抽成一个新的 event，造成重复写入

所以这次实现的目标不是推翻现有 V1 主链，而是在现有链路里补一层：

```text
projection_inbox
  -> drainPendingGraphUpdates
  -> Core Span + Context Envelope
  -> extractor
  -> canonicalizeV2
  -> persistSemanticBatchV2
```

也就是说，**让 extractor 在理解时能看到有限上下文，但在写 event 时仍然只能从 Core 生成新的 decision event。**

---

## 2. 一句话总结

这次改动把原来的“孤立 transcript chunk 抽取”改成了：

```text
候选 Core Span
  + 最小必要 Context Envelope
  + current_state_context（仅消歧）
  -> quote-first extraction
  -> quote-grounded decision_claim_recorded
```

其中最重要的约束是：

- `CORE` 决定是否生成新的 decision event
- `CONTEXT` 只负责解释 “这个 / 刚才 / 按上面说的 / 那个日期”
- `CURRENT_STATE_CONTEXT` 只负责帮助模型理解当前口径，不允许作为证据来源

---

## 3. 这次实现前的链路长什么样

在这次改动之前，V1 主链已经是：

```text
L0 决策候选粗筛
  -> projection_inbox
  -> drainPendingGraphUpdates
  -> extractor
  -> canonicalizeV2
  -> persistSemanticBatchV2
  -> event_records_v2 / decision_state_view_v2 / graph_edges_v2
```

它已经能完成：

- L0 命中 `decision_memory_candidate`
- drain 抽出 `decision_claim_recorded`
- 将 claim 写入 `event_records_v2`
- 更新 `decision_state_view_v2`
- query 命中 `decision_card`

但当 extractor 的输入只是一个按大小切出来的 transcript chunk 时，会有一个明显缺陷：

- chunk 里可能只有“不要对外说死”
- 但没有“5 月 5 日是目标日期”“迁移窗口还没锁定”这些上文
- 这时模型看见的是一句不完整的话

所以问题不在主事实模型，而在 **drain 输入的上下文组织方式**。

---

## 4. 这次实现后的整体流程

现在的整体流程是：

```text
afterTurn / beforeCompaction
  -> L0 detector
  -> projection_inbox 按 span 入队
  -> drainPendingGraphUpdates
      -> 先保留 inbox row 边界，得到 Core groups
      -> 再从同 source 聚合 entries 中补最小 Context
      -> 构造 Core Span + Context Envelope
      -> extractor 做 quote-first extraction
      -> canonicalizeV2 做 Core/Context-aware validation
      -> persistSemanticBatchV2 同事务写 evidence + event
      -> 更新 decision_state_view_v2 和 graph_edges_v2
```

可以把它理解成两步：

### 4.1 Core 决定“要不要写新 event”

Core 就是当前真正待处理的候选消息范围。  
只有 Core 里出现了新的语义动作，才允许写新的 `decision_claim_recorded`。

这类新动作包括：

- 确认
- 修订
- 反对
- 风险提醒
- 时间点变化
- 阶段变化
- “不要对外说死”
- “不是已确认”
- “顺延”

### 4.2 Context 只负责“帮你看懂 Core”

Context 的职责是：

- 解释 “这个” 指的是哪个日期
- 解释 “刚才那个口径” 到底是哪条结论
- 解释 “按上面说的” 里的“上面”是什么

但 Context 不能单独触发新的 event。

---

## 5. Core Span + Context Envelope 是怎么构造的

这次实现里，drain 不再只把一段纯文本直接送给 extractor，而是先构造结构化 envelope。

最终输入结构是：

```ts
{
  anchors: {
    task_refs: string[],
    thread_ids: string[],
    doc_refs: string[],
    project_names: string[],
    source_chat_ids: string[],
  },
  current_state_context: {
    topic_ref: string | null,
    decision_axis_key: string | null,
    active_conclusion: string | null,
    active_time_points: string[],
    active_rationales: string[],
    active_objections: string[],
  } | null,
  context_entries: [
    { entry_id, parent_id, role, content, timestamp }
  ],
  core_entries: [
    { entry_id, parent_id, role, content, timestamp }
  ],
}
```

然后再渲染成 prompt 里的四段：

```text
[ANCHORS]
...

[CURRENT_STATE_CONTEXT]
...

[CONTEXT]
...

[CORE]
...
```

### 5.1 Core 是什么

Core 来自 `projection_inbox` 里的 candidate span。  
这一步很关键：这次实现里不再把所有 pending entries 混成一个统一大块，而是**保留 inbox row 的边界**，让每个候选 span 都有自己的 Core。

### 5.2 Context 是什么

Context 采用“同源最小集”：

- thread source
  - root
  - parent
  - Core 前 3 到 5 条同 thread 上文
  - 可选后 1 到 2 条
- 普通 chat source
  - 同 chat、同 anchor、近时间窗口前 3 到 5 条消息
  - 没有 anchor 就不扩展
- doc/wiki/base/sheet sync source
  - 同 source item 的标题、相邻内容、同步摘要

这里特意没有做跨 source / 全局 recall，因为 V1 先追求保守和可控。

### 5.3 current_state_context 是什么

`current_state_context` 来自已有的 `decision_state_view_v2` 摘要。  
它只包含简短的当前状态信息，例如：

- 当前 `topic_ref`
- 当前 `decision_axis_key`
- 当前 active conclusion
- 当前 active time points
- 当前 active rationales / objections

它的作用只是帮助模型理解“现在已经有什么口径”，**不能被当成证据**。

## 6. 这次实现的核心难点

### 6.1 难点一：如何补上下文，但又不让旧上下文重新触发新 event

这是这次最大的难点。

如果你把完整上下文都给模型，它很容易做两件坏事：

1. 把 Context 里的旧结论又写一遍
2. 看到 current state 摘要后，把摘要内容当成新 evidence

这会直接污染：

- `event_records_v2`
- `decision_state_view_v2`
- 后续的 `decision_card`

所以这次实现不是“给更多上下文”，而是“**严格限制上下文的使用边界**”。

### 6.2 难点二：如何让 extractor 真正做到 quote-first，而不是自由总结

如果模型被要求“总结这段对话的决策”，它很容易做自由扩写。  
这样虽然表面上更聪明，但和 V1 的事实模型不兼容，因为 V1 需要的是：

- quote-grounded
- 原子 decision event
- evidence 可回溯

所以必须把任务改写成：

1. 先在 Core 找 `evidence_quote`
2. 再从 Context 找 supporting quotes
3. 再归类 `claim_field`
4. 最后才规范化成 `decision_claim_recorded`

### 6.3 难点三：如何把 `evidence_quote` 真正定位到某个 Core entry

V1 的 `evidence_records` 不能保存整段 Context，也不能只记“这大概来自这批消息”。  
如果 `evidence_quote` 不能落到具体 Core entry，后面做：

- debug
- evidence 回溯
- query 卡片引用

都会变弱。

所以这次实现把 quote 定位进一步收紧成：

- `evidence_quote` 必须命中某个 `core_entry.messageContent`
- 尽量记录 `resolved_core_entry_id`
- `evidence_records` 里只存 quote-grounded snippet

---

## 7. 具体是怎么解决这些难点的

## 7.1 解决方法一：Prompt 层明确规定 Core/Context 边界

这次在 extractor prompt 里加了几条硬约束：

- `Use CORE to decide whether to create new decision events.`
- `Use CONTEXT only to resolve references ...`
- `Do not generate a new decision event from CONTEXT alone.`
- `Do not use CURRENT_STATE_CONTEXT as evidence.`
- `Supporting context quotes may come only from CONTEXT entries.`
- `If CORE has no new semantic action, return should_extract=false or claims=[].`

这让模型的角色变成：

- Core 决定写不写
- Context 只是帮它理解

而不是自由总结整段输入。

## 7.2 解决方法二：Schema 不变，只在 `claim_value_json` 里补 metadata

这次没有改顶层 extraction schema，也没有新增专用事实表。  
只是在 `claim_value_json` 里允许补充两个可选字段：

```json
{
  "core_entry_id": "entry-core",
  "supporting_context_quotes": [
    {
      "quote": "FEISHU-231 目标发布时间暂定 5 月 5 日。",
      "entry_id": "entry-ctx-1",
      "source": "context"
    }
  ]
}
```

这样做的好处是：

- 不破坏 V1 主事实模型
- 只给 extractor 和 canonicalizer 增加必要 metadata
- event 落库后仍然是 `decision_claim_recorded`

## 7.3 解决方法三：Validation 从“整段文本匹配”改成“Core/Context-aware 校验”

这次最重要的工程改动其实不在 prompt，而在 `canonicalizeV2` 的本地校验。

新增的关键规则有：

### 7.3.1 `evidence_quote` 必须命中 Core

- 先看 extractor 有没有给 `core_entry_id`
- 如果给了，就优先用它定位
- 如果没给，就在多个命中的 core entries 里做本地解析：
  - 优先最近
  - 再选最短可稳定定位的 entry
- 还是不稳定，就拒绝或降为低置信

最终落库时，`evidence_records` 里会写：

- `resolved_core_entry_id`

### 7.3.2 supporting quotes 只能来自 Context

- supporting quote 找不到时，先删除该 quote
- 删除后如果 claim 不再被 `evidence_quote + 剩余 supporting quotes` 支撑，就拒绝整条 claim
- `current_state_context` 里的内容不允许充当 supporting quote

### 7.3.3 Core 没有新语义动作时，不允许重写旧 claim

如果 Core 只是：

- “收到”
- “好的”
- “我看下”

即使 Context 里有旧结论，也不允许生成新的 `decision_claim_recorded`。

这一步用一组保守的本地 cue 检测来保证：

- 命中确认、修订、反对、风险、日期变化、阶段变化、不要对外说死、不是已确认、顺延等动作，才允许继续
- 否则即使模型生成了 claim，也会在 validation 阶段被拒绝

## 7.4 解决方法四：Evidence 仍然只保存 quote-grounded snippet

这次没有改变 evidence 的持久化原则。

`evidence_records` 仍然只保存成功支撑 event 的 quote-grounded snippet：

- `content_text = evidence_quote`
- `content_json` 里补充：
  - `resolved_core_entry_id`
  - `supporting_context_entry_ids`

但不会保存：

- 整段 Context
- `current_state_context` 文本

这样可以同时保住两件事：

- evidence 可回溯
- 长期存储不会无限膨胀

## 8. 这次实现后，真实流程怎么走

用一个典型例子来描述：

### 输入

```text
CONTEXT:
A: FEISHU-231 目标发布时间暂定 5 月 5 日。
B: 迁移窗口还没锁定。

CORE:
C: 那就先按这个来，但不要对外说死。
```

### 流程

1. L0 命中候选，Core span 进入 `projection_inbox`
2. drain 时保留该 Core span，同时补：
   - 上面的两条 Context
   - 必要的 anchors
3. extractor 在 Core 里找到：
   - `evidence_quote = "不要对外说死"`
4. extractor 再用 Context 理解：
   - “这个” 指的是 5 月 5 日
   - “不要说死”的原因和上下文是迁移窗口未锁定
5. canonicalizer 验证：
   - `evidence_quote` 确实来自 Core entry
   - supporting quotes 确实来自 Context entries
   - claim 不是纯粹重复旧 Context
6. 持久化：
   - `event_records_v2` 新增一条 `decision_claim_recorded`
   - `evidence_records` 保存 `不要对外说死`
   - `decision_state_view_v2` 更新 active claim

### 结果

系统可以回答：

- 当前是不是确认 5 月 5 日？
- 为什么还不能对外说死？
- 这条口径的证据来自哪里？

---

## 9. 这次实现的边界

这次实现虽然补了“上下文不完整”问题，但仍然有边界：

### 9.1 只做同源最小上下文

现在不会做：

- 跨 source 的全局扩窗
- 从整个历史里自由检索一大段上下文
- 任意全局 recall 再回灌 extractor

这是有意为之，因为 V1 先追求：

- 保守
- 可控
- 不重复抽取

### 9.2 `current_state_context` 不参与证据

它只能帮助模型理解：

- 当前已有的 state 是什么

但不能被视为：

- 新 claim 的证据
- supporting quote

### 9.3 仍然不把所有群聊长期写入 `evidence_records`

V1 仍然坚持：

- `projection_inbox` 是候选缓冲
- `evidence_records` 是成功支撑 event 的有效证据库

这意味着：

- 不是所有原始群聊都会永久保存到 evidence 层

## 10. 测试覆盖了什么

这次补了三类测试：

### 10.1 extractor 测试

验证：

- prompt 确实包含 Core/Context 约束
- `supporting_context_quotes`
- `core_entry_id`

能够被正常解析和 normalize。

### 10.2 canonicalizer / validation 测试

验证：

- `evidence_quote` 必须命中 Core entry
- 多个 core entry 同时命中时，优先使用 extractor 给的 `core_entry_id`
- supporting quote 找不到时会先删除，再决定是否拒绝 claim
- Core 只是 acknowledgement 时，不会重写旧 claim

### 10.3 projection / drain 测试

验证：

- Core 依赖 Context 才能理解
- Context-only 不会重复抽取
- 原有 FEISHU-231 smoke 继续通过

## 11. 这次实现后的价值

这次改动的价值，不是“让模型看到更多东西”，而是：

> 让 V1 决策记忆在不破坏主事实模型的前提下，第一次真正具备了处理“不完整企业协作消息”的能力。

更具体地说，它解决了三个问题：

1. Core 本身不完整时，不必直接 `abstain`
2. Context 可以帮助理解，但不会直接污染 event ledger
3. 每条新 event 仍然能回到一个明确的 Core quote 和 Core entry

所以这次实现之后，V1 决策记忆主链的含义更清楚了：

```text
Core 产生新的事实
Context 帮助解释这个事实
State 只维护当前 active 口径
Evidence 只保存真正支撑事件的 quote-grounded snippet
```

这也让后续继续往下做时有了更稳定的基础：

- 如果要增强 recall，可以先增强 context 选择
- 如果要增强 query，可以继续从 active state + historical events 生成更强卡片
- 但不需要再回头推翻 V1 的事实层和状态层
