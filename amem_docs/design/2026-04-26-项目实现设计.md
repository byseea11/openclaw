1. 数据集：使用lark_cli工具，创建agent pipline自动创建。
   agent pipline设计：[builder_agent](data_builder_agents/2026-04-25-builder_agent_plan.md)
2. 定义：飞书项目决策与上下文记忆系统：从群聊、线程、文档、Base/Sheet、审批卡片里提取“项目决策、理由、反对意见、当前结论和时间线”，在后续讨论再次触及相关话题时，自动检索并推送“历史决策卡片”。
3. 架构设计：
   第一层：Evidence Layer
   保存原始证据，不做语义承诺

   第二层：Decision Claim Event Layer
   从候选 span 中抽取最小决策声明，不生成完整 decision

   第三层：Decision View + Lightweight Graph Layer
   围绕 topic 聚合 claim，形成当前决策视图和轻量关系索引

   第四层：Query-time Decision Card Layer
   用户触发时，检索 claims + evidence，生成历史决策卡片

4. 核心能力定义成：

   第一句：不是全量 LLM 抽取，而是 slot-driven routing

   我们没有把所有飞书消息都直接交给 LLM 抽取，而是先通过 anchor detection 识别 task、person、date、blocker、doc 等业务锚点，再通过 event registry 将候选文本路由到具体状态槽位，例如 release_target、p0_blocker、confirmed_release_date。LLM 只在槽位级别做受控补全。

   第二句：event type 来自状态槽位变化

   event type 不是手工随意枚举的，而是由状态槽位和操作类型组合得到。比如 p0_blocker + assert 得到 blocker_asserted，confirmed_release_date + deny 得到 confirmed_release_date_denied。每个 event 都是一个可回放的状态补丁。

   第三句：graph 是由 event/state 投影出来的

   图谱不是直接从文本里抽出来的，而是由 event 更新 state，再由 state 投影出 active edge。以任务节点为中心，向负责人、日期、blocker、状态、文档、证据等节点辐射，并通过 previous_edge_id / supersedes_edge_id 保留版本链，从而支持当前状态查询和历史决策追溯。

5. 架构

### slot_key：由项目方向决定

> 在飞书项目群聊或文档讨论中，自动提取决策、理由、反对意见、结论，并建立与项目阶段、时间点的关联；当后续讨论触及相关话题时，主动推送历史决策卡片。

系统最终要回答的问题：

1. 之前围绕什么 topic 讨论过？
2. 当前结论是什么？
3. 为什么这么定？
4. 有哪些反对意见？
5. 这个结论关联哪个项目阶段？
6. 这个结论关联哪个时间点？
7. 后来有没有变化？
8. 证据来自哪里？

| 字段                | 作用                      | 底层怎么写      |
| ------------------- | ------------------------- | --------------- |
| `topic_ref`         | 属于哪个项目 / 任务       | anchor 绑定     |
| `decision_axis`     | 围绕哪个决策问题          | 聚类 / 轻量归纳 |
| `conclusion_claims` | 关于结论的声明            | append          |
| `rationale_claims`  | 关于理由的声明            | append          |
| `objection_claims`  | 关于反对意见 / 风险的声明 | append          |
| `stage_claims`      | 关于项目阶段的声明        | append          |
| `time_point_claims` | 关于时间点的声明          | append          |
| `evidence_refs`     | 证据来源                  | append          |
