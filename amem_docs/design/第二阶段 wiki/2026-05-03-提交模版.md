### 项目填写内容（✅ 已真实验证实现 / ⚠️ 已实现但仍有边界）
- **解决什么问题/痛点？**：针对性解决现有记忆系统的三大核心缺陷：
  1️⃣ 现有OpenClaw记忆以个人为核心，团队协作时信息分散在各自独立的记忆片段中，形成信息孤岛，不同人维护的信息语义不一致，导致沟通成本高、信息差大
  2️⃣ 传统信息抽取无结构化校验，容易遗漏关键上下文，多源信息冲突时没有自动消解机制，导致决策信息不可信
  3️⃣ 记忆无法验证、无法自动更新，信息抽取后变为静态，决策变更/废弃后旧信息不会同步更新，导致后续执行出错，重复讨论历史问题
- **AI 在其中起到什么关键作用？**：用大模型从自然语言对话里自动提取结构化决策，代替人工整理，解决了传统程序无法理解非结构化聊天内容的问题，全程不需要用户改变使用习惯，全自动运行。
- **流程是否完整闭环？能否落地使用？**：当前已经形成完整主链：飞书消息/线程 → task binding → source session → verified session_event → session_wiki / index / task_wiki → lint / forgetting / log。这个闭环已经通过真实 FEISHU-231 群消息读取 + 本地重放验证；其中 `comment` live 验收、`doc` 正文 live runtime、人工 review/retry 仍在后续收口范围内。
- **Demo 是否稳定、可正常演示？**：当前 Demo 已经可以稳定演示 FEISHU-231 真实群样本的全链路重放和三层产物生成。需要注意的是，这里“稳定”指当前样本和当前范围内的主链稳定，不等于所有 source 类型都已完成生产级长期验证。
- **带来什么实际价值/效率提升？**：当前已经验证可自动沉淀项目决策上下文，减少重复讨论，让新人不必逐条翻历史聊天记录即可进入项目语境；更具体的提效幅度还需要后续真实项目持续统计。

### 待提升点（⏳ 已知缺口）

2）核心部分代码展示
（✅ 当前 end-to-end 主链主要已实现于 `extensions/feishu-task-wiki/openclaw-lark/src/`）
- **任务绑定层核心**：`task-banding/task-binding.ts`
  - 职责：从 chat / thread / comment / doc 输入中识别任务锚点，生成 canonical task，并维护 source 到 task 的绑定关系
  - 伪代码：

```ts
function resolveTaskBinding(inbound) {
  const texts = [
    inbound.rootMessageText,
    ...inbound.replyTexts,
    inbound.chatTitle,
    inbound.docTitle,
  ]

  const taskKey = extractCanonicalTaskKey(texts)
  if (!taskKey) {
    return null
  }

  const existingBinding = resolveTaskBindingMatch({
    accountId: inbound.accountId,
    threadId: inbound.threadId,
    rootId: inbound.rootId,
    chatId: inbound.chatId,
    sourceId: inbound.sourceId,
    taskKey,
  })

  if (existingBinding) {
    return existingBinding
  }

  let task = findTaskByKey(taskKey)
  if (!task) {
    task = buildCanonicalTaskRecord({
      taskId: `task:${taskKey}`,
      taskTitle: summarizeTitle(texts),
      taskSummary: summarizeContext(texts),
      taskKeywords: extractTaskKeywords(texts),
    })
    saveTask(task)
  }

  const binding = buildTaskSourceBindingRecord({
    taskId: task.taskId,
    sourceType: inbound.sourceType,
    sourceId: inbound.sourceId,
    chatId: inbound.chatId,
    threadId: inbound.threadId,
    rootId: inbound.rootId,
  })

  saveBinding(binding)

  if (shouldBackfillThreadBinding(inbound, binding)) {
    saveThreadOrRootBinding(task.taskId, inbound)
  }

  return { task, binding }
}
```

- **事件提取层核心**：`task-events/extractor.js`
  - 职责：从已绑定 task 的 source session 中提取结构化事件，完成 candidate_event 生成、程序硬校验、LLM verifier 和 session_event 落盘
  - 伪代码：

```js
function extractEventsForSessionIngest(sessionIngest) {
  const evidenceSpan = {
    task_id: sessionIngest.taskId,
    source_session_id: sessionIngest.sourceSessionId,
    ingest_version: sessionIngest.ingestVersion,
    core_entries: buildCoreEntries(sessionIngest),
    context_entries: buildContextEntries(sessionIngest),
  }

  const candidates = extractCandidateEvents({
    task: sessionIngest.task,
    sourceSessionId: sessionIngest.sourceSessionId,
    ingestVersion: sessionIngest.ingestVersion,
    coreEntries: evidenceSpan.core_entries,
    contextEntries: evidenceSpan.context_entries,
  })

  const validCandidates = []
  for (const candidate of candidates) {
    const validation = validateCandidateEvent(candidate, evidenceSpan.core_entries)
    saveCandidate(candidate, validation)

    if (validation.ok) {
      validCandidates.push(candidate)
    }
  }

  if (validCandidates.length === 0) {
    markIngestStatus("processed_no_event")
    return
  }

  enqueueVerificationJobs(validCandidates)

  for (const candidate of validCandidates) {
    const verdict = verifyCandidateEvent({
      candidateEvent: candidate,
      coreEntries: evidenceSpan.core_entries,
      contextEntries: evidenceSpan.context_entries,
    })

    if (verdict === "verified") {
      writeSessionEvent(candidate)
    } else {
      writeCandidateVerdict(candidate, verdict)
    }
  }
}
```

- **Wiki投影层核心**：`task-wiki/projector.js`
  - 职责：消费 verified session_event，把事件组织为 Memory Block + KI Slots，并增量更新 `session_wiki.md`、`index.md`、`task_wiki.md`
  - 伪代码：

```js
async function updateTaskWikiFromVerifiedEvents(sessionDir) {
  const verifiedEvents = readSessionEvents(sessionDir)
  const metadata = readMetadata(sessionDir)
  const sessionMarkdown = readSessionMarkdown(sessionDir)

  const coarseGroups = groupEventsByStructuredKeys(verifiedEvents)

  const topicAssignments = await assignTopicsWithLLM({
    events: verifiedEvents,
    previousState: readSessionWikiState(sessionDir),
  })

  const blocks = buildMemoryBlocks({
    events: verifiedEvents,
    coarseGroups,
    topicAssignments,
  })

  for (const block of blocks) {
    block.slots = buildSlotItems(block.events)
    block.summary = summarizeBlock(block)
    block.status = inferBlockStatus(block.slots)
  }

  patchSessionWikiMarkdown({
    pagePath: sessionDir + "/session_wiki.md",
    changedBlocks: blocks,
    summary: summarizeSession(blocks),
  })

  patchIndexMarkdown({
    taskRootDir: getTaskRoot(sessionDir),
    changedPages: [sessionDir],
    changedBlocks: blocks,
  })

  patchTaskWikiMarkdown({
    taskRootDir: getTaskRoot(sessionDir),
    changedTopics: extractChangedTopics(blocks),
  })
}
```

3）LLM 在主链中的具体职责与 Prompt 设计
（✅ 当前真实主链中的 LLM 使用主要集中在 `task-events/extractor.js` 与 `task-wiki/projector.js`）

- **LLM 职责 1：第二层 candidate_event 抽取**
  - 对应代码：`task-events/extractor.js` 中的 `buildExtractionPrompts(...)`、`extractCandidateEventsWithLLM(...)`
  - 作用：从 `trigger_entries` 中抽取最小 typed `candidate_event`
  - 严格约束：
    - 只能从 `TRIGGER` 触发 event
    - `SUPPORT` 和 `CONTEXT` 只允许做指代消歧
    - 不允许使用 `current_state_context`
    - 不允许补全原文没说的 owner、deadline、target、强度
  - 当前 prompt 结构（与真实实现一致）：

```text
System Prompt
- 你是飞书 Task Wiki 第二层的事件抽取器
- 你的任务是从 TRIGGER 中抽取最小 typed candidate_event
- TRIGGER 负责触发 event，SUPPORT 和 CONTEXT 只允许做指代消歧，不能作为独立证据
- 不要使用 current_state_context
- 只允许输出一个 JSON object，格式为 {"events":[...]}
- event_type 只能是：
  conclusion_event, rationale_event, objection_event, constraint_event,
  commitment_event, status_event, time_event, scope_event
- 每条 event 必须包含：event_type, claim, core_entry_id, evidence_quote
- 不得补全原文没有说的 owner、deadline、target、强度
- 如果无法确定，就不要生成该 event

User Prompt
{
  "task": {
    "task_id": "...",
    "task_key": "...",
    "task_title": "..."
  },
  "source_session_id": "...",
  "ingest_version": 3,
  "trigger_entries": [...],
  "support_entries": [...],
  "context_entries": [...]
}
```

- **LLM 职责 2：第二层 verifier 判定**
  - 对应代码：`task-events/extractor.js` 中的 `buildVerifierPrompts(...)`、`verifyCandidateEventWithLLM(...)`
  - 作用：不重新抽取事件，只判断给定 `candidate_event` 是否足以成为 verified `session_event`
  - 严格约束：
    - 输入只包括 `core_entries`、`context_entries`、`candidate_event`
    - `context` 只能用于消歧，不能作为独立证据
    - 不能使用 runtime task 或说话人默认补齐字段
    - 如果字段不被 `evidence_quote` 或允许的 context 直接支撑，不能判 `verified`
  - 当前 prompt 结构（与真实实现一致）：

```text
System Prompt
- 你是飞书 Task Wiki 第二层 verifier
- 你不会重新抽取事件，只会判断给定 candidate_event 是否足以成为 verified session_event
- 输入只包括 core_entries、context_entries 和 candidate_event
- context 只能用于消歧，不能作为独立证据
- 不能使用 runtime task 或说话人默认补齐字段
- 如果字段不被 evidence_quote 或允许的 context 直接支撑，不能判 verified
- 只允许输出一个 JSON object，格式为：
  {"verdict":"verified|needs_review|rejected","claim_supported":true|false,"unsupported_parts":[],"reason":"..."}

User Prompt
{
  "trigger_entries": [...],
  "support_entries": [...],
  "context_entries": [...],
  "candidate_event": {...}
}
```

- **LLM 职责 3：第三层 Memory Block topic 归一**
  - 对应代码：`task-wiki/projector.js` 中的 `assignTopicsWithLLM(...)`
  - 作用：不是自由生成 Wiki，而是在字段粗分后，把语义上相近的 verified events 归并成稳定 topic
  - 例如把不同来源的事件归并成：
    - `发布时间口径`
    - `销售承诺风险`
    - `接口文档行动项`
    - `方案范围裁剪`
  - 严格约束：
    - 不能改 event 内容
    - 不能丢 event
    - 不能创造新事实
    - 只能做 topic 归一和命名
  - 当前 prompt 结构（与真实实现一致）：

```text
System Prompt
- You are normalizing verified task-wiki events into Memory Block topics
- Return one JSON object only
- Do not change event facts, do not invent new facts, and do not drop events
- You may only assign each event into a short Chinese topic_key/topic_title so semantically equivalent events share the same topic
- Prefer stable Chinese topic titles such as 发布时间口径, 销售承诺风险, 接口文档行动项, 方案范围裁剪

User Prompt
{
  "task": {
    "task_id": "...",
    "task_key": "..."
  },
  "previous_assignments": [...],
  "events": [
    {
      "event_id": "...",
      "event_type": "...",
      "coarse_key": "...",
      "suggested_topic_title": "...",
      "claim": "...",
      "key_field": "...",
      "evidence_quote": "..."
    }
  ],
  "output_schema": {
    "assignments": [
      {
        "event_id": "string",
        "topic_key": "short Chinese topic key",
        "topic_title": "short Chinese topic title"
      }
    ]
  }
}
```

- **LLM 职责 4：第三层摘要生成**
  - 对应代码：`task-wiki/projector.js` 中的 `requestSummary(...)`
  - 作用：
    - 生成 `session_wiki.md` 的 session summary
    - 生成单个 Memory Block 的 block summary
    - 生成 `task_wiki.md` 的 task summary
  - 严格约束：
    - 只能基于已经 verified 的 facts
    - 不能发明新事实
    - LLM 不可用时自动 fallback 到模板摘要
  - 当前 prompt 结构（与真实实现一致）：

```text
System Prompt
- You generate short Chinese summaries for Feishu Task Wiki pages
- Return one JSON object only
- Do not invent new facts and do not mention anything not grounded in the provided verified events

User Prompt
{
  "kind": "block | session | task",
  "payload": {...},
  "output_schema": {
    "summary": "short Chinese summary"
  }
}
```

- **当前真实边界**
  - LLM 负责的主要是：
    - candidate_event 抽取
    - verifier 判定
    - topic 归一
    - 摘要生成
  - LLM 不负责的部分：
    - task binding 主键决定
    - verified event 的程序硬校验
    - lifecycle overlay（revoke / invalidation / supersession）
    - block / slot / current item 的最终工程组织
  - 也就是说，这套系统不是“把所有事情交给大模型”，而是“让 LLM 只负责它擅长的语义判断，程序负责结构约束、追溯、校验和增量更新”。

4）项目亮点介绍
✨ **产品侧亮点**：
- 非侵入式设计：用户不需要改变飞书使用习惯，不需要手动打标签/记笔记，系统在后台自动处理当前支持的主链
- 全链路可追溯：所有决策都保留原始消息引用，支持一键回溯到原讨论位置
- 自动冲突检测：自动识别矛盾决策、过期承诺、未解决异议，避免信息不一致
- 分层知识组织：从单场讨论摘要到全局任务总览，三层Wiki结构满足不同查看需求

⚙️ **技术侧亮点**：
- 三层解耦架构：任务绑定、事件提取、Wiki投影三层独立，扩展性强
- 增量处理机制：仅处理新增消息，不需要全量重跑，性能高效
- 记忆全生命周期管理：支持决策更新、覆盖、废弃，自动维护信息有效性
- 严格工程规范：核心模块已有测试，并且补了 lint / forgetting / log 等运维侧产物

5）AI 亮点介绍
此模块侧重体现项目的 AI 工程化深度与落地价值：

**▸ 项目中使用了哪些高阶 AI 技巧？**
- 定制化场景Prompt工程：针对飞书对话场景设计专门的决策提取Prompt，内置对话角色、上下文格式、输出结构约束
- 结构化输出校验：对大模型返回结果做 JSON 格式校验、字段完整性校验、语义合理性校验
- 增量上下文拼接：仅拼接新增消息和相关上下文，避免token浪费
- 少样本引导：内置项目决策场景的Few-Shot示例，提升提取准确率

**▸ 项目中人和 AI 的分工是怎么样的？**
- 人：只需要正常在飞书里聊天讨论、做决策，不需要为了这套系统额外维护结构化笔记
- AI：自动完成「任务绑定→上下文聚合→事件提取→校验落盘→Wiki更新→冲突检测」主链；人工 review/retry 和主动告警仍在后续范围内
- （当前边界）人工 review / retry 流程还未最终接上，所以这里更适合写成“后续可补人工修正闭环”，不要写成已经上线可用

**▸ 项目中包含了哪些核心模型选型思路？**
- 优先选择支持函数调用/结构化输出的大模型，降低结果解析成本
- 平衡效果和成本：当前已经把抽取和投影的 LLM 使用与程序化校验拆开，但自动模型分档切换还没有作为已验证能力对外宣称
- 模型和业务逻辑基本解耦，可切换不同模型；不过“完全无需修改核心业务代码”这种表述还是偏满，建议降级描述

**▸ 引入 AI 后对原有工作流带来了哪些改变？**
- 原来：需要专门的项目助理手动整理群聊决策、更新项目文档，容易遗漏、更新不及时
- 现在：在当前已验证范围内，AI 可以把真实飞书群讨论自动沉淀成 task wiki 主产物；但人工 review/retry、主动告警推送、更多 source 类型仍有后续工作
- 原来：新人上手需要翻几百条历史聊天记录，还容易遗漏关键信息
- 现在：直接查看 Task Wiki 就能获取已沉淀的项目决策上下文，减少新人翻历史聊天记录的成本；具体缩短幅度目前还没有量化验证
- 原来：决策更新后需要专门在群里通知，很容易有人没看到导致执行错误
- 现在：系统已经能自动更新 Wiki、自动收敛当前态，并在 `lint/` 中报告冲突/失效/过期问题；主动告警推送还未实现
