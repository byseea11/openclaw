# Task Wiki 记忆系统架构说明

## 1. 核心目标

本系统的目标是围绕一个具体任务，持续沉淀企业协作过程中的项目记忆。

在日常协作中，一个任务相关的信息可能分散在多个群聊、文档、会议纪要、评论区或审批记录中。传统做法通常是在需要回答问题时临时检索原始消息，再让模型重新总结。这种方式的问题是，每次查询都像从零开始，历史讨论、决策依据、反对意见和约束条件很难形成长期积累。

本方案采用类似 LLM Wiki 的思路，但会把 Wiki 层和 event 抽取层明确分开：

- **event 抽取层**负责从原始协作内容中抽取可验证的最小协作事实；
- **Wiki 层**负责消费已经验证过的 events，并将它们组织成可检索、可更新、可追溯的任务记忆。

因此，本系统不是直接让模型总结群聊或文档，而是先把原始协作内容转化成 verified events，再由 Wiki 层把这些 events 聚合成结构化的 Memory Blocks。

整体链路可以理解为：

Raw Messages / Docs
→ Session Creation
→ Event Extraction / Verification
→ session.md + events.jsonl
→ session_wiki.md
→ Memory Blocks
→ index.md
→ task_wiki.md

---

## 2. 基础数据层：Session 与 Event

系统首先以 **task** 为核心组织所有信息。

一个 task 相关的内容可能来自不同来源，例如：

- 群聊 thread；
- 飞书文档；
- 会议纪要；
- 任务评论；
- 审批记录；
- 多维表格记录。

这些内容不会直接进入 Wiki，而是先被整理成一个个 **session**。

一个 session 表示围绕某个 task 的一次可摄入协作上下文。它可以是一段群聊、一个文档版本、一段会议纪要，或者某个任务评论窗口。

每个 session 至少包含两个核心文件：

### 2.1 session.md

`session.md` 保存该 session 的原始消息或原始内容。

它是事实来源。
Wiki 不直接把这里的内容当作结论，而是通过 event 引用它。

### 2.2 events.jsonl

`events.jsonl` 保存从该 session 中抽取并通过验证的 events。

event 不是模型自由总结出来的观点，而是由原文 quote 直接支撑的最小可验证协作事实。

event 可以包括：

- 结论或当前口径；
- 理由或依据；
- 异议、担忧或反对意见；
- 约束、边界或禁止项；
- 行动承诺；
- 状态事实；
- 时间点、截止日期或里程碑；
- 范围、阶段或适用对象。

这里需要强调一点：event 不一定是“状态改变”，更准确地说，它是**最小可验证协作事实**。例如，“我担心销售会直接拿 5 号承诺客户”并不是一个状态改变，但它是一个重要的 objection event，后续 Wiki 需要记住它。

---

## 3. Wiki 层的边界

Wiki 层不负责从原始消息中抽 event。

Wiki 层的输入是：

- `session.md`
- `events.jsonl`

Wiki 层的任务是：

- 读取 verified events；
- 按语义把 events 聚合成 Memory Blocks；
- 生成或更新 `session_wiki.md`；
- 更新 `index.md`；
- 按需刷新 `task_wiki.md`；
- 在后续查询时快速定位相关 Memory Block，并回溯到 event 和原始证据。

也就是说：

event extraction / verification 是 Wiki 的上游事实层；
Wiki 只消费已经验证过的 events。

这个边界很重要。它可以避免 Wiki 页面变成模型自由总结的结果，也可以保证每一条 Wiki 记忆都能回到具体的 event、quote 和原始 session。

---

## 4. session_wiki.md：一手 Wiki 页面

每个 session 会对应一个 `session_wiki.md`。

`session_wiki.md` 是该 session 的一手 Wiki 页面。它不是简单复述原始消息，也不是跨 session 的最终总结，而是把该 session 中的 verified events 按语义组织起来。

一个 session 中可能讨论多个事情。比如同一段群聊中，大家可能先讨论发布时间，再讨论销售承诺风险，随后又讨论接口文档行动项。这些内容虽然都属于同一个 task，但不应该混在一个大总结里。

因此，`session_wiki.md` 内部会拆成多个 **Memory Blocks**。

结构上可以理解为：

session_wiki.md
→ Memory Block 1
→ Memory Block 2
→ Memory Block 3
→ ...

每个 Memory Block 表示该 session 中围绕同一个问题、主题、决策轴或执行事项形成的一段局部记忆。

例如：

- Memory Block A：发布时间口径；
- Memory Block B：销售承诺风险；
- Memory Block C：接口文档行动项；
- Memory Block D：方案范围裁剪。

---

## 5. Memory Block 与 KI Slots

Memory Block 是 `session_wiki.md` 内部最重要的组织单元。

一个 Memory Block 会围绕同一主题聚合若干 events，并用一组结构化槽位组织这些信息。

第一版可以使用 8 个 KI Slots：

1. **Conclusion Slot**：结论 / 当前口径 / 决定；
2. **Rationale Slot**：理由 / 依据；
3. **Objection Slot**：异议 / 担忧 / 反对意见；
4. **Constraint Slot**：约束 / 边界 / 禁止项；
5. **Commitment Slot**：行动承诺；
6. **Status Slot**：状态事实；
7. **Time Slot**：时间点 / 截止日期 / 里程碑；
8. **Scope Slot**：范围 / 阶段 / 适用对象。

这些 slot 不直接从原文中编造内容，而是引用 `events.jsonl` 里的 verified events。

证据链路是：

session_wiki.md
→ Memory Block
→ KI Slot
→ event_ref
→ events.jsonl
→ evidence_quote
→ session.md / raw message

也就是说，KI Slot 里的每一条内容都应该能通过 event_ref 回到原文证据。

这样做的好处是，Memory Block 既能提供适合人阅读的结构化总结，又不会丢失可追溯性。

---

## 6. index.md：两层导航索引

`index.md` 的作用不是存储完整事实，也不是把所有 events 平铺出来。

它是 task 级别的导航文件，主要解决一个问题：

**当用户在协作场景中提到某个问题时，系统如何快速找到历史上相关的记忆块？**

因此，`index.md` 应该采用两层结构：

第一层是 **Wiki Page Index**：
记录这个 task 下有哪些 Wiki 页面，例如 `task_wiki.md`、各个 `session_wiki.md`，以及可选的 topic views。

第二层是 **Memory Block Index under each Wiki Page**：
在每个 Wiki 页面下面列出该页面包含哪些 Memory Blocks，并用一句话说明每个 Memory Block 在讨论什么。

结构可以理解为：

index.md
├── Task Overview
├── Wiki Page Index
│ ├── task_wiki.md
│ ├── sessions/A/session_wiki.md：一句话摘要
│ │ ├── Memory Block 1：一句话摘要
│ │ ├── Memory Block 2：一句话摘要
│ │ └── Memory Block 3：一句话摘要
│ └── sessions/B/session_wiki.md：一句话摘要
│ ├── Memory Block 1：一句话摘要
│ └── Memory Block 2：一句话摘要
└── Topic Routes，可选
├── 发布时间 → blocks
├── 风险 → blocks
└── 行动项 → blocks

也就是说，index 的顶层不是 Memory Block，而是 Wiki Page。Memory Block 是每个 Wiki Page 下面的二级索引项。

每个 Memory Block 在 index 中只需要保留轻量信息，例如：

- block link；
- block id；
- topic；
- status；
- slots；
- 一句话摘要。

index 不应该放完整证据、完整 event 列表或长摘要。这些信息应该留在 `session_wiki.md`、`events.jsonl` 和 `session.md` 中。

## 7. 检索流程

检索的目标是：当用户在群聊或任务上下文中提出一个问题时，系统能够快速判断历史上是否已有相关讨论，并返回合适的记忆卡片。

检索路径是：

Query
→ identify task
→ read index.md
→ select wiki page
→ select memory block
→ read KI slots
→ fetch event_refs if needed
→ return card

具体过程如下：

1. 先识别用户当前问题属于哪个 task；
2. 读取该 task 的 `index.md`；
3. 先扫描 Wiki Page Index，判断哪些 `session_wiki.md` 或 `task_wiki.md` 可能相关；
4. 再扫描这些 Wiki Page 下的 Memory Blocks；
5. 找到最相关的 Memory Block；
6. 读取该 block 里的 KI Slots；
7. 必要时通过 event_ref 回到 `events.jsonl` 和 `session.md`；
8. 生成一张可读的历史记忆卡片返回给用户。

检索结果可以分成三类：

### 7.1 Direct Hit

如果用户问题能直接命中某个 Memory Block，则返回该 block 的卡片。

例如，用户问：

“5 号这个时间能不能对外承诺？”

系统可以命中：

- 发布时间口径 block；
- 销售承诺风险 block；
- 对外沟通约束 block。

返回内容可以包括：

- 当前结论；
- 相关约束；
- 之前的异议或风险；
- 证据引用。

### 7.2 Related Hit

如果没有找到完全对应的 Memory Block，但存在相关历史讨论，则返回“相关历史记忆”。

例如，用户问的是一个新表达，但历史上已有类似的对外口径约束。系统可以提示：

“没有找到完全对应的历史结论，但有相关口径可参考。”

### 7.3 No Hit

如果没有找到相关 Memory Block，则不要强行召回不相关历史。

系统可以返回：

“没有找到与该问题直接相关的历史记忆。该问题可以作为新的讨论进入 session/event pipeline。”

## 8. 更新机制

系统采用增量更新，而不是每次全量重写。

当新的消息、文档内容或会议纪要进入系统时，流程是：

new raw content
→ update or create session
→ extract new events
→ verify events
→ append to events.jsonl
→ locate affected Memory Blocks
→ update session_wiki.md
→ update index.md
→ refresh task_wiki.md if needed

更新的核心是：

**优先更新受影响的 Memory Block，而不是重写整个 Wiki。**

当一个新 event 进入系统后，需要判断：

1. 它属于哪个 session；
2. 它影响哪个 `session_wiki.md`；
3. 它应该进入哪个 Memory Block；
4. 它应该填入哪个 KI Slot；
5. 它是否改变该 Memory Block 的 summary 或 status；
6. 它是否影响整个 `session_wiki.md` 的 session summary；
7. 它是否影响 `task_wiki.md` 的当前状态；
8. 它是否需要更新 `index.md` 中的摘要或状态。

例如，如果一个新 event 表明“目标发布时间从 5 月 5 日顺延到 5 月 10 日”，那么系统不应该删除旧 event，而应该：

- 保留旧 event 作为历史事实；
- 用新 event 更新相关 Memory Block 的当前状态；
- 将旧结论标记为 superseded；
- 在 `task_wiki.md` 中展示新的当前状态；
- 在时间线里保留历史变化。

---

## 9. 遗忘机制

遗忘用于处理来源被删除、消息被撤回、文档被删除、权限失效或 event 抽取错误等情况。

遗忘不应该默认物理删除所有信息。更稳妥的做法是先标记失效，再沿引用链更新 Wiki。

遗忘流程可以是：

source revoked / deleted
→ mark session as revoked
→ mark related events as source_revoked
→ find Memory Blocks referencing these events
→ remove or mark affected KI Slot items
→ update affected Memory Blocks
→ update session_wiki.md
→ update index.md
→ refresh task_wiki.md
→ append log.md

这样做的原因是：

- 可以保留审计线索；
- 可以避免引用突然断裂；
- 可以支持误删后的恢复；
- 可以区分“来源失效”和“被新事实覆盖”。

需要区分三类情况：

### 9.1 Source-level Forgetting

如果原始 session 被删除或撤回，则将该 session 标记为 revoked，并将相关 events 标记为 source_revoked。

如果某个 Memory Block 完全依赖这些失效 events，则该 block 应该被 archived 或 invalidated。

### 9.2 Event-level Invalidation

如果某个 event 后续被发现抽取错误，或者 claim 并不被 quote 支撑，则将该 event 标记为 invalidated。

随后更新引用该 event 的 KI Slots 和 Memory Blocks。

### 9.3 Knowledge-level Supersession

如果新事实覆盖旧事实，例如截止日期从 5 号改到 10 号，这不是遗忘，也不是删除。

旧 event 仍然保留，新的 event 成为当前状态。
`task_wiki.md` 默认展示新状态，但历史仍可追溯。

---

## 10. 最终结构总结

本系统的核心结构是：

session.md
保存原始 message / doc / meeting 内容。

events.jsonl
保存 verified events。

session_wiki.md
保存该 session 的一手 Wiki 页面，内部包含多个 Memory Blocks。

Memory Block
围绕某个主题、问题、决策轴或执行事项聚合 events。

KI Slot
Memory Block 内部的结构化栏目，包括 conclusion、rationale、objection、constraint、commitment、status、time、scope。

index.md
task 级导航索引，采用 Wiki Page → Memory Block 的两层结构。

task_wiki.md
基于多个 session_wiki 和 Memory Blocks 汇总出的任务当前状态视图。

最终证据链路是：

task_wiki.md / index.md
→ session_wiki.md
→ Memory Block
→ KI Slot
→ event_ref
→ events.jsonl
→ evidence_quote
→ session.md

---

## 11. 一句话概括

这套系统的核心思想是：

**先把 task 相关协作内容编译成 verified events，再让 Wiki 层把 events 聚合成 session_wiki 中的 Memory Blocks。index.md 负责用 Wiki Page → Memory Block 的两层结构做快速路由，task_wiki.md 负责呈现当前任务状态。更新和遗忘都沿着 event_ref 反向影响 Memory Block、index 和 task_wiki。**

换句话说：

**event 负责可信，Memory Block 负责组织，index 负责定位，task_wiki 负责当前状态。**
