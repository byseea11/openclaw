# 飞书 Task Wiki：基于 Session Event Ledger 的项目记忆系统

## 0. 核心理念

本系统面向飞书企业协作场景，目标不是对群聊、文档或会议纪要做一次性总结，而是围绕具体 `task_id` 增量构建并维护一个可追溯、可验证、可持续演进的项目记忆 Wiki。

传统 RAG 的工作方式是：在查询时临时检索原始资料，再让 LLM 重新拼接答案。这样每次回答都像从零开始，知识不会沉淀。

本系统采用 LLM Wiki 思路：当新的协作资料进入系统时，LLM 不只是为未来检索建立索引，而是将其编译为可验证的事实事件，并把这些事件增量整合进任务 Wiki 中。随着每个 session file 被摄入，任务 Wiki 会持续更新当前结论、理由、异议、约束、行动项、时间线和证据引用。

核心链路如下：

```text
原始飞书协作流
  → task_id 绑定
  → session file 摄入
  → Evidence Span 构造
  → Atomic Event 抽取与验证
  → Session-level Event Ledger
  → Task-level Index
  → KI 聚合
  → Task Wiki 更新
  → 检索 / 巡检 / 遗忘
```

其中最重要的原则是：

```text
Raw Source 是事实来源。
Session File 是一次可摄入的协作上下文文件。
Event 是可验证事实层。
Session Wiki 是局部记忆层。
Task Index 是跨 session 的导航和聚合层。
KI 是知识项聚合层。
Task Wiki 是当前状态视图。
```

系统不会直接让 LLM 总结一段群聊并写入 Wiki，而是先把重要协作文本拆成多个由原文证据支撑的最小事实 event。Wiki 再基于这些 event 进行归并、更新和展示。

---

# 1. 核心对象定义

## 1.1 Task

Task 是项目记忆的核心组织单位。

它可以是：

```text
- 一个项目任务
- 一个需求
- 一个问题单
- 一个缺陷修复
- 一个审批事项
- 一个里程碑目标
```

系统不再以个人、会话参与者或普通 thread 作为主要记忆对象，而是以 `task_id` 作为所有后续记忆处理的主键。

---

## 1.2 Raw Source

Raw Source 是不可变的原始资料。

它可以来自飞书中的多种协作载体：

```text
- 群聊消息
- 会话线程 thread
- 文档 document
- 文档评论
- 多维表格记录
- 会议纪要
- 审批记录
- 任务评论
```

Raw Source 原则上只读不改，是所有 event 和 Wiki 内容最终可回溯的事实来源。

---

## 1.3 Session File

Session File 是围绕某个 task 的一次可摄入协作上下文文件。

它不是完整群聊，也不是完整文档，而是经过 task 绑定和重要性过滤后形成的处理单位。

一个 session file 可以对应：

```text
- 某个 thread 中围绕 task 的关键讨论片段
- 某篇文档的一个版本或关键段落
- 某次会议纪要
- 某个任务评论区的一段变更讨论
- 某个群聊中围绕 task 的连续片段
```

因此：

```text
session_id ≠ thread_id
session_id = task_id + source_id + ingest_window / version
```

示例：

```text
task_id: FEISHU-231
session_id: FEISHU-231__thread_abc__2026-04-27
source_type: chat_thread
```

---

## 1.4 Event

Event 是从某个 session 的 Core 中抽取出的、由原文 quote 直接支撑的最小协作事实。

Event 不表示 Wiki 更新操作。

Event 不直接表示：

```text
- 新增 Wiki item
- 更新 Wiki 字段
- 删除旧结论
- 修改当前状态
```

这些都是 Wiki 消费 event 之后做的事情。

Event 只回答一个问题：

```text
这段 Core 原文中明确表达了什么可验证事实？
```

---

## 1.5 Session Wiki

Session Wiki 是一个 session file 被处理后的局部记忆页面。

它记录：

```text
- 这个 session 讨论了什么
- 这个 session 贡献了哪些 verified events
- 这些 events 对 task 有什么局部意义
- 这个 session 中有哪些待后续聚合的线索
```

Session Wiki 不是 Task Wiki 的最终状态，而是该 session 对 task 贡献的局部知识说明。

---

## 1.6 Task Index

Task Index 是 task 级别的导航和聚合层。

它维护：

```text
- 这个 task 有哪些 session
- 每个 session 贡献了哪些 event
- 哪些 event 影响了哪些 KI
- 当前哪些 KI 是 active
- 哪些旧结论被覆盖
- 哪些异议还没关闭
- 哪些行动项仍未完成
```

Task Index 对应 LLM Wiki 中的 `index.md` 思路，但更面向任务记忆系统。

---

## 1.7 KI

KI，即 Knowledge Item，是 Task Wiki 中的知识单元。

它不是直接从原文抽出来的，也不是 event 的同义词。

更准确地说：

```text
KI = 基于 Event Ledger 聚合出来的、面向 Wiki 展示和任务理解的知识项。
```

Event 是事实输入。

KI 是知识聚合结果。

---

## 1.8 Task Wiki

Task Wiki 是围绕 `task_id` 生成和维护的任务当前状态页面。

它不是原文总结，也不是 event 列表。

它是：

```text
基于所有 session event、KI 和 Task Index 编译出来的当前任务知识视图。
```

---

# 2. 目录结构建议

一个 task 可以对应一个本地 Wiki 目录。

建议结构如下：

```text
task_memory/
  FEISHU-231/
    task.yaml
    index.md
    log.md
    task_wiki.md

    sessions/
      2026-04-27_thread_abc/
        source.md
        metadata.yaml
        evidence_spans.jsonl
        events.jsonl
        session_wiki.md

      2026-04-28_doc_xyz/
        source.md
        metadata.yaml
        evidence_spans.jsonl
        events.jsonl
        session_wiki.md

    event_index.jsonl

    ki/
      overview.md
      findings.md
      decisions.md
      rationales.md
      objections.md
      constraints.md
      commitments.md
      timeline.md
      resources.md

    lint/
      open_conflicts.md
      stale_claims.md
      orphan_events.md
      unresolved_objections.md
      overdue_commitments.md
```

各文件职责：

```text
task.yaml:
任务元信息。

index.md:
任务级目录，记录 session、KI、当前状态和关键链接。

log.md:
只增日志，记录摄入、更新、巡检、遗忘操作。

task_wiki.md:
面向用户阅读的任务当前状态页面。

sessions/*/source.md:
本次摄入的 session 原始或半结构化文本。

sessions/*/evidence_spans.jsonl:
从 source 中筛出的 Evidence Span。

sessions/*/events.jsonl:
该 session 中抽取并验证后的 event。

sessions/*/session_wiki.md:
该 session 对 task 的局部记忆说明。

event_index.jsonl:
task 级跨 session event 索引。

ki/*.md:
按知识类型维护的聚合页面。

lint/*.md:
巡检结果和待处理问题。
```

# 3. 任务绑定和信息归类（Preprocessing）

## 3.1 目标

确定每条信息是否属于某个任务，并确保后续处理都围绕正确的 `task_id` 展开。

如果信息无法绑定到任何 `task_id`，则不进入记忆处理链路。

---

## 3.2 任务绑定规则

每个会话线程、文档或协作对象需要尽可能绑定到一个明确的 `task_id`。

绑定方式包括：

```text
1. 显式绑定
   - 文档创建时选择所属 task
   - thread 开启时选择所属 task
   - 任务卡片下的评论天然继承 task_id

2. 继承绑定
   - thread 继承父消息的 task_id
   - 文档评论继承文档的 task_id
   - 会议纪要继承会议关联任务的 task_id

3. 上下文绑定
   - 消息中出现任务编号、需求编号、项目名
   - 消息所在群或频道与某个 task 有明确关联
   - 文档标题、父目录或模板中包含 task 线索
```

处理规则：

```text
未绑定 task_id 的信息 → 不处理
已绑定 task_id 的信息 → 形成 task-bound source unit，进入 session file 构造
```

---

## 3.3 输出

Preprocessing 阶段输出的是：

```text
Task-bound Source Unit
```

它至少包含：

```text
- task_id
- source_type
- source_id
- thread_id / doc_id / message_id
- parent_id
- author
- timestamp
- raw_content
```

这一层只负责回答：

```text
这条信息属于哪个任务？
```

它不负责判断这条信息是否值得进入 Wiki。

---

# 4. Session File 摄入

## 4.1 目标

将已绑定 `task_id` 的协作内容整理成一次可摄入的 session file。

Session File 是后续 event 抽取的基本处理单位。

---

## 4.2 Session File 不是完整原始流

系统不会把完整群聊、完整 thread 或完整文档无差别写入记忆系统。

Session File 应该是：

```text
围绕某个 task 的一次重要协作上下文文件。
```

它可以通过以下方式形成：

```text
- 按 thread 形成 session file
- 按文档版本形成 session file
- 按会议纪要形成 session file
- 按任务评论窗口形成 session file
- 按一段连续的 task 相关群聊形成 session file
```

---

## 4.3 Session File 元数据

每个 session file 至少包含：

```text
- session_id
- task_id
- source_type
- source_id
- source_title
- time_range
- participants
- ingest_time
- source_url
- source_hash / version
```

---

# 5. Evidence Span 构造

## 5.1 目标

从 session file 中筛选出可能包含关键协作事实的片段，并为 event 抽取构造必要上下文。

Evidence Span 不是完整 session。

Evidence Span 是经过重要性过滤后的候选证据包。

---

## 5.2 Evidence Span 的结构

一个 Evidence Span 由三部分组成：

```text
1. Core
2. Context
3. Current State Context
```

---

## 5.3 Core

Core 是真正待处理的关键文本片段。

只有 Core 可以触发新的 event。

Core 中必须出现新的协作事实动作，例如：

```text
- 明确结论
- 给出理由
- 提出异议
- 增加约束
- 分配行动项
- 表达状态变化
- 确认时间点
- 明确范围边界
```

如果 Core 只是：

```text
- 收到
- 好的
- 我看看
- +1
- 辛苦了
```

则不生成 event。

---

## 5.4 Context

Context 是为了帮助理解 Core 的最小必要上下文。

Context 可以用于解释：

```text
- “这个”指什么
- “刚才那个方案”是哪一个
- “那个日期”是哪一天
- “按上面说的”指哪条结论
- “这个风险”对应哪个风险
```

但是 Context 不能单独生成 event。

也就是说：

```text
Core 决定是否抽取 event。
Context 只负责消歧。
```

---

## 5.5 Current State Context

Current State Context 是当前 Task Wiki 或已有 event index 中提取出来的状态摘要。

它可以包含：

```text
- 当前 active conclusion
- 当前时间点
- 当前开放行动项
- 当前未关闭异议
- 当前风险或约束
- 当前项目阶段
```

它的作用是帮助模型理解当前已有口径，避免重复抽取或错误解释。

但是它有一个硬约束：

```text
Current State Context 不能作为新 event 的证据。
```

它只能用于理解和消歧，不能用于支撑新的 claim。

---

# 6. Atomic Event 抽取

## 6.1 Event 的定义

Event 是从 Evidence Span 的 Core 中抽取出的、由原文 quote 直接支撑的最小协作事实断言。

定义如下：

```text
Event = 从 Core 原文中抽取出的、由一个或多个 quote 直接支撑的最小协作事实断言。
```

Event 不表示 Wiki 更新操作。

Event 只回答一个问题：

```text
这段 Core 原文中明确表达了什么可验证事实？
```

---

## 6.2 Event 抽取原则

每条 event 必须满足：

```text
1. 必须由 Core 触发
2. 必须有 evidence_quote
3. evidence_quote 必须来自 Core
4. claim 只能表达一个事实
5. claim 不能超出 evidence_quote 与必要 Context quote 的支持范围
6. Context 只能用于消歧，不能单独生成 event
7. Current State Context 不能作为证据
8. 原文没有的信息不能补
```

---

## 6.3 Event 类型

第一版 event 使用 8 类。

这 8 类不是 Wiki 模块，而是可验证事实类型。

```text
1. conclusion_event：结论 / 口径 / 决定
2. rationale_event：理由 / 依据
3. objection_event：异议 / 担忧 / 反对意见
4. constraint_event：约束 / 边界 / 禁止项
5. commitment_event：承诺 / 行动项
6. status_event：状态事实
7. time_event：时间点 / 截止日期 / 里程碑
8. scope_event：范围 / 阶段 / 适用对象
```

---

## 6.4 Event 类型说明

### conclusion_event：结论 / 口径 / 决定

用于表示 Core 中明确表达了一个结论、决定、选择或当前口径。

典型原文：

```text
那就先按方案 B 来。
本期不做自定义节点。
这个先按 5 月 5 日推进。
```

验证要求：

```text
- quote 中必须有明确结论动作
- 不能把“先按”抽成“最终决定”
- 不能把个人建议抽成团队结论
```

---

### rationale_event：理由 / 依据

用于表示 Core 中给出了某个选择、判断、风险或约束背后的原因。

典型原文：

```text
方案 A 成本太高。
因为迁移窗口还没锁定。
客户主要卡在审批配置复杂。
```

验证要求：

```text
- quote 必须表达原因、依据或背景
- claim 只能保留原因本身
- reason_for 可以通过 Context 消歧，但不能凭空补
```

---

### objection_event：异议 / 担忧 / 反对意见

用于表示 Core 中有人提出了反对、担忧、风险提醒或保留意见。

典型原文：

```text
我担心方案 B 后面扩展性不够。
这个时间销售可能会拿去承诺客户。
我不同意这期砍掉审批配置。
```

验证要求：

```text
- quote 必须包含担忧、反对、不同意、风险提醒等语气
- 普通提问不抽 objection_event
- objector 必须来自说话人或原文
- 不能把模型推测的风险写进 event
```

---

### constraint_event：约束 / 边界 / 禁止项

用于表示 Core 中出现了限制、禁止、边界、规则或外部口径约束。

典型原文：

```text
不要对外说死。
不能承诺 5 号一定上线。
这个接口不能破坏现有兼容性。
所有客户定制需求都必须先进需求池。
```

验证要求：

```text
- quote 必须表达限制、禁止、必须、边界或约束
- target 可以由 Context 消歧
- claim 中的约束强度不能超过原文
- “不要对外说死”不能抽成“禁止对外沟通”
```

---

### commitment_event：承诺 / 行动项

用于表示 Core 中出现了行动承诺或责任分配。

典型原文：

```text
李四周五前补齐接口文档。
我来同步销售。
研发这周给出排期。
```

验证要求：

```text
- quote 必须能识别 owner + action
- deadline 没出现就填 null
- “后面看看”不算 commitment
- owner 不明确时降级为 candidate 或不抽
```

---

### status_event：状态事实

用于表示 Core 中表达了某个对象的状态。

典型原文：

```text
接口文档我补好了。
这个风险还没解。
迁移窗口还没锁定。
审批还没过。
```

验证要求：

```text
- quote 必须表达明确状态
- target 必须能从 Core 或 Context 解析
- 不要把情绪判断抽成状态
```

---

### time_event：时间点 / 截止日期 / 里程碑

用于表示 Core 中确认、暂定、修改或顺延了某个时间点。

典型原文：

```text
截止日期是 5 号。
目标发布时间暂定 5 月 5 日。
从 5 号顺延到 10 号。
下周三评审。
```

验证要求：

```text
- quote 必须包含时间表达
- time_target 必须明确
- “5 号吧”如果 Context 不能解析对象，则不抽
- 必须保留原文强度：暂定、确认、不确定、顺延
```

---

### scope_event：范围 / 阶段 / 适用对象

用于表示 Core 中明确了范围、阶段、适用对象、包含项或排除项。

典型原文：

```text
本期只做模板化配置，不做自定义节点。
这个规则只适用于 P0 客户问题。
先在华东区试点。
MVP 阶段不支持多审批人。
```

验证要求：

```text
- quote 必须表达范围、阶段、适用对象或排除项
- included / excluded 必须能在 quote 中找到
- 不要把决策原因混进 scope_event
```

---

# 7. Event Verification

## 7.1 目标

Verification 的目标不是给 event 打一个主观置信度，而是确保 event 满足：

```text
1. 证据位置可追溯
2. 字段结构完整
3. claim 被证据支持
4. event 是原子的
```

系统不是：

```text
先让模型自由抽 event，再问它可不可信
```

而是：

```text
只允许模型抽那些能被原文 quote 直接支撑的 event。
不满足证据形态和字段规则的 event 不能进入 ledger。
```

---

## 7.2 Location Verification

验证 event 的 `evidence_quote` 是否真的来自 Core。

规则：

```text
1. evidence_quote 必须是 Core entry 的子串，或经过轻微归一化后可匹配
2. 必须记录 core_entry_id
3. 如果 quote 出现在多个 Core entry 中，必须能唯一定位
4. quote 不能来自 Context
5. quote 不能来自 Current State Context
```

这一层应尽量程序化完成。

---

## 7.3 Schema Verification

验证不同 event 类型是否满足对应的必填字段。

例如：

```text
conclusion_event:
- claim
- target
- conclusion
- evidence_quote

rationale_event:
- claim
- reason
- evidence_quote

objection_event:
- claim
- objector
- target
- objection
- evidence_quote

constraint_event:
- claim
- target
- constraint
- evidence_quote

commitment_event:
- claim
- owner
- action
- evidence_quote

status_event:
- claim
- target
- status
- evidence_quote

time_event:
- claim
- time_target
- time_value
- certainty
- evidence_quote

scope_event:
- claim
- scope_target
- evidence_quote
```

如果必填字段缺失，系统不应该让模型硬补，而应该标记为：

```text
candidate / needs_review / rejected
```

---

## 7.4 Claim Support Verification

验证 claim 是否真的被 `evidence_quote` 和必要的 `context_quotes` 支撑。

这一层可以由 verifier LLM 完成，但 verifier 只能做判断，不重新发明 event。

它需要判断：

```text
- claim 的每个关键信息是否都有证据
- claim 是否加入了原文没有的强度
- claim 是否把暂定说成确认
- claim 是否把担忧说成事实已经发生
- claim 是否把建议说成决策
```

---

## 7.5 Atomicity Verification

验证一条 event 是否只表达一个事实。

不合格示例：

```text
因为方案 A 成本高，所以本期采用方案 B，并由李四周五前补文档。
```

这句话至少应该拆成三条 event：

```text
1. rationale_event：方案 A 成本高
2. conclusion_event：本期采用方案 B
3. commitment_event：李四周五前补文档
```

Atomicity Verification 的目标是避免 event 退化成“总结”。

---

## 7.6 Verification 结果

event verification 不应该只有通过和失败，而应该允许三种结果：

```text
verified:
证据直接支撑，可以进入 event ledger。

candidate:
信息有价值，但 target / owner / relation 等字段不完整，需要后续确认。

rejected:
证据不足、过度推断、context-only、非原子，不能进入 event ledger。
```

---

# 8. 记忆存储：Session Event Ledger 与 Task Index

## 8.1 存储目标

记忆存储的目标不是把所有 event 混进一个不可区分的大表，而是同时保证：

```text
1. event 能回到具体 session 和证据来源
2. task 能跨 session 检索和聚合 event
```

因此采用双层存储：

```text
Session-level Event Ledger：保留完整证据归属
Task-level Event Index：支持跨 session 聚合和检索
```

---

## 8.2 Session-level Event Ledger

每个 session 保存自己的 event：

```text
sessions/{session_id}/events.jsonl
```

每条 event 至少包含：

```json
{
  "event_id": "evt_xxx",
  "task_id": "FEISHU-231",
  "session_id": "2026-04-27_thread_abc",
  "event_type": "constraint_event",
  "claim": "5 月 5 日不能作为确定的对外承诺日期",
  "core_entry_id": "msg_123",
  "evidence_quote": "不要对外说死",
  "context_quotes": [
    {
      "entry_id": "msg_120",
      "quote": "目标发布时间暂定 5 月 5 日",
      "role": "resolve_reference"
    }
  ],
  "event_time": "2026-04-27T10:30:00+08:00",
  "verification": {
    "verdict": "verified"
  }
}
```

---

## 8.3 Task-level Event Index

每个 task 维护跨 session event 索引：

```text
event_index.jsonl
```

它可以只保存检索和聚合所需字段：

```json
{
  "event_id": "evt_xxx",
  "task_id": "FEISHU-231",
  "session_id": "2026-04-27_thread_abc",
  "event_type": "constraint_event",
  "topic": "发布时间口径",
  "claim": "5 月 5 日不能作为确定的对外承诺日期",
  "event_time": "2026-04-27T10:30:00+08:00",
  "status": "active",
  "source_path": "sessions/2026-04-27_thread_abc/events.jsonl"
}
```

---

## 8.4 存储原则

```text
1. Raw Source 不改
2. Session File 可版本化
3. Event 只增，不随意覆盖
4. Session Event Ledger 保存完整证据
5. Task Event Index 保存可检索摘要
6. Wiki 页面可以被重写，因为它是编译结果
```

写入前不需要再做独立的“存储语义校验”，因为 event 是否可信已经在 extraction verification 阶段完成。

---

# 9. KI：知识项聚合层

## 9.1 KI 的定位

KI 是 Task Wiki 中的知识单元。

更准确地说：

```text
KI = 基于多个 session event 聚合出来的、面向 Wiki 展示和任务理解的知识项。
```

Event 是事实输入。

KI 是知识聚合结果。

---

## 9.2 KI 与 Event 的关系

一个 KI 可以由一个或多个 event 支撑。

例如：

```text
KI：发布时间口径
```

可能由以下 event 支撑：

```text
time_event：目标发布时间暂定为 5 月 5 日
constraint_event：5 月 5 日不能作为确定对外承诺
objection_event：有人担心销售会把 5 月 5 日承诺给客户
conclusion_event：外部口径改为预计 5 月上旬
```

因此，KI 不应该只保存一个总结，而应该保留它背后的 event references。

---

## 9.3 KI 类型

第一版 Task Wiki 中可以维护 6 类 KI：

```text
1. Finding KI：事实、问题、风险发现
2. Decision KI：决策、结论、取舍
3. Rationale KI：理由、依据
4. Objection KI：异议、担忧、反对意见
5. Rule / Constraint KI：规则、约定、约束、边界
6. Commitment KI：行动项、承诺、owner、deadline
```

这些 KI 类型用于组织 Wiki 页面，而不是 event 抽取类型。

---

## 9.4 KI 通用字段

每个 KI 至少包含：

```text
- ki_id
- task_id
- ki_type
- title
- current_claim
- status
- related_events
- evidence_quotes
- participants
- owner
- created_at
- updated_at
- valid_from
- valid_until
- relations
```

其中最重要的是：

```text
related_events:
该 KI 由哪些 event 支撑。

evidence_quotes:
从 related_events 中回溯出来的关键原文证据。

status:
当前是否 active、superseded、resolved、open、done。
```

---

# 10. Task Wiki 更新

## 10.1 目标

Task Wiki 是围绕 `task_id` 生成和维护的任务当前状态页面。

它不是原文总结，也不是 event 列表。

它是：

```text
基于 Session Event Ledger、Task Event Index 和 KI 聚合生成的任务当前知识视图。
```

---

## 10.2 Task Wiki 页面结构

每个 task 可以维护一个 Wiki 页面，包含：

```text
1. 当前摘要
2. 当前结论
3. 关键决策
4. 决策依据
5. 异议与风险
6. 规则与约束
7. 行动项
8. 时间线
9. 关联资源
10. 原始证据引用
```

---

## 10.3 更新流程

当新 session 被摄入后，执行：

```text
1. 从 session file 中抽取 verified events
2. 写入 sessions/{session_id}/events.jsonl
3. 更新 task/event_index.jsonl
4. 根据 event 更新或创建 KI
5. 刷新 task_wiki.md
6. 更新 index.md
7. 追加 log.md
8. 可选触发 lint
```

---

## 10.4 Wiki 更新规则

Task Wiki 每次更新时，应满足：

```text
1. 每个 Wiki 结论都能追溯到 KI
2. 每个 KI 都能追溯到 related_events
3. 每个 event 都能追溯到 Core evidence_quote
4. Wiki 可以生成当前状态，但不能抹掉历史事实
5. 新 event 可以使旧 KI 失效、被修订或被标记为已解决
```

---

## 10.5 Wiki 不是 Event Ledger 的简单拼接

Event Ledger 是事实流水。

Task Wiki 是聚合视图。

例如：

```text
4 月 20 日：
time_event：截止日期是 5 月 5 日。

4 月 28 日：
time_event：截止日期从 5 月 5 日顺延到 5 月 10 日。
```

Event Ledger 中两条 event 都保留。

但 Task Wiki 当前状态应该是：

```text
当前截止日期：5 月 10 日
历史变更：
- 4 月 20 日：截止日期为 5 月 5 日
- 4 月 28 日：截止日期顺延到 5 月 10 日
```

这体现了 Wiki 的职责：

```text
保留历史事实，同时维护当前有效状态。
```

---

# 11. 记忆检索

## 11.1 目标

当后续讨论触及某个 task 或相关主题时，系统可以快速召回历史上下文。

检索不应直接从原始资料开始，而应优先使用已经编译好的 Wiki 和索引。

---

## 11.2 检索路径

推荐路径：

```text
Query
  → Task Index
  → KI
  → Event
  → Evidence Quote
  → Raw Source
```

即：

```text
1. 根据 task_id 找 Task Index
2. 根据话题 / 实体 / 时间找相关 KI
3. 根据 KI 找 related_events
4. 根据 event 找 evidence_quote
5. 必要时回到 session source
```

这比普通 RAG 更稳定，因为它不是每次重新理解原始资料，而是复用已经编译过的 task memory。

---

## 11.3 主动推送：历史决策卡片

当后续讨论触及某个 task 或相关主题时，系统可以生成历史决策卡片。

卡片可以包含：

```text
- 当前结论
- 当时理由
- 反对意见
- 未关闭风险
- 相关约束
- 后续行动项
- 时间线
- 原始证据链接
```

示例：

```text
历史决策卡片：FEISHU-231 发布时间口径

当前状态：
- 内部目标发布时间：5 月 5 日
- 对外口径：预计 5 月上旬
- 对外不可承诺具体日期

理由：
- 迁移窗口尚未锁定

异议 / 风险：
- 销售可能将 5 月 5 日直接承诺给客户

相关行动：
- 需要同步销售统一外部口径

来源：
- session: 2026-04-27_thread_abc
- event_001, event_002, event_003
```

---

# 12. 记忆巡检：Lint

## 12.1 目标

Lint 用于维护 Task Wiki 的长期健康度。

它不是抽取流程，而是周期性检查和修复流程。

---

## 12.2 巡检内容

Lint 应检查：

```text
1. 是否有 event 没有进入任何 KI
2. 是否有 KI 没有证据
3. 是否有旧结论被新 event 覆盖但还显示为 active
4. 是否有开放异议长期未解决
5. 是否有行动项过期
6. 是否有 session 被删除但 event 仍在支撑 Wiki
7. 是否有 claim 强度超过 quote
8. 是否有同一 topic 下的结论冲突
9. 是否有孤立 session 或孤立 KI
10. 是否缺少必要交叉引用
```

---

## 12.3 巡检输出

巡检结果可以写入：

```text
lint/open_conflicts.md
lint/stale_claims.md
lint/orphan_events.md
lint/unresolved_objections.md
lint/overdue_commitments.md
```

并追加到 `log.md`。

---

# 13. 记忆遗忘：Forgetting

## 13.1 目标

企业协作记忆不能只增加，还需要支持遗忘、失效、覆盖和隐藏。

遗忘不是简单删除，而是要保证可追溯和当前视图正确。

---

## 13.2 Source-level Forgetting：来源删除

适用于：

```text
- 原始消息被删除
- 文档被撤回
- 用户要求移除某个来源
- 来源不再有权限访问
```

处理方式：

```text
1. 标记 session 为 revoked / deleted
2. 找出该 session 贡献的所有 events
3. 将这些 events 标记为 source_revoked
4. 重新计算受影响 KI
5. 更新 task_wiki.md
6. 在 log.md 记录遗忘操作
```

如果 event 失去唯一证据，它不能继续作为 active fact。

---

## 13.3 Event-level Invalidation：事件失效

适用于：

```text
- event 抽取错误
- verification 后续发现不成立
- quote 不支持 claim
- 人工审核驳回
```

处理方式：

```text
event.status = invalidated
event.invalidated_reason = ...
event.invalidated_at = ...
```

然后重建相关 KI 和 Task Wiki。

---

## 13.4 Knowledge-level Supersession：知识被覆盖

适用于：

```text
- 截止日期从 5 号改到 10 号
- 决策从方案 A 改成方案 B
- 风险已解决
- 行动项已完成
```

这不是删除旧 event。

旧 event 仍然存在，但 KI 当前状态被新 event 覆盖。

例如：

```text
event_001: 截止日期是 5 月 5 日
event_008: 截止日期顺延到 5 月 10 日
```

Task Wiki 中显示：

```text
当前截止日期：5 月 10 日
历史：
- 曾定为 5 月 5 日
- 后顺延到 5 月 10 日
```

---

## 13.5 View-level Forgetting：当前视图隐藏

适用于：

```text
- 旧结论已经无关
- 行动项已完成很久
- 风险已关闭
- 当前讨论不需要展示
```

处理方式：

```text
event 仍保留
KI 状态变为 archived / resolved / superseded
Task Wiki 默认不展示，但时间线和证据仍可查
```

---

# 14. 日志与索引

## 14.1 index.md

`index.md` 是 task 的内容目录。

它应记录：

```text
- task 基本信息
- session 列表
- 当前 active KI
- 当前未关闭异议
- 当前开放行动项
- 关键时间点
- 重要资源链接
- 最近更新
```

---

## 14.2 log.md

`log.md` 是只增日志。

它记录：

```text
- session ingest
- event extraction
- KI update
- task wiki refresh
- lint
- forgetting
- manual review
```

建议使用统一前缀，便于解析：

```text
## [2026-04-27] ingest | 2026-04-27_thread_abc
## [2026-04-27] extract | 12 verified events
## [2026-04-27] update | refreshed task_wiki.md
## [2026-04-28] lint | 2 overdue commitments
## [2026-04-29] forget | revoked session 2026-04-20_doc_old
```

---

# 15. 系统操作总览

## 15.1 提取 Extraction

```text
1. 确认 source 已绑定 task_id
2. 形成 session file
3. 筛选 Evidence Span
4. 区分 Core / Context / Current State Context
5. 从 Core 抽取 atomic event
6. 执行 verification
7. 写入 session events.jsonl
```

---

## 15.2 存储 Storage

```text
1. Raw Source 只读保存
2. Session File 版本化保存
3. Event 写入 session-level event ledger
4. Event 摘要注册到 task-level event index
5. Wiki 页面作为编译产物可重写
```

---

## 15.3 检索 Retrieval

```text
1. 根据 task_id 找 Task Index
2. 根据 topic / entity / time 找 KI
3. 根据 KI 找 related_events
4. 根据 event 找 evidence_quote
5. 必要时回到 session source
```

---

## 15.4 更新 Update

```text
1. 新 session 被摄入
2. 抽取 verified events
3. 更新 event_index.jsonl
4. 创建或更新 KI
5. 刷新 task_wiki.md
6. 更新 index.md
7. 追加 log.md
8. 可选触发 lint
```

---

## 15.5 遗忘 Forgetting

```text
1. 来源删除 → source-level forgetting
2. event 错误 → event-level invalidation
3. 新事实覆盖旧知识 → knowledge-level supersession
4. 旧内容不再展示 → view-level forgetting
```

---

# 16. 最终总结

本系统以 `task_id` 为核心组织飞书企业协作记忆。

它的关键不是让 LLM 直接总结协作内容，而是构建一条可验证、可索引、可维护的事实链路：

```text
Raw Source
  → Task-bound Source Unit
  → Session File
  → Evidence Span
  → Atomic Event
  → Session Event Ledger
  → Task Event Index
  → KI
  → Task Wiki
```

其中：

```text
Raw Source:
不可变事实来源。

Task-bound Source Unit:
确认信息属于哪个 task。

Session File:
一次可摄入的 task 协作上下文文件。

Evidence Span:
从 session 中筛出的候选证据包。

Atomic Event:
从 Core 中抽取出的最小可验证协作事实。

Session Event Ledger:
按 session 保存完整 event 和证据归属。

Task Event Index:
跨 session 聚合 event，支持检索和 Wiki 编译。

KI:
基于 event 聚合出的任务知识项。

Task Wiki:
基于 KI 和 event index 维护的任务当前状态页面。
```

最终，系统可以在后续协作中主动感知相关话题，召回历史决策、理由、异议、约束、行动项和证据来源，减少信息差、避免重复争论，并降低团队沟通成本。
