# Event

不是：

```text
先让模型抽 event
再问模型这个 event 可不可信
```

而应该是：

```text
只允许模型抽那些能被原文 quote 直接支撑的 event
每一种 event 都有明确的证据形态和校验规则
不满足证据形态，就不允许抽
```

之前方案里已经有一个很重要的基础：**Core 负责触发新 event，Context 只负责消歧，current_state_context 不能作为证据**。这条原则应该继续保留，因为它正好解决“模型看了上下文以后自由总结”的问题。

---

# 1. 可验证 event 的核心定义

我建议你先把 event 定义成：

```text
Event = 从 Core 原文中抽取出的、由一个或多个 quote 直接支撑的最小协作事实断言。
```

这里有三个关键词：

## 1）从 Core 原文中抽取

event 必须由 Core 触发。
Context 可以解释“这个”“刚才”“那个日期”，但不能自己生成 event。

## 2）quote 直接支撑

event 不能是“模型觉得应该是这样”。
它必须能回答：

> 这条 claim 的哪一部分来自哪句原文？

## 3）最小协作事实断言

一条 event 只能表达一个事实。
不能把“理由 + 结论 + 行动项 + 风险”揉在一起。

---

# 3. event 类型

## A. conclusion_event：结论 / 口径 / 决定

**抽什么：**
明确表达“怎么定”“按什么来”“当前结论是什么”。

**典型原文：**

```text
那就先按方案 B 来。
本期不做自定义节点。
这个先按 5 月 5 日推进。
```

**event：**

```json
{
  "event_type": "conclusion_event",
  "claim": "本期先采用方案 B",
  "target": "方案选择",
  "conclusion": "采用方案 B",
  "evidence_quote": "那就先按方案 B 来"
}
```

**验证规则：**

```text
1. quote 中必须出现明确结论词：
   “定了 / 按...来 / 采用 / 不做 / 先走 / 确认 / 结论是”
2. claim 不能添加 quote 中没有的强度。
   “先按方案 B 来”不能抽成“长期采用方案 B”。
3. 如果只是个人建议，不抽 conclusion_event。
   “我觉得方案 B 可以”不是结论。
```

---

## B. rationale_event：理由 / 依据

**抽什么：**
某个选择、判断、担忧、约束背后的原因。

**典型原文：**

```text
方案 A 成本太高。
因为迁移窗口还没锁定。
客户现在主要卡在审批配置复杂。
```

**event：**

```json
{
  "event_type": "rationale_event",
  "claim": "方案 A 成本过高",
  "reason": "方案 A 成本过高",
  "reason_for": "不采用方案 A / 采用方案 B",
  "evidence_quote": "方案 A 成本太高"
}
```

**验证规则：**

```text
1. quote 必须表达原因、依据或背景。
2. claim 只能保留原因本身。
3. reason_for 可以来自 Context 消歧，但不能凭空补。
4. 如果 quote 只是结论，不要强行抽 rationale。
```

注意：
`rationale_event` 不一定自己知道它支持哪个 conclusion。
可以后面由 wiki 或 relation resolver 去关联。

---

## C. objection_event：异议 / 担忧 / 反对意见

**抽什么：**
有人提出不同意见、风险担忧、保留态度。

**典型原文：**

```text
我担心方案 B 后面扩展性不够。
这个时间销售可能会拿去承诺客户。
我不同意这期砍掉审批配置。
```

**event：**

```json
{
  "event_type": "objection_event",
  "claim": "王五担心方案 B 后续扩展性不足",
  "objector": "王五",
  "target": "方案 B",
  "objection": "后续扩展性不足",
  "evidence_quote": "我担心方案 B 后面扩展性不够"
}
```

**验证规则：**

```text
1. quote 必须包含担忧、反对、不同意、风险提醒等语气。
2. 如果只是普通问题，不抽 objection。
   “方案 B 怎么实现？”不是 objection。
3. objector 必须来自说话人或 quote 明确指向。
4. 不能把模型推测的风险写进 objection。
```

这类 event 对“避免重复争论”非常重要。

---

## D. constraint_event：约束 / 边界 / 禁止项

**抽什么：**
不能做什么、必须满足什么、对外口径限制、规则边界。

**典型原文：**

```text
不要对外说死。
不能承诺 5 号一定上线。
这个接口不能破坏现有兼容性。
所有客户定制需求都必须先进需求池。
```

**event：**

```json
{
  "event_type": "constraint_event",
  "claim": "5 月 5 日不能作为确定的对外承诺日期",
  "target": "5 月 5 日上线时间",
  "constraint": "不能对外说死",
  "evidence_quote": "不要对外说死",
  "context_quotes": ["目标发布时间暂定 5 月 5 日"]
}
```

**验证规则：**

```text
1. quote 必须表达限制、禁止、必须、边界、约束。
2. 如果 target 依赖指代，可以用 Context 解析。
3. claim 中的约束强度不能超过 quote。
   “不要对外说死”不能抽成“禁止对外沟通该事项”。
4. 如果是一次性约束还是长期规则，event 层不强判，wiki 层再归类。
```

---

## E. commitment_event：承诺 / 行动项

**抽什么：**
谁要做什么，最好有时间。

**典型原文：**

```text
李四周五前补齐接口文档。
我来同步销售。
研发这周给出排期。
```

**event：**

```json
{
  "event_type": "commitment_event",
  "claim": "李四需要在周五前补齐接口文档",
  "owner": "李四",
  "action": "补齐接口文档",
  "deadline": "周五",
  "evidence_quote": "李四周五前补齐接口文档"
}
```

**验证规则：**

```text
1. quote 必须能识别 owner + action。
2. deadline 没出现就填 null，不能脑补。
3. “后面看看”不算 commitment。
4. 如果 owner 不明确，降级为 candidate 或不抽。
```

这类 event 最好要求 `owner` 和 `action` 必填，否则行动项会很脏。

---

## F. status_event：状态事实

**抽什么：**
某件事完成了、没完成、阻塞了、还没解决、已确认、待确认。

**典型原文：**

```text
接口文档我补好了。
这个风险还没解。
迁移窗口还没锁定。
审批还没过。
```

**event：**

```json
{
  "event_type": "status_event",
  "claim": "迁移窗口尚未锁定",
  "target": "迁移窗口",
  "status": "unlocked",
  "evidence_quote": "迁移窗口还没锁定"
}
```

**验证规则：**

```text
1. quote 必须表达明确状态。
2. target 必须能从 Core 或 Context 解析。
3. 状态值要来自受控枚举：
   done / open / blocked / unresolved / confirmed / unconfirmed / pending
4. 不要把情绪判断抽成状态。
```

---

## G. time_event：时间点 / 截止日期 / 里程碑

**抽什么：**
确认、暂定、修改、顺延某个时间。

**典型原文：**

```text
截止日期是 5 号。
目标发布时间暂定 5 月 5 日。
从 5 号顺延到 10 号。
下周三评审。
```

**event：**

```json
{
  "event_type": "time_event",
  "claim": "目标发布时间暂定为 5 月 5 日",
  "time_target": "目标发布时间",
  "time_value": "5 月 5 日",
  "certainty": "tentative",
  "evidence_quote": "目标发布时间暂定 5 月 5 日"
}
```

**验证规则：**

```text
1. quote 必须包含时间表达。
2. time_target 必须明确，不能只有孤立时间。
   “5 号吧”如果 Context 不能解析 target，就不抽。
3. certainty 必须保留原文强度：
   暂定 / 确认 / 不确定 / 顺延
4. 不能把暂定时间抽成 confirmed deadline。
```

这个类型非常重要，因为原始需求里明确提到“上周五确认了截止日期是 5 号”。

---

## H. scope_event：范围 / 适用对象 / 阶段

**抽什么：**
这件事适用于什么范围、哪个阶段、哪些对象。

**典型原文：**

```text
本期只做模板化配置，不做自定义节点。
这个规则只适用于 P0 客户问题。
先在华东区试点。
MVP 阶段不支持多审批人。
```

**event：**

```json
{
  "event_type": "scope_event",
  "claim": "本期只支持模板化配置，不支持自定义节点",
  "scope_target": "本期审批流配置能力",
  "included": ["模板化配置"],
  "excluded": ["自定义节点"],
  "evidence_quote": "本期只做模板化配置，不做自定义节点"
}
```

**验证规则：**

```text
1. quote 必须表达范围、阶段、适用对象或排除项。
2. included / excluded 必须能在 quote 中找到。
3. 不要把决策原因混进 scope。
```

---

# 4. event 类型字段要强约束

8 类 Event：

```text
1. conclusion_event：结论 / 口径 / 决定
2. rationale_event：理由 / 依据
3. objection_event：异议 / 担忧 / 反对意见
4. constraint_event：约束 / 边界 / 禁止项
5. commitment_event：承诺 / 行动项
6. status_event：状态事实
7. time_event：时间点 / 截止日期 / 里程碑
8. scope_event：范围 / 阶段 / 适用对象
```

这 8 类的好处是：

```text
它们都能被原文直接验证。
```

---

# 5. 通用 event schema

所有 event 都必须有这些字段：

```json
{
  "event_id": "evt_xxx",
  "task_ref": "FEISHU-231",
  "event_type": "conclusion_event",
  "claim": "本期先采用方案 B",
  "core_entry_id": "msg_123",
  "evidence_quote": "那就先按方案 B 来",
  "context_quotes": [
    {
      "entry_id": "msg_120",
      "quote": "方案 A 成本太高",
      "role": "disambiguation"
    }
  ],
  "participants": ["张三", "李四"],
  "event_time": "2026-04-29T10:20:00+08:00",
  "source": {
    "source_type": "chat_thread",
    "source_id": "thread_xxx",
    "url": "https://..."
  },
  "confidence": 0.86,
  "verification": {
    "core_quote_found": true,
    "claim_supported_by_quote": true,
    "context_only_generation": false,
    "single_atomic_claim": true,
    "required_fields_complete": true,
    "no_unsupported_inference": true,
    "verdict": "verified"
  }
}
```

注意这里有两个字段很重要：

```text
evidence_quote：必须来自 Core
context_quotes：只能用于消歧，不能单独支撑新 event
```

之前 V1 里 Core / Context 边界的延续：`evidence_quote` 必须命中 Core，supporting quotes 只能来自 Context，current_state_context 不能当证据。

---

# 6. verification 分层

做四层 verification。

---

## 第一层：位置校验 Location Verification

验证：

```text
这条 event 的 evidence_quote 是否真的来自 Core？
```

规则：

```text
1. evidence_quote 必须是 Core entry 的子串，或经过极轻微归一化后匹配。
2. 必须记录 core_entry_id。
3. 如果 quote 在多个 Core entry 中都出现，必须可唯一定位；否则低置信或拒绝。
4. quote 不能来自 Context。
```

输出：

```json
{
  "core_quote_found": true,
  "resolved_core_entry_id": "msg_123",
  "quote_match_type": "exact"
}
```

这一层可以程序化做，不要交给模型。

---

## 第二层：字段完整性校验 Schema Verification

不同 event 类型有不同必填字段。

例如：

```text
conclusion_event:
- claim
- conclusion
- evidence_quote
- target

rationale_event:
- claim
- reason
- evidence_quote

objection_event:
- claim
- objection
- objector
- target
- evidence_quote

commitment_event:
- claim
- owner
- action
- evidence_quote

time_event:
- claim
- time_target
- time_value
- certainty
- evidence_quote
```

如果必填字段缺失，就：

```text
reject / candidate / needs_review
```

不要让模型硬补字段。

---

## 第三层：语义蕴含校验 Claim Support Verification

验证：

```text
claim 是否真的被 evidence_quote + 必要 context_quotes 支撑？
```

这个可以让另一个 verifier LLM 做，但必须非常窄。

它不是问：

> 这个总结对不对？

而是问：

> 给定 quote，claim 里的每个关键信息是否都有证据？

可以要求 verifier 输出：

```json
{
  "verdict": "supported | partially_supported | unsupported",
  "unsupported_parts": ["长期采用", "团队一致决定"],
  "reason": "quote 只说先按方案 B 来，没有长期采用或一致决定"
}
```

例子：

```text
quote: "那就先按方案 B 来"
claim: "团队一致决定长期采用方案 B"
```

应该判：

```text
partially_supported
unsupported_parts: ["团队一致", "长期"]
```

---

## 第四层：原子性校验 Atomicity Verification

验证：

```text
这条 event 是否只表达一个事实？
```

例如这个 event 不合格：

```json
{
  "claim": "因为方案 A 成本高，所以本期采用方案 B，并由李四周五前补文档"
}
```

它至少包含三个事实：

```text
1. 方案 A 成本高
2. 本期采用方案 B
3. 李四周五前补文档
```

应该拆成三个 event。

atomic verifier 可以判断：

```json
{
  "single_atomic_claim": false,
  "suggested_split": ["方案 A 成本过高", "本期采用方案 B", "李四周五前补齐接口文档"]
}
```

这一层特别重要，因为要解决的正是“直接总结不可验证”。

---

# 7. 每类 event 的可验证证据形态

给 extractor 一张表。
它只要不符合证据形态，就不能抽。

| event 类型       | 必须看到的证据形态                       | 不应该抽的情况           |
| ---------------- | ---------------------------------------- | ------------------------ |
| conclusion_event | 明确结论、决定、采用、不做、确认         | 只是建议、猜测、个人想法 |
| rationale_event  | 因为、原因、考虑到、成本、数据、客户反馈 | 模型自己推断原因         |
| objection_event  | 担心、不同意、风险、反对、不建议         | 普通提问                 |
| constraint_event | 不能、不要、必须、只允许、边界、规则     | 只是描述现状             |
| commitment_event | owner + action，最好有 deadline          | “后面看看”               |
| status_event     | 已完成、未解决、阻塞、待确认、没锁定     | 情绪表达                 |
| time_event       | 明确时间 + 时间对象                      | 孤立时间，没有对象       |
| scope_event      | 本期/阶段/范围/只做/不做/适用于          | 范围不明确               |

这个表就是 verification 的基础。

# 8. 抽取 prompt 应该怎么要求

让 extractor 遵守这几条硬规则：

```text
只能从 CORE 中抽取 event。
CONTEXT 只能用于解释指代，不得单独生成 event。
CURRENT_STATE_CONTEXT 不能作为证据。

每条 event 必须满足：
1. evidence_quote 是 CORE 中的原文短句
2. claim 只表达一个事实
3. claim 的所有关键信息都能由 evidence_quote 或 context_quotes 支撑
4. 不要补全原文没有说的 owner、deadline、原因、结论强度
5. 如果 quote 只能支持弱表达，就保留弱表达，例如“暂定”“先按”“还没锁定”
6. 如果无法定位 target，就 abstain 或输出 candidate
```

尤其要强调：

```text
不要抽“总结型 event”，只抽“证据型 event”。
```

---

# 9. verification prompt 应该怎么问

verifier 不要重新抽取，而是只做判定。

输入：

```json
{
  "core_entries": [...],
  "context_entries": [...],
  "candidate_event": {...}
}
```

输出：

```json
{
  "verdict": "verified | candidate | rejected",
  "checks": {
    "evidence_quote_in_core": true,
    "context_quotes_in_context": true,
    "claim_supported": true,
    "single_atomic_claim": true,
    "required_fields_complete": true,
    "no_context_only_generation": true,
    "no_state_as_evidence": true
  },
  "unsupported_parts": [],
  "suggested_fix": null
}
```

其中 `suggested_fix` 只允许做两件事：

```text
1. 删除 unsupported 的部分
2. 建议拆成多条 event
```

不能让 verifier 自己发明新 event。

---

# 10. 应该允许三种结果，不要只有通过/失败

```text
verified：证据直接支撑，可以入 event ledger
candidate：大概率有价值，但 target / owner / relation 不完整，需要后续确认
rejected：证据不足、过度推断、context-only、非原子
```

例如：

```text
“那就按刚才的来。”
```

如果 Context 能明确解释“刚才的”是什么，可以是 verified。

如果 Context 不够，只能是：

```json
{
  "verdict": "candidate",
  "reason": "Core 有确认动作，但 target 不能唯一解析"
}
```

不要强行抽成：

```text
团队确认采用方案 B
```

# 11. 一个完整例子

输入：

```text
CONTEXT:
A：FEISHU-231 目标发布时间暂定 5 月 5 日。
B：迁移窗口还没锁定。

CORE:
C：那就先按这个来，但不要对外说死。
D：我担心销售那边会直接拿 5 号承诺客户。
E：那外部口径就说“预计 5 月上旬”，不要写死日期。
```

应该抽：

```json
[
  {
    "event_type": "conclusion_event",
    "claim": "FEISHU-231 内部暂按 5 月 5 日作为目标发布时间推进",
    "target": "FEISHU-231 目标发布时间",
    "conclusion": "暂按 5 月 5 日推进",
    "evidence_quote": "那就先按这个来",
    "context_quotes": [
      {
        "quote": "FEISHU-231 目标发布时间暂定 5 月 5 日",
        "role": "resolve_reference"
      }
    ]
  },
  {
    "event_type": "constraint_event",
    "claim": "FEISHU-231 的 5 月 5 日发布时间不能作为确定对外承诺",
    "target": "FEISHU-231 5 月 5 日发布时间",
    "constraint": "不能对外说死",
    "evidence_quote": "不要对外说死",
    "context_quotes": [
      {
        "quote": "FEISHU-231 目标发布时间暂定 5 月 5 日",
        "role": "resolve_reference"
      }
    ]
  },
  {
    "event_type": "objection_event",
    "claim": "有人担心销售会将 5 月 5 日直接承诺给客户",
    "target": "5 月 5 日发布时间",
    "objection": "销售可能将该日期承诺给客户",
    "evidence_quote": "我担心销售那边会直接拿 5 号承诺客户"

    "event_type": "conclusion_event",

    "event_type": "constraint_event",
    "claim": "FEISHU-231 对外口径不要写死具体日期",
    "target": "FEISHU-231 对外发布时间口径",
    "constraint": "不要写死日期",
    "evidence_quote": "不要写死日期"
  }
]
```

不要抽：

```text
团队决定 FEISHU-231 于 5 月 5 日上线，但对外宣传为 5 月上旬。
```

因为这句话混合了内部目标、外部口径、约束、风险，而且“上线”强度可能超过“目标发布时间”。

# 12. 你现在这套 verification 的关键设计原则

最后我建议你把原则写成这几条：

## 原则 1：Evidence-first

先找 quote，再生成 claim。
不能先总结，再找 quote。

```text
quote → claim
不是
summary → evidence
```

## 原则 2：Core-triggered

只有 Core 能触发 event。
Context 只消歧。

## 原则 3：Claim minimality

一条 event 只表达一个事实。
有“因为 / 所以 / 并且 / 同时 / 但是”，大概率要拆。

## 原则 4：Modality preservation

保留原文强度。

```text
暂定 ≠ 确认
先按 ≠ 最终决定
不要说死 ≠ 禁止沟通
担心 ≠ 已发生
```

## 原则 5：No slot hallucination

字段缺失就填 null，不补。

```text
没有 owner → null
没有 deadline → null
没有原因 → null
没有 target → candidate / reject
```

## 原则 6：Typed verification

不同 event 类型有不同验证规则。
不要用一套泛泛的“是否可信”验证所有东西。

# 13. 最推荐你落下来的版本

你可以这样定稿：

```text
我们将 event 定义为从重要协作片段的 Core 中抽取出的最小可校验协作事实。event 不直接表示 wiki 更新操作，而是作为 task wiki 的事实输入。每条 event 必须包含一个由 Core 原文直接支撑的 evidence_quote，并且 claim 不得超出 evidence_quote 与必要 Context quote 所能支持的范围。

第一版 event 类型包括：
1. conclusion_event：结论、决定、当前口径
2. rationale_event：理由、依据
3. objection_event：异议、担忧、反对意见
4. constraint_event：约束、边界、禁止项
5. commitment_event：行动承诺
6. status_event：状态事实
7. time_event：时间点、截止日期、里程碑
8. scope_event：范围、阶段、适用对象

verification 分为四层：
1. Location verification：evidence_quote 必须命中 Core entry
2. Schema verification：不同 event 类型满足各自必填字段
3. Claim support verification：claim 的每个关键信息都必须被 quote 支撑
4. Atomicity verification：一条 event 只能表达一个事实，复杂表达必须拆分
```

这样你抽出来的 event 就不再是“模型总结”，而是一个可以进入 ledger 的、后续 wiki 能消费的事实层。
