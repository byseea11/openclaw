# Event

Layer 2 的目标不是让模型自由总结聊天记录，而是把已经绑定到任务的新增 source 内容转成可验证的协作事实。

当前真实实现采用 immediate extraction：

```text
maybeIngestTaskSourceSession(...)
-> append source session
-> pending_ingests / evidence_spans
-> extractCandidateEventsWithLLM(...)
-> validateCandidateEvent(...)
-> candidate_events
-> verification_jobs
-> runVerificationJobs(...)
-> session_events
```

这里的硬规则是：

- event 必须来自当前 ingest 的原文证据。
- context 只负责消歧，不能单独生成 event。
- candidate_event 和 session_event 必须分层。
- regex / heuristic 只能作为 cheap hint、splitter 或 fallback；主线 event 抽取与 verifier 由 LLM 完成。
- 当前实现没有独立 drain API；`session-ingest.js` 未导出额外的 drain/freshness 入口。

## 1. 可验证 Event 的核心定义

```text
Event = 从当前 ingest evidence envelope 中抽取出的、由一个或多个 quote 直接支撑的最小协作事实断言。
```

它有三个关键词：

## 1.1 从当前证据中抽取

event 必须由 `trigger_entries` / `core_entries` 触发。

`context_entries` 可以解释“这个”“刚才”“那个日期”，但不能自己生成 event。

## 1.2 quote 直接支撑

event 不能是“模型觉得应该是这样”。

它必须能回答：

```text
这条 claim 的哪一部分来自哪句原文？
```

## 1.3 最小协作事实断言

一条 event 只能表达一个事实。

不能把“理由 + 结论 + 行动项 + 风险”揉在一起。

当前实现明确区分两层输出：

```text
candidate_event:
写入 candidate_events.jsonl，保存候选层，包括 pending_verification / needs_review / rejected。

session_event:
写入 session_events.jsonl，只保存 verified 的正式事件，作为 Layer 3 Wiki 的输入。
```

## 2. Ingest 状态

当前 ingest ledger 使用这些状态：

```text
pending_extraction
pending_verification
verified
needs_review
rejected
processed_no_event
```

`processed_no_event` 表示当前 ingest 已进入 source session，并且本次 immediate extraction 没有产生可进入 verification 的 candidate event。

## 3. Evidence Envelope

`evidence_spans.jsonl` 是 per-ingest evidence envelope。

它不是“上下文文件”，而是本次抽取使用的证据容器：

- `trigger_entries`：本次新增 message / reply / comment。
- `core_entries`：最可能承载新事实的主证据集合。
- `context_entries`：解释代词、时间、修正、否定、前后文关系的邻近消息。
- `support_entries`：thread root、comment root 或上位背景等辅助证据。

## 4. Validate / Verify

Layer 2 是三段式链路：

```text
extractCandidateEventsWithLLM(...)
-> validateCandidateEvent(...)
-> verifyCandidateEvent(...)
```

`extractCandidateEventsWithLLM(...)` 负责提出候选，不负责最终确认。

`validateCandidateEvent(...)` 是 programmatic gate，负责：

- schema / typed fields 检查
- evidence quote 对齐检查
- atomicity 检查
- 基础可验证性检查

`verifyCandidateEvent(...)` 是语义确认层，负责判断 candidate 是否真的被证据支撑，并决定是否进入 verified ledger。

## 5. Event 类型

## A. conclusion_event：结论 / 口径 / 决定

抽明确表达“怎么定”“按什么来”“当前结论是什么”的消息。

典型原文：

```text
那就先按方案 B 来。
本期不做自定义节点。
这个先按 5 月 5 日推进。
```

验证规则：

- quote 中必须出现明确结论词。
- claim 不能添加 quote 中没有的强度。
- 如果只是个人建议，不抽 conclusion_event。

## B. rationale_event：理由 / 依据

抽某个选择、判断、担忧、约束背后的原因。

典型原文：

```text
方案 A 成本太高。
因为迁移窗口还没锁定。
客户现在主要卡在审批配置复杂。
```

验证规则：

- quote 中必须直接表达原因。
- reason_for 不能超出上下文能支撑的范围。
- 不能把背景描述强行抽成理由。

## C. action_item_event：行动项 / 待办

抽明确有人要做什么、什么时候做、交付什么。

验证规则：

- 必须有 owner 或可由上下文消解出的执行主体。
- 必须有 action。
- deadline 缺失时不能虚构。

## D. state_update_event：状态变化

抽任务当前 owner、status、blocker、deadline、dependency 等状态变化。

验证规则：

- 必须能从 quote 直接支撑状态变化。
- 如果存在修正口径，旧值只能作为 historical / superseded，不得进入 current state。

## 6. Layer 3 输入边界

Layer 3 projector 只消费 verified `session_events`。

没有通过 validation / verification 的 candidate 可以保留在 audit 文件里，但不能进入 wiki current state。
