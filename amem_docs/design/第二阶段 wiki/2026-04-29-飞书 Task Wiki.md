# 飞书 Task Wiki：基于 Session Wiki 的项目记忆系统

## 0. 核心理念

本系统面向飞书企业协作场景，目标不是对群聊、文档或会议纪要做一次性总结，而是围绕具体 `task_id` 增量构建并维护一个可追溯、可验证、可持续演进的项目记忆 Wiki。

传统 RAG 的工作方式是：在查询时临时检索原始资料，再让 LLM 重新拼接答案。这样每次回答都像从零开始，知识不会沉淀。

本系统采用 LLM Wiki 思路：当新的协作资料进入系统时，LLM 不只是为未来检索建立索引，而是将其编译成一个可持续维护的 Wiki 页面。对于飞书项目协作场景，最稳定的一手 Wiki 页面不是主题页，而是 **session wiki page**。

对应关系是：

```text
Paper Wiki 场景：
一篇 paper → 一个 paper page → 多个 paper page 综合成 topic page / survey page

飞书 Task Wiki 场景：
一个 session file → 一个 session_wiki.md → 多个 session_wiki.md 综合成 task_wiki.md / topic view
```

因此，本系统采用以下核心链路：

```text
飞书协作内容
  → task_id 绑定
  → session file 摄入
  → Evidence Span 构造
  → candidate_event 抽取
  → verification
  → session_event 存储
  → session_wiki.md 生成 / 更新
  → index.md 更新
  → task_wiki.md 汇总更新
  → 可选 topic views 更新
  → 检索 / 巡检 / 遗忘
```

其中最重要的原则是：

```text
Session File 是事实来源，也是摄入单位。
candidate_event 是抽取阶段产生的候选事件。
session_event 是通过 verification 后落盘的正式事件。
session_wiki.md 是一手记忆页，也是基础 Wiki Page。
index.md 指向 session_wiki.md，并按 topic 聚合 session。
task_wiki.md 是由多个 session_wiki.md 汇总出的任务当前状态总览。
views/*.md 是可选的二级主题综合页，不是主存储。
```

系统不会直接让 LLM 总结一段群聊并写入 Task Wiki，而是先把 session file 中的重要协作文本拆成多个由原文证据支撑的最小事实事件。通过验证后的 session_event 会作为事实输入，生成或更新该 session 对应的 `session_wiki.md`。`index.md` 再把这些 session wiki 按主题、时间、状态组织起来，`task_wiki.md` 基于多个 session wiki 汇总当前任务状态。

---

# 1. 核心对象定义

## 1.1 Task

Task 是项目记忆的核心组织单位。

它可以是：

```text
- 一个项目任务
- 一个需求
- 一个问题单
- 一个缺陷修复
- 一个审批事项
- 一个里程碑目标
```

系统不再以个人、会话参与者或普通 thread 作为主要记忆对象，而是以 `task_id` 作为所有后续记忆处理的主键。

---

## 1.2 Session File

Session File 是围绕某个 task 的一次可摄入协作上下文文件。

它同时承担两种角色：

```text
1. source：事实来源
2. ingest unit：本次摄入和抽取的处理单位
```

因此本文不再单独区分 Raw Source 和 Session File。

Session File 可以来自飞书中的多种协作载体：

```text
- 某个 thread 中围绕 task 的关键讨论片段
- 某篇文档的一个版本或关键段落
- 某次会议纪要
- 某个任务评论区的一段变更讨论
- 某个群聊中围绕 task 的连续片段
- 某条审批流记录
- 某条多维表格记录
```

Session File 不是完整群聊，也不是完整文档，而是经过 task 绑定和重要性过滤后形成的处理单位。

因此：

```text
session_id ≠ thread_id
session_id = task_id + source_id + ingest_window / version
```

示例：

```text
task_id: FEISHU-231
session_id: FEISHU-231__thread_abc__2026-04-27
source_type: chat_thread
```

---

## 1.3 Evidence Span

Evidence Span 是从 session file 中筛出的候选证据包。

它不是完整 session，而是为了 event 抽取组织出来的局部上下文。

一个 Evidence Span 包含：

```text
1. Core
2. Context
3. Current State Context
```

其中：

```text
Core：唯一可以触发新 event 的原文片段。
Context：只用于解释指代和补全语义，不能单独生成 event。
Current State Context：当前 Wiki 状态摘要，只用于理解已有口径，不能作为证据。
```

---

## 1.4 candidate_event

candidate_event 是从 Evidence Span 的 Core 中抽取出来的候选事件。

它还没有通过 verification，因此不能直接进入 Wiki，也不能作为正式事实使用。

candidate_event 的作用是：

```text
把一段自然语言拆成一个或多个最小事实断言，等待验证。
```

candidate_event 必须尽量满足 event schema，但可以因为字段缺失、指代未完全解析、claim 支撑不足等原因被标记为：

```text
candidate / needs_review / rejected
```

---

## 1.5 session_event

session_event 是通过 verification 后正式落盘的事件。

它是系统中的正式事实单位。

定义如下：

```text
session_event = 从某个 session file 的 Core 中抽取出的、由原文 quote 直接支撑的、通过 verification 的最小协作事实。
```

session_event 不表示 Wiki 更新操作。

session_event 不直接表示：

```text
- 新增 Wiki item
- 更新 Wiki 字段
- 删除旧结论
- 修改当前状态
```

这些都是 session_wiki.md、task_wiki.md 或 topic view 消费 session_event 之后做的事情。

session_event 只回答一个问题：

```text
这段 Core 原文中明确表达了什么可验证事实？
```

---

## 1.6 session_wiki.md

`session_wiki.md` 是系统中的基础 Wiki Page。

每个 session file 对应一个 `session_wiki.md`。

它类似 Paper Wiki 里的 paper page：一个原始来源文件被摄入后，生成一个对应的、可长期维护的记忆页面。

`session_wiki.md` 记录：

```text
- 这个 session 讨论了什么
- 这个 session 产生了哪些 session_event
- 这个 session 对 task 贡献了哪些结论、理由、异议、约束、行动项和时间点
- 这个 session 中哪些问题仍待后续处理
```

它是一手记忆页，证据边界清晰，更新路径稳定。

---

## 1.7 KI Slot

KI Slot 是 `session_wiki.md` 内部的结构化知识槽位。

它不是独立文件，也不是 event 的同义词。

第一版可以使用 8 个 slot：

```text
1. conclusion slot：结论 / 当前口径
2. rationale slot：理由 / 依据
3. objection slot：异议 / 担忧 / 反对意见
4. constraint slot：约束 / 边界 / 禁止项
5. commitment slot：行动承诺
6. status slot：状态事实
7. time slot：时间点 / 截止日期 / 里程碑
8. scope slot：范围 / 阶段 / 适用对象
```

这些 slot 与 session_event 类型相对应，但不是 event 本身。

session_event 是事实来源。

slot 是页面组织方式。

---

## 1.8 index.md

`index.md` 是 task 级别的目录和导航层。

它不维护跨 session 的 event index，也不复制所有 event 摘要。

但是，在引入 Memory Block 之后，`index.md` 的索引粒度不应该只停留在 session_wiki.md 级别。

更准确地说：

```text
index.md 主要索引 Memory Block，同时保留其所属 session_wiki.md 作为来源边界。
```

也就是说，index 不是只回答：

```text
这个 task 有哪些 session？
```

而是要回答：

```text
这个 task 下面有哪些可复用的记忆单元？
这些 Memory Block 分别属于哪个 session？
它们对应什么 topic、阶段、状态、行动项或风险？
```

index.md 主要维护：

```text
- 当前 task 下有哪些 session_wiki.md
- 每个 session_wiki.md 中有哪些 Memory Block
- 每个 Memory Block 的 topic / stage / status
- 每个 Memory Block 所属 session
- 每个 Memory Block 最近更新时间
- 每个 Memory Block 覆盖哪些 KI Slot
- 哪些 Memory Block 共同构成某个 topic 的演进链路
- 哪些 Memory Block 影响 task_wiki.md 的当前状态
```

因此后续检索路径应该是：

```text
index.md → Memory Block → session_wiki.md → Event Reference → session events.jsonl → Evidence Quote
```

其中，session_wiki.md 仍然是来源页；Memory Block 是 index 中主要被组织和聚合的记忆粒度。

---

## 1.9 task_wiki.md

`task_wiki.md` 是围绕 `task_id` 生成和维护的任务当前状态总览。

它不是原文总结，也不是 event 列表。

它是：

```text
基于多个 session_wiki.md 汇总生成的任务当前状态视图。
```

Task Wiki 不直接维护全部细节，而是引用相关 session_wiki.md。

---

## 1.10 Topic View，可选

Topic View 是可选的二级综合页。

当某个主题跨越多个 session，且在 task 中变得足够重要时，可以生成一个 topic view。

例如：

```text
views/release_plan.md
views/external_communication.md
views/risk_and_blockers.md
```

Topic View 不是基础存储层。

基础存储层仍然是：

```text
sessions/*/session_wiki.md
```

Topic View 是从多个 session wiki page 进一步综合出来的派生视图。

# 2. 目录结构建议

一个 task 可以对应一个本地 Wiki 目录。

目录结构应参考 Openclaw / LLM Wiki 的文件式维护方式：

```text
task_memory/
  FEISHU-231/
    task.yaml
    index.md
    log.md
    task_wiki.md

    sessions/
      2026-04-27_thread_abc/
        session.md
        metadata.yaml
        evidence_spans.jsonl
        events.jsonl
        session_wiki.md

      2026-04-28_doc_xyz/
        session.md
        metadata.yaml
        evidence_spans.jsonl
        events.jsonl
        session_wiki.md

    views/                    # 可选：二级综合视图，不是主存储
      release_plan.md
      external_communication.md
      risk_and_blockers.md

    lint/
      open_conflicts.md
      stale_claims.md
      orphan_events.md
      unresolved_objections.md
      overdue_commitments.md
```

这里不再设计 `event_index.jsonl`，也不把主题页作为第一层主存储。

原因是：

```text
1. session_event 物理上归属于 sessions/{session_id}/events.jsonl
2. event_id 全局唯一
3. 每个 session file 都有自己的 session_wiki.md
4. index.md 指向 session_wiki.md，并按 topic 聚合 session
5. task_wiki.md 基于多个 session_wiki.md 汇总
6. views/*.md 只是可选的二级主题综合视图
```

各文件职责：

```text
task.yaml:
任务元信息。

index.md:
任务级目录，指向各个 session_wiki.md，并按 topic / time / status 聚合 session。

log.md:
只增日志，记录摄入、更新、巡检、遗忘操作。

task_wiki.md:
面向用户阅读的任务当前状态总览，由多个 session_wiki.md 汇总生成。

sessions/*/session.md:
本次摄入的 session file，也就是事实来源文件。

sessions/*/metadata.yaml:
该 session 的来源、时间范围、参与人、source hash、绑定 task 等元数据。

sessions/*/evidence_spans.jsonl:
从 session.md 中筛出的 Evidence Span。

sessions/*/events.jsonl:
该 session 中抽取并验证后的 session_event。event_id 全局唯一。

sessions/*/session_wiki.md:
该 session 对 task 的一手记忆页，是基础 Wiki Page。

views/*.md:
可选的跨 session 主题综合页。当某个主题涉及多个 session 且需要长期跟踪时才创建。

lint/*.md:
巡检结果和待处理问题。
```

# 3. 任务绑定和信息归类（Preprocessing）

## 3.1 目标

确定每条信息是否属于某个任务，并确保后续处理都围绕正确的 `task_id` 展开。

如果信息无法绑定到任何 `task_id`，则不进入记忆处理链路。

---

## 3.2 任务绑定规则

每个会话线程、文档或协作对象需要尽可能绑定到一个明确的 `task_id`。

绑定方式包括：

```text
1. 显式绑定
   - 文档创建时选择所属 task
   - thread 开启时选择所属 task
   - 任务卡片下的评论天然继承 task_id

2. 继承绑定
   - thread 继承父消息的 task_id
   - 文档评论继承文档的 task_id
   - 会议纪要继承会议关联任务的 task_id

3. 上下文绑定
   - 消息中出现任务编号、需求编号、项目名
   - 消息所在群或频道与某个 task 有明确关联
   - 文档标题、父目录或模板中包含 task 线索
```

处理规则：

```text
未绑定 task_id 的信息 → 不处理
已绑定 task_id 的信息 → 形成 session file
```

---

# 4. Session File 摄入

## 4.1 目标

将已绑定 `task_id` 的协作内容整理成一次可摄入的 session file。

Session File 是事实来源，也是后续 event 抽取的基本处理单位。

---

## 4.2 Session File 不是完整原始流

系统不会把完整群聊、完整 thread 或完整文档无差别写入记忆系统。

Session File 应该是：

```text
围绕某个 task 的一次重要协作上下文文件。
```

它可以通过以下方式形成：

```text
- 按 thread 形成 session file
- 按文档版本形成 session file
- 按会议纪要形成 session file
- 按任务评论窗口形成 session file
- 按一段连续的 task 相关群聊形成 session file
```

---

## 4.3 Session File 元数据

每个 session file 至少包含：

```text
- session_id
- task_id
- source_type
- source_id
- source_title
- time_range
- participants
- ingest_time
- source_url
- source_hash / version
```

---

# 5. Evidence Span 构造

## 5.1 目标

从 session file 中筛选出可能包含关键协作事实的片段，并为 event 抽取构造必要上下文。

Evidence Span 不是完整 session。

Evidence Span 是经过重要性过滤后的候选证据包。

---

## 5.2 Evidence Span 的结构

一个 Evidence Span 由三部分组成：

```text
1. Core
2. Context
3. Current State Context
```

---

## 5.3 Core

Core 是真正待处理的关键文本片段。

只有 Core 可以触发新的 event。

Core 中必须出现新的协作事实动作，例如：

```text
- 明确结论
- 给出理由
- 提出异议
- 增加约束
- 分配行动项
- 表达状态变化
- 确认时间点
- 明确范围边界
```

如果 Core 只是：

```text
- 收到
- 好的
- 我看看
- +1
- 辛苦了
```

则不生成 event。

---

## 5.4 Context

Context 是为了帮助理解 Core 的最小必要上下文。

Context 可以用于解释：

```text
- “这个”指什么
- “刚才那个方案”是哪一个
- “那个日期”是哪一天
- “按上面说的”指哪条结论
- “这个风险”对应哪个风险
```

但是 Context 不能单独生成 event。

也就是说：

```text
Core 决定是否抽取 event。
Context 只负责消歧。
```

---

## 5.5 Current State Context

Current State Context 是当前 Task Wiki 或已有 session_wiki.md 中提取出来的状态摘要。

它可以包含：

```text
- 当前 active conclusion
- 当前时间点
- 当前开放行动项
- 当前未关闭异议
- 当前风险或约束
- 当前项目阶段
```

它的作用是帮助模型理解当前已有口径，避免重复抽取或错误解释。

但是它有一个硬约束：

```text
Current State Context 不能作为新 event 的证据。
```

它只能用于理解和消歧，不能用于支撑新的 claim。

---

# 6. candidate_event 抽取

## 6.1 candidate_event 的定义

candidate_event 是从 Evidence Span 的 Core 中抽取出的候选最小协作事实断言。

它尚未通过 verification，因此不能作为正式记忆使用。

定义如下：

```text
candidate_event = 从 Core 原文中抽取出的、等待验证的最小协作事实断言。
```

---

## 6.2 抽取原则

每条 candidate_event 必须尽量满足：

```text
1. 必须由 Core 触发
2. 必须有 evidence_quote
3. evidence_quote 必须来自 Core
4. claim 只能表达一个事实
5. claim 不能超出 evidence_quote 与必要 Context quote 的支持范围
6. Context 只能用于消歧，不能单独生成 event
7. Current State Context 不能作为证据
8. 原文没有的信息不能补
```

如果无法满足这些原则，则该 candidate_event 应被标记为 `candidate`、`needs_review` 或 `rejected`。

---

## 6.3 Event 类型

第一版 event 使用 8 类。

这 8 类不是 Wiki 模块，而是可验证事实类型。

```text
1. conclusion_event：结论 / 口径 / 决定
2. rationale_event：理由 / 依据
3. objection_event：异议 / 担忧 / 反对意见
4. constraint_event：约束 / 边界 / 禁止项
5. commitment_event：承诺 / 行动项
6. status_event：状态事实
7. time_event：时间点 / 截止日期 / 里程碑
8. scope_event：范围 / 阶段 / 适用对象
```

---

# 7. Verification：从 candidate_event 到 session_event

## 7.1 目标

Verification 的目标不是给 event 打一个主观置信度，而是把 candidate_event 判断为：

```text
1. 可以落盘为 session_event
2. 需要人工或后续上下文确认
3. 应该拒绝
```

系统不是：

```text
先让模型自由总结，再问它可不可信
```

而是：

```text
只允许那些能被原文 quote 直接支撑的 candidate_event 变成 session_event。
```

---

## 7.2 Location Verification

验证 candidate_event 的 `evidence_quote` 是否真的来自 Core。

规则：

```text
1. evidence_quote 必须是 Core entry 的子串，或经过轻微归一化后可匹配
2. 必须记录 core_entry_id
3. 如果 quote 出现在多个 Core entry 中，必须能唯一定位
4. quote 不能来自 Context
5. quote 不能来自 Current State Context
```

这一层应尽量程序化完成。

---

## 7.3 Schema Verification

验证不同 event 类型是否满足对应的必填字段。

例如：

```text
conclusion_event:
- claim
- target
- conclusion
- evidence_quote

rationale_event:
- claim
- reason
- evidence_quote

objection_event:
- claim
- objector
- target
- objection
- evidence_quote

constraint_event:
- claim
- target
- constraint
- evidence_quote

commitment_event:
- claim
- owner
- action
- evidence_quote

status_event:
- claim
- target
- status
- evidence_quote

time_event:
- claim
- time_target
- time_value
- certainty
- evidence_quote

scope_event:
- claim
- scope_target
- evidence_quote
```

如果必填字段缺失，系统不应该让模型硬补，而应该标记为：

```text
candidate / needs_review / rejected
```

---

## 7.4 Claim Support Verification

验证 claim 是否真的被 `evidence_quote` 和必要的 `context_quotes` 支撑。

这一层可以由 verifier LLM 完成，但 verifier 只能做判断，不重新发明 event。

它需要判断：

```text
- claim 的每个关键信息是否都有证据
- claim 是否加入了原文没有的强度
- claim 是否把暂定说成确认
- claim 是否把担忧说成事实已经发生
- claim 是否把建议说成决策
```

---

## 7.5 Atomicity Verification

验证一条 candidate_event 是否只表达一个事实。

不合格示例：

```text
因为方案 A 成本高，所以本期采用方案 B，并由李四周五前补文档。
```

这句话至少应该拆成三条 event：

```text
1. rationale_event：方案 A 成本高
2. conclusion_event：本期采用方案 B
3. commitment_event：李四周五前补文档
```

Atomicity Verification 的目标是避免 event 退化成“总结”。

---

## 7.6 Verification 结果

verification 不应该只有通过和失败，而应该允许三种结果：

```text
verified:
证据直接支撑，可以写入 sessions/{session_id}/events.jsonl，成为 session_event。

candidate:
信息有价值，但 target / owner / relation 等字段不完整，需要后续确认。

rejected:
证据不足、过度推断、context-only、非原子，不能进入正式记忆。
```

---

# 8. session_event 存储

## 8.1 存储目标

记忆存储的目标不是把所有 event 混进一个跨 task 或跨 session 的大表，而是让每个 session_event 保留清晰的来源边界，并让 session_wiki.md 能够直接引用这些 session_event。

因此采用文件式存储：

```text
sessions/{session_id}/events.jsonl
```

不需要额外维护 `task-level event_index.jsonl`。

原因是：

```text
1. event_id 全局唯一，可以直接引用
2. session_event 的完整内容保存在所属 session/events.jsonl 中
3. session_wiki.md 直接记录 related_event_refs
4. index.md 只需要索引 session_wiki.md，而不是索引全部 event
5. task_wiki.md 由 session_wiki.md 汇总，不直接依赖 event_index
```

---

## 8.2 session_event schema

每条 session_event 至少包含：

```json
{
  "event_id": "evt_01HXYZ...",
  "task_id": "FEISHU-231",
  "session_id": "2026-04-27_thread_abc",
  "event_type": "constraint_event",
  "claim": "5 月 5 日不能作为确定的对外承诺日期",
  "core_entry_id": "msg_123",
  "evidence_quote": "不要对外说死",
  "context_quotes": [
    {
      "entry_id": "msg_120",
      "quote": "目标发布时间暂定 5 月 5 日",
      "role": "resolve_reference"
    }
  ],
  "event_time": "2026-04-27T10:30:00+08:00",
  "verification": {
    "verdict": "verified"
  }
}
```

`event_id` 必须全局唯一。

session_wiki.md 引用 event 时，建议同时保存 `event_id` 与 `event_path`，避免后续查找时必须依赖中心索引。

示例：

```json
{
  "event_id": "evt_01HXYZ...",
  "event_path": "sessions/2026-04-27_thread_abc/events.jsonl",
  "claim": "5 月 5 日不能作为确定的对外承诺日期"
}
```

---

# 9. session_wiki.md、Memory Block 与 KI Slot

## 9.1 session_wiki.md 的定位

`session_wiki.md` 是本系统中最重要的一手 Wiki Page。

它不是按主题创建的页面，而是按 session 创建的页面。

更准确地说：

```text
session_wiki.md = 某个 session file 被摄入后生成的一手记忆页。
```

它记录该 session 对 task 贡献了什么，而不是试图立即生成跨 session 的最终结论。

但是，一个 session 里可能讨论多件事情。

例如同一个群聊片段中可能先讨论发布时间，再讨论方案选择，随后又讨论风险和行动项。这些内容虽然都属于同一个 task，但不应该被压进同一组 slot 中。

因此，`session_wiki.md` 不应该只有一组固定 slot，而应该包含多个 Memory Block。

---

## 9.2 Memory Block 的定位

Memory Block 是 session_wiki.md 内部的最小组织单元。

它表示这个 session 中围绕某个具体问题、主题、决策轴或执行事项形成的一段局部记忆。

也就是说：

```text
session_wiki.md = 多个 Memory Block 的集合
Memory Block = 一组围绕同一问题/主题的 session_event 聚合
```

例如一个 session_wiki.md 里可以有多个 block：

```text
Memory Block A：发布时间口径
Memory Block B：方案 B 是否替代方案 A
Memory Block C：销售承诺风险
Memory Block D：接口文档行动项
```

每个 Memory Block 都可以使用一组 KI Slot 来组织内容。

这样可以避免把一个 session 里发生的多件事情混成一个大总结。

---

## 9.3 KI Slot 的定位

KI Slot 是 Memory Block 内部的结构化栏目。

它用于把同一个问题/主题下的不同类型记忆组织清楚。

第一版可以使用 8 个 slot：

```text
1. conclusion slot：结论 / 当前口径
2. rationale slot：理由 / 依据
3. objection slot：异议 / 担忧 / 反对意见
4. constraint slot：约束 / 边界 / 禁止项
5. commitment slot：行动承诺
6. status slot：状态事实
7. time slot：时间点 / 截止日期 / 里程碑
8. scope slot：范围 / 阶段 / 适用对象
```

这些 slot 与 session_event 类型相对应，但不是 event 本身。

session_event 是事实来源。

Memory Block 是局部记忆单元。

KI Slot 是 block 内部的组织方式。

注意：

```text
不是每个 Memory Block 都必须填满 8 个 slot。
只填本 block 中有证据支撑的 slot。
没有证据的 slot 可以省略或留空。
```

---

## 9.4 Memory Block 的生成规则

session_event 写入 `events.jsonl` 后，需要在生成 session_wiki.md 时按语义进行分组。

分组依据可以包括：

```text
- topic_key：主题，例如 发布时间、对外口径、方案选择
- target：事件作用对象，例如 方案 B、5 月 5 日、接口文档
- decision_axis：决策轴，例如 是否采用方案 B、是否对外承诺日期
- owner/action：行动项对象
- time_target：时间对象，例如 截止日期、发布时间
- source proximity：原文中相邻的一组消息
```

每组相关 session_event 形成一个 Memory Block。

一个 session_event 原则上应归入一个主要 Memory Block，但在必要时可以被多个 block 引用。

---

## 9.5 session_wiki.md 建议结构

```text
# Session Wiki: 2026-04-27_thread_abc

## Metadata
- Task: FEISHU-231
- Source Type: chat_thread
- Time Range: 2026-04-27 10:00-10:40
- Participants: 张三、李四、王五

## Session Summary
这次讨论主要涉及 FEISHU-231 的发布时间口径、销售承诺风险和接口文档行动项。

## Memory Blocks

### Block 1: 发布时间口径

#### Summary
内部暂按 5 月 5 日推进，但对外口径调整为预计 5 月上旬。

#### Conclusion
- 内部暂按 5 月 5 日推进。
- 对外口径为预计 5 月上旬。

#### Rationale
- 迁移窗口尚未锁定。

#### Constraint
- 不要对外说死具体日期。

#### Time
- 内部目标发布时间：5 月 5 日。
- 对外口径：5 月上旬。

#### Evidence References
- evt_001 → sessions/2026-04-27_thread_abc/events.jsonl
- evt_002 → sessions/2026-04-27_thread_abc/events.jsonl

---

### Block 2: 销售承诺风险

#### Summary
有人担心销售将 5 月 5 日直接承诺给客户。

#### Objection / Risk
- 销售可能将 5 月 5 日直接承诺给客户。

#### Constraint
- 对外不能承诺具体日期。

#### Evidence References
- evt_003 → sessions/2026-04-27_thread_abc/events.jsonl

---

### Block 3: 接口文档行动项

#### Summary
需要补齐接口文档，并同步销售统一口径。

#### Commitment
- 李四负责补齐接口文档。
- 需要同步销售统一外部口径。

#### Status
- 待处理。

#### Evidence References
- evt_004 → sessions/2026-04-27_thread_abc/events.jsonl
```

---

## 9.6 为什么不只用一组 8 个 slot

如果整个 session_wiki.md 只有一组 slot，会出现几个问题：

```text
1. 一个 session 中多件事情会被混在一起
2. 不同结论的理由、异议和行动项容易错配
3. 后续 task_wiki.md 很难判断哪个信息属于哪个主题
4. index.md 无法准确按 topic 聚合 session
5. 跨 session 更新时无法对齐同一个问题轴
```

因此，8 个 slot 应该作用在 Memory Block 上，而不是整个 session_wiki.md 上。

---

# 10. index.md 与 task_wiki.md 更新

## 10.1 增量更新流程

当新 session 被摄入后，不需要全量重建所有 Wiki。

推荐增量更新流程：

```text
1. 从 session file 中抽取 candidate_event
2. 对 candidate_event 做 verification
3. verified event 写入 sessions/{session_id}/events.jsonl，成为 session_event
4. 生成或更新 sessions/{session_id}/session_wiki.md
5. 在 session_wiki.md 内生成或更新多个 Memory Block
6. 更新 index.md，把新增或变化的 Memory Block 挂到相关 topic / stage / status 下
7. 判断 task_wiki.md 是否需要刷新相关摘要
8. 如果某个 topic 已有 views/*.md，按需增量更新该 topic view
9. 追加 log.md
10. 可选触发 lint
```

更新粒度应该是：

```text
session_event → Memory Block → session_wiki.md → index.md → task_wiki.md → optional topic view
```

而不是：

```text
session_event → 只更新整个 session_wiki.md 的粗粒度摘要
```

也不是：

```text
session_event → 全量重写 Task Wiki
```

---

## 10.2 index.md 的职责

`index.md` 是 task 的导航页。

它应该同时保留两层索引：

```text
1. Session Index：有哪些 session_wiki.md
2. Memory Block Index：每个 session_wiki.md 里有哪些可复用的 Memory Block
```

其中真正用于检索、聚合和 task_wiki 汇总的主要粒度是 Memory Block。

示例：

```text
# FEISHU-231 Index

## Sessions

| Session | Source | Time | Main Topics | Status |
|---|---|---|---|---|
| [[sessions/2026-04-27_thread_abc/session_wiki.md]] | 群聊 thread | 2026-04-27 | 发布时间、对外口径、销售风险 | active |
| [[sessions/2026-04-28_doc_xyz/session_wiki.md]] | 方案文档 | 2026-04-28 | 技术方案、范围裁剪 | active |

## Memory Blocks

| Block | Topic | Stage | Status | Session |
|---|---|---|---|---|
| [[sessions/2026-04-27_thread_abc/session_wiki.md#block-1-发布时间口径]] | 发布时间 | 阶段 A | active | 2026-04-27_thread_abc |
| [[sessions/2026-04-27_thread_abc/session_wiki.md#block-2-销售承诺风险]] | 风险与阻塞 | 阶段 A | open | 2026-04-27_thread_abc |
| [[sessions/2026-04-28_doc_xyz/session_wiki.md#block-1-方案选择]] | 方案选择 | 阶段 B | active | 2026-04-28_doc_xyz |

## Topics

### 发布时间
- [[sessions/2026-04-27_thread_abc/session_wiki.md#block-1-发布时间口径]]
- [[sessions/2026-04-30_meeting_release/session_wiki.md#block-2-发布时间调整]]

### 方案选择
- [[sessions/2026-04-28_doc_xyz/session_wiki.md#block-1-方案选择]]

### 风险与阻塞
- [[sessions/2026-04-27_thread_abc/session_wiki.md#block-2-销售承诺风险]]
- [[sessions/2026-04-29_task_comment/session_wiki.md#block-1-迁移窗口风险]]
```

这样即使一个 session 中包含多个事情，index 也不会只停留在 session 级别。

同时，即使同一个主题跨群、跨文档、跨时间，index 也可以把多个 Memory Block 串成 topic 演进链路。

---

## 10.3 task_wiki.md 的定位

`task_wiki.md` 是任务总览，不直接承载所有细节。

它主要从 index.md 中挑选当前最重要的 Memory Block，并综合这些 block 的结论、风险、行动项和时间线。

它应包含：

```text
1. 当前摘要
2. 当前结论
3. 关键决策
4. 决策依据
5. 异议与风险
6. 规则与约束
7. 行动项
8. 时间线
9. 相关 Session Wiki
10. 可选 Topic Views
```

Task Wiki 中的每个结论都应该能链接到相关 Memory Block，再由 Memory Block 回到 session_wiki.md，并最终回溯到 session_event。

---

## 10.4 Topic View 的更新原则

Topic View 是可选派生页，不是主存储。

只有当某个主题跨多个 session，且需要长期维护时，才创建或更新：

```text
views/release_plan.md
views/external_communication.md
views/risk_and_blockers.md
```

Topic View 的来源应该是多个 Memory Block，而不是直接从原始 session file 或 event 生成。

```text
Memory Block → views/*.md
```

这保证了所有综合内容都能回到一手 session 记忆页。

---

# 11. 记忆检索

## 11.1 目标

当后续讨论触及某个 task 或相关主题时，系统可以快速召回历史上下文。

检索不应直接从原始资料开始，而应优先使用已经编译好的 Wiki 和索引。

---

## 11.2 检索路径

推荐路径：

```text
Query
  → index.md
  → Memory Block
  → session_wiki.md
  → Event Reference
  → session events.jsonl
  → Evidence Quote
  → session.md
```

即：

```text
1. 根据 task_id 找到对应任务目录
2. 读取 index.md，根据 topic / time / status 定位相关 Memory Block
3. 通过 Memory Block 链接进入对应 session_wiki.md
4. 在 Memory Block 中找到相关 slot 和 Evidence References
5. 根据 event_id / event_path 找到 session events.jsonl
6. 从 session_event 中读取 evidence_quote
7. 必要时回到 session.md
```

如果存在相关 topic view，也可以走：

```text
Query
  → index.md
  → views/*.md
  → Memory Block
  → session_wiki.md
  → session_event
  → evidence_quote
```

---

# 12. 记忆巡检：Lint

## 12.1 目标

Lint 用于维护 Task Wiki 的长期健康度。

它不是抽取流程，而是周期性检查和修复流程。

---

## 12.2 巡检内容

Lint 应检查：

```text
1. 是否有 session_event 没有被对应 session_wiki.md 引用
2. 是否有 session_wiki.md 没有 Evidence References
3. 是否有旧结论被新 event 覆盖但还显示为 active
4. 是否有开放异议长期未解决
5. 是否有行动项过期
6. 是否有 session 被删除但 event 仍在支撑 Wiki
7. 是否有 claim 强度超过 quote
8. 是否有同一 topic 下的结论冲突
9. 是否有孤立 session_wiki.md
10. 是否缺少必要交叉引用
```

---

# 13. 记忆遗忘：Forgetting

## 13.1 目标

企业协作记忆不能只增加，还需要支持遗忘、失效、覆盖和隐藏。

遗忘不是简单删除，而是要保证可追溯和当前视图正确。

---

## 13.2 Source-level Forgetting：session 删除

适用于：

```text
- 原始消息被删除
- 文档被撤回
- 用户要求移除某个 session
- 来源不再有权限访问
```

处理方式：

```text
1. 标记 session 为 revoked / deleted
2. 找出该 session 贡献的所有 session_event
3. 将这些 session_event 标记为 source_revoked
4. 更新或归档该 session_wiki.md
5. 更新 index.md
6. 重新计算 task_wiki.md
7. 如果相关 topic view 依赖该 session，也同步更新
8. 在 log.md 记录遗忘操作
```

如果 event 失去唯一证据，它不能继续作为 active fact。

---

## 13.3 Event-level Invalidation：事件失效

适用于：

```text
- session_event 抽取错误
- verification 后续发现不成立
- quote 不支持 claim
- 人工审核驳回
```

处理方式：

```text
event.status = invalidated
event.invalidated_reason = ...
event.invalidated_at = ...
```

然后重建相关 session_wiki.md、task_wiki.md 和可选 topic view。

---

## 13.4 Knowledge-level Supersession：知识被覆盖

适用于：

```text
- 截止日期从 5 号改到 10 号
- 决策从方案 A 改成方案 B
- 风险已解决
- 行动项已完成
```

这不是删除旧 event。

旧 event 仍然存在，但 task_wiki.md 或 topic view 的当前状态被新 session_event 覆盖。

---

## 13.5 View-level Forgetting：当前视图隐藏

适用于：

```text
- 旧结论已经无关
- 行动项已完成很久
- 风险已关闭
- 当前讨论不需要展示
```

处理方式：

```text
event 仍保留
session_wiki.md 仍保留历史
index.md 或 task_wiki.md 中对应内容变为 archived / resolved / superseded
task_wiki.md 默认不展示，但时间线和证据仍可查
```

---

# 14. 日志与索引

## 14.1 index.md

`index.md` 是 task 的 session wiki 与 Memory Block 目录。

它应记录：

```text
- task 基本信息
- session_wiki.md 列表
- 每个 session 的来源、时间、参与人
- 每个 session 中的 Memory Block
- 每个 Memory Block 的 topic / stage / status
- topic 到 Memory Block 的反向索引
- 当前未关闭异议
- 当前开放行动项
- 关键时间点
- 可选 topic view 链接
```

它不需要记录所有 event。

index.md 的核心粒度是 Memory Block，而不是整个 session_wiki.md。

---

## 14.2 log.md

`log.md` 是只增日志。

它记录：

```text
- session ingest
- candidate_event extraction
- verification
- session_event write
- session_wiki update
- index update
- task_wiki refresh
- topic view update
- lint
- forgetting
- manual review
```

建议使用统一前缀，便于解析：

```text
## [2026-04-27] ingest | 2026-04-27_thread_abc
## [2026-04-27] extract | 14 candidate_events
## [2026-04-27] verify | 12 session_events verified
## [2026-04-27] update | sessions/2026-04-27_thread_abc/session_wiki.md
## [2026-04-28] refresh | task_wiki.md
## [2026-04-28] lint | 2 overdue commitments
## [2026-04-29] forget | revoked session 2026-04-20_doc_old
```

---

# 15. 系统操作总览

## 15.1 提取 Extraction

```text
1. 确认 source 已绑定 task_id
2. 形成 session file
3. 筛选 Evidence Span
4. 区分 Core / Context / Current State Context
5. 从 Core 抽取 candidate_event
6. 执行 verification
7. verified event 写入 session events.jsonl，成为 session_event
```

---

## 15.2 存储 Storage

```text
1. Session File 作为事实来源保存
2. Session File 版本化保存
3. session_event 写入 sessions/{session_id}/events.jsonl
4. session_wiki.md 引用 session_event
5. index.md 指向 session_wiki.md
6. task_wiki.md 作为总览页可增量刷新
7. views/*.md 作为可选派生视图
```

---

## 15.3 检索 Retrieval

```text
1. 根据 task_id 找到任务目录
2. 读取 index.md
3. 找到相关 session_wiki.md
4. 从 session_wiki.md 找到 Evidence References
5. 根据 event_id / event_path 找到 session events.jsonl
6. 读取 evidence_quote
7. 必要时回到 session.md
```

---

## 15.4 更新 Update

```text
1. 新 session 被摄入
2. 抽取 candidate_event
3. verification 后生成 session_event
4. 写入 session events.jsonl
5. 生成或更新该 session 的 session_wiki.md
6. 在 session_wiki.md 中生成或更新 Memory Block
7. 更新 index.md 中的 Memory Block 索引
8. 按需刷新 task_wiki.md
9. 如已有 topic view，按需刷新 views/*.md
10. 追加 log.md
11. 可选触发 lint
```

---

## 15.5 遗忘 Forgetting

```text
1. session 删除 → source-level forgetting
2. event 错误 → event-level invalidation
3. 新事实覆盖旧知识 → knowledge-level supersession
4. 旧内容不再展示 → view-level forgetting
```

---

# 16. 最终总结

本系统以 `task_id` 为核心组织飞书企业协作记忆。

它的关键不是让 LLM 直接总结协作内容，也不是一开始就按主题维护 Wiki，而是构建一条以 session 为基础的可验证、可索引、可维护的事实链路：

```text
飞书协作内容
  → task_id 绑定
  → Session File
  → Evidence Span
  → candidate_event
  → verification
  → session_event
  → session_wiki.md
  → index.md
  → task_wiki.md
  → optional topic views
```

其中：

```text
Session File:
事实来源，也是一次可摄入的 task 协作上下文文件。

Evidence Span:
从 session 中筛出的候选证据包。

candidate_event:
从 Core 中抽取出的候选最小协作事实。

verification:
判断 candidate_event 是否能成为正式记忆。

session_event:
通过 verification 后写入 session events.jsonl 的正式事实事件。

session_wiki.md:
一个 session 对应的一手记忆页，是基础 Wiki Page。

Memory Block:
session_wiki.md 内部围绕具体问题、主题、阶段或事项形成的局部记忆单元，是 index.md 的核心索引粒度。

index.md:
指向 session_wiki.md 中的 Memory Block，并按 topic / stage / status 聚合这些 block。

task_wiki.md:
基于多个 session_wiki.md 汇总出的任务当前状态总览。

views/*.md:
可选的跨 session 主题综合视图。
```

最终，系统可以在后续协作中主动感知相关话题，召回历史决策、理由、异议、约束、行动项和证据来源，减少信息差、避免重复争论，并降低团队沟通成本。
