## Openclaw问题

在Memory.md里面提取出来的：其实还不错，但是没有证据，无法确定和验证真伪，并且这个视角是对于单个用户的视角，而不是企业项目为视角，如果有个人的重要信息在里面那么这个文件就会被其他信息稀释

难点：
问题描述
OpenClaw 目前的记忆机制存在三个主要问题，它们彼此之间形成一个闭环，导致信息处理的不一致、不可验证和不可更新：

信息分散：以个人为核心，导致不同的记忆片段孤立在各个地方。
抽取不完全：信息抽取机制不够结构化，可能漏掉关键信息。
无法验证与更新：一旦信息被抽取，无法验证其准确性，也没有自动更新的机制。
=>一个task会在用户间反复讨论，甚至因为信息不一致问题导致理解错位

知识图谱问题：
图结构复杂且维护困难：事件合并、边的更新和增量更新的复杂性使得图结构不适合处理动态变化的任务信息。
信息一致性和可验证性问题：事件抽取的不一致性和别名问题让图结构无法准确记录任务的状态和决策过程。

#### 详细分析

1️⃣ 个人为核心导致信息分散和不一致
问题描述：
现状：OpenClaw 的记忆机制基于个人工作流，每个人独立维护自己的 memory。
分散：不同的员工、不同的任务、不同的文档和聊天都分别形成“独立的记忆片段”。
不一致：这导致了信息的重复、遗漏，且每个人维护的信息在语义上不一定完全一致。
本质问题：

以个人为核心的记忆模型无法在团队协作中整合不同的信息源，导致信息的孤岛现象。这不仅增加了后期的跨部门、跨任务沟通成本，还容易出现信息碎片化、冲突以及遗漏的情况。

2️⃣ 信息抽取不完全和多元信息冲突
问题描述：
现状：OpenClaw 在抽取信息时，并没有结构化地进行提取，它依赖的是基于模型的自然语言处理。
漏掉信息：这种抽取方式并不保证每一条信息都被准确、完整地捕捉到，可能会漏掉关键的上下文或细节。
冲突：由于没有结构化的冲突解决机制，多个信息源中可能会存在相互冲突的信息。比如，任务的不同状态描述，或者决策的不同表述，这些冲突无法自动解决或统一。
本质问题：

缺乏结构化抽取和冲突消解机制会导致信息处理的不一致。不同来源的决策、状态或事实可能相互矛盾，但由于缺乏自动验证和协调机制，系统不能自动判定哪个是最新、哪个是准确的，从而产生不可信的结果。

3️⃣ 无法验证和缺乏自动更新
问题描述：
现状：OpenClaw 没有清晰的机制来验证每一条被抽取的信息的准确性，也无法动态地更新和修正已存储的记忆。
无法验证：抽取的信息本身就无法被验证，且系统缺乏检查其正确性的能力。这意味着，系统只能基于当前的记忆提供答案，但不能根据新的输入或历史状态来自动调整或纠正。
无法更新：当信息发生变化时，系统不能自动检测到更新并修改已存储的记忆，也不会有冲突消解机制来确保信息的一致性。
本质问题：

无法验证和无法更新导致了系统的长期记忆和当前信息状态可能不一致。信息一旦被抽取，它便成为静态的，后续的更新不会被自动检测和整合，导致系统无法提供持续一致的决策支持。

### 结论

1. 任务绑定和信息归类（Preprocessing阶段）
   目标： 确定每条信息（消息、文档、评论等）是否属于某个任务，并确保信息关联到正确的 task_id。
   步骤：
   每个会话线程（thread）和文档（document）都会绑定到一个特定的 task_id。这个 task_id 是任务的唯一标识符。
   在消息或文档创建时，会通过上下文来判断是否需要绑定到某个 task_id。如果绑定，则继续处理；如果没有绑定，则不做处理。
   注意：
   这个绑定过程非常关键，因为它确定了所有后续的信息处理都将围绕 任务 展开，而不是围绕个人或其他无关的上下文。

2. 抽取 Evidence（事件证据提取）
   目标： 从每条与 task_id 相关的消息或文档中，抽取出最小的、可验证的 协作事实（即事件证据）。
   步骤：
   使用 event 抽取机制（如决策、理由、异议、约束等）来拆解每条消息或文档。
   确保每个抽取出来的 event 都是 最小的、可验证的事实断言，并且由原文直接支撑。这样可以确保在后续使用中，这些事实是可校验的。
   例子：
   从一条消息中提取出：“方案 A 成本太高”，然后通过 rationale_event 类型来表达这个理由。
   从一条消息中提取出：“李四周五前补齐接口文档”，然后通过 commitment_event 类型来记录这个承诺。

3. Event 存储（Event Ledger）
   目标： 存储所有与 task_id 相关的 event。
   步骤：
   每个被抽取的 event 会存储在一个数据库表中（event ledger）。这些 event 将形成一个按时间顺序排列的事实流水，表示与任务相关的所有关键信息变化。
   验证：
   在 event 被存储之前，会进行 验证，确保：
   事件是由 Core evidence 支撑的。
   事件没有超出证据的支持范围（比如没有被强行添加新的细节）。
   每条事件只表达一个明确的事实。

4. 创建 KI（知识项）
   目标： 基于 event ledger 和抽取的 event 创建任务的 知识项（KI）。
   步骤：
   将每个 event 转化为 KI（Knowledge Item），并根据其类型（例如决策、理由、行动项等）将其组织在 task wiki 中。
   每个 KI 代表任务中的一个知识单元，并可以由多个事件更新。例如，commitment 类型的事件可以在任务的 wiki 中更新 行动项 部分。
   字段设计：
   每个 KI 会包括一些标准字段（如：claim，owner，deadline，evidence_quote 等），并且会随着新的 event 的引入而更新。
   例子：
   KI1：目标发布时间，结论：5 月 5 日。
   KI2：行动项，李四需要补齐接口文档，截止日期：5 月 10 日。

5. Wiki 更新（Task Wiki 更新）
   目标： 通过 event 来更新和维护 任务 Wiki，并保持任务的当前状态。
   步骤：
   每个任务（task_id）会有一个 任务 Wiki，这是所有相关 event 的集合和组织。
   Wiki 页面会随着 event 的更新而变化。例如，如果某个决策被修订，Wiki 中的相应决策项也会随之更新。
   例子：
   Wiki Item 1：当前结论是“5 月 5 日目标发布时间”。
   Wiki Item 2：行动项“李四补齐接口文档，截止日期 5 月 10 日”。

6. **任务绑定和信息归类**：通过判断是否绑定到 `task_id` 来确保所有信息都归属正确任务。
7. **事件证据抽取**：从相关信息中抽取出最小、可验证的事件。
8. **Event 存储**：将事件存储到数据库，形成任务的事件流水（事件记账）。
9. **创建 KI（知识项）**：根据事件创建知识项（KI），组织并存储任务相关的知识。
10. **任务 Wiki 更新**：维护和更新任务的 Wiki，保证每个任务的状态和知识是最新的。

核心挑战与解决思路
如何准确地判断一个消息是否与任务相关？
通过任务绑定机制 (task_id) 来判断每条信息是否与某个任务相关。如果某个消息没有绑定到 task_id，则不处理。

如何确保每个抽取的 event 是可验证的？
强制确保每个 event 都由 Core evidence 支撑，确保 claim 只表达一个事实，不强行加细节，且事件的每个部分都可以回溯到原文证据。

如何确保任务 Wiki 更新是自动化且可追溯的？
任务 Wiki 直接从 event ledger 中生成，确保所有更新都能追溯到原始 event，并且能在后续任务中自动推送历史决策和相关上下文。

提取：按 session 抽 event
存储：event 存在 session/events.jsonl
记忆页：每个 session 一个 session_wiki.md
索引：index.md 把 session wiki 按 topic 聚合
更新：新 session 只增量更新自己的页面和 index
检索：先查 index，再读相关 session wiki，必要时回到 event 和 quote
综合：task_wiki.md 汇总多个 session wiki
