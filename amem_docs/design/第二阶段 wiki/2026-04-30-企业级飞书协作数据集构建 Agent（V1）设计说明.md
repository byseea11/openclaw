# Feishu IM Dataset Builder Agent（V1）设计说明

## 1. 工具定位

**Feishu IM Dataset Builder Agent（V1）** 是一个用于自动构造企业软件需求协作数据的离线数据构建工具。

它的目标不是实现记忆引擎，也不是直接做评测，而是先解决一个更基础的问题：

> 如何自动生成一批真实感强、可真实落地到飞书 IM、并能转换为 OpenClaw 飞书消息入口格式的企业协作数据集。

V1 严格聚焦 **飞书群聊 / thread 消息**，只处理飞书 IM 中的项目群聊消息和 thread 回复。

V1 不直接处理：

```text
文档评论 @Agent
任务评论入口
日历 / 会议事件入口
飞书卡片点击事件
reaction 语义
query_set / golden answer
Memory Block / task_wiki 评测
```

V1 的最终产物是：

```text
飞书真实 raw messages
+ OpenClaw 可回放的 Feishu message ingress 数据
```

后续的 golden answer、query set、Memory Block、task_wiki 评测可以基于 V1 数据集继续构建，但不属于 V1 的核心产物。

---

## 2. V1 数据集形态

V1 数据集不是一个 run 目录，也不是一个单独的大 JSON 文件。

V1 的数据组织方式是：

> **一个 case = 一个文件夹。**

每个 case 文件夹表示一个完整的企业软件需求协作故事。文件夹中保存该 case 从故事生成到飞书执行、再到 OpenClaw message ingress 转换的完整构造轨迹。

推荐目录结构：

```text
feishu_im_dataset_v1/
  dataset_manifest.json

  cases/
    case_001_sso_audit/
      case_spec.json
      story.json
      characters.json
      conflict_timeline.json
      execution_plan.json
      execution_result.json
      lark_fetch_records.jsonl
      openclaw_message_ingress.jsonl
      build_report.json

    case_002_release_blocker/
      case_spec.json
      story.json
      characters.json
      conflict_timeline.json
      execution_plan.json
      execution_result.json
      lark_fetch_records.jsonl
      openclaw_message_ingress.jsonl
      build_report.json
```

说明：

```text
case_spec.json
  用户或批量生成器给定的 case 输入种子。

story.json
  Story Generator 生成的企业需求故事背景。

characters.json
  参与该 case 的企业角色与职责设定。

conflict_timeline.json
  Conflict Timeline Planner 生成的冲突时间线。

execution_plan.json
  Story-to-Command Mapper 生成的 lark-cli 可执行计划。

execution_result.json
  Lark Executor 真实执行后的飞书 ID 映射和执行状态。

lark_fetch_records.jsonl
  Lark Raw Collector 回收的 lark-cli 原始返回。

openclaw_message_ingress.jsonl
  OpenClaw Adapter 转换后的可回放 Feishu message ingress 数据。

build_report.json
  本 case 的构建报告和数据质量统计。
```

### 2.1 实现形态和非目标

当前 V1 的实现形态必须明确为：

- 一个 **IM-only 的离线数据构建 Builder**
- 一个 **以 case 文件夹为原始产物层** 的数据构建工具
- 一个负责“故事生成 -> 飞书真实落地 -> raw 回收 -> OpenClaw ingress 转换”的离线流水线

当前 V1 case 文件夹是 Builder 原始产物层，与旧 `eval_old` / snapshot 结构**无兼容要求**。

旧 eval 可以作为历史参考，但不是 V1 的输出目标。V1 当前只负责：

```text
故事生成
真实 IM 落地
raw message 回收
OpenClaw message ingress 转换
```

V1 当前不负责：

```text
query set
golden answer
旧 snapshot/export 兼容层
自动评分
```

## 3. 为什么需要这个 Agent

企业级记忆引擎需要处理的不是普通聊天，而是围绕任务、需求、项目推进产生的长期协作上下文。

例如一个企业软件需求从提出到落地，往往会经历：

```text
客户提出需求
→ 产品定义范围
→ 研发评估方案
→ 安全提出约束
→ 运维指出上线窗口问题
→ 销售可能提前承诺客户
→ 项目组修正对外口径
→ 后续消息覆盖早期结论
```

这类数据很难直接找到公开真实数据集，因此需要一个 Data Agent 自动生成。

V1 Data Agent 的核心价值是：

1. 自动生成企业软件需求协作故事。
2. 自动生成足够多的企业角色和部门关系。
3. 自动设计有冲突、有状态变化的故事线。
4. 自动把故事线编译成 lark-cli 可执行计划。
5. 在飞书里真实创建群聊 / thread / 消息。
6. 回收飞书 raw message。
7. 转换成 OpenClaw 可回放的 message ingress 数据。

---

## 4. V1 范围边界

### 4.1 V1 做什么

V1 只做飞书消息型数据集生成：

```text
飞书项目群聊
飞书 thread 回复
文本消息
系统消息可保留但不作为核心协作事实
```

V1 支持的核心场景：

```text
企业软件需求协作
项目决策讨论
上线时间变更
阻塞原因同步
负责人变化
对外口径修正
历史结论被后续消息覆盖
```

### 4.2 V1 不做什么

V1 暂不处理：

```text
飞书文档评论 @Agent
飞书任务评论入口
日历 / 会议事件入口
飞书卡片点击事件
reaction 语义
golden answer 自动评测
Memory Block 评分
task_wiki 评分
```

这些属于后续阶段。

### 4.3 V1 的终点

V1 的终点不是 query set，也不是 gold answer。

V1 的终点是：

```text
1. 已经在飞书中真实创建了一段企业协作消息过程
2. 已经回收了飞书 raw message
3. 已经转换成 OpenClaw 可回放的 Feishu message ingress 数据
```

## 5. V1 的七步流水线

V1 Data Agent 可以被拆成 7 个模块。

```text
Step 1：Story Generator
Step 2：Character Generator
Step 3：Conflict Timeline Planner
Step 4：Story-to-Command Mapper
Step 5：Lark Executor
Step 6：Lark Raw Collector
Step 7：OpenClaw Adapter
```

其中 Step 5 到 Step 7 共同组成“真实落地、回收与适配”阶段。

---

## 6. 全局规则

这些规则适用于所有 Agent / 模块。

### 6.1 V1 严格 IM-only

V1 只能生成和执行以下 IM 动作：

```text
create_chat
send_message
reply_in_thread
fetch_chat_messages
fetch_thread_messages
```

V1 不允许生成以下动作：

```text
create_doc
update_doc
comment_doc
create_task
update_task
comment_task
create_calendar_event
fetch_doc
fetch_task
fetch_calendar_event
```

如果故事中需要出现“文档更新”“任务状态变化”“会议结论”等信息，只能通过群聊或 thread 消息表达，例如：

```text
我刚更新了需求文档，结论是本期只做 SSO，不做审计日志导出。
任务状态我改成 blocked 了，原因是安全审批还没过。
今天会议结论同步一下，发布时间从 5 月 5 日改为 5 月 10 日灰度。
```

### 6.2 每个 case 必须围绕一个 task_id

每个 case 必须有唯一的：

```text
case_id
task_id
```

所有故事、角色、时间线、执行动作、飞书消息和 OpenClaw ingress 都必须显式携带或可追溯到这个 `task_id`。

### 6.3 每个 case 必须有足够多的企业角色

每个 case 至少包含 **6 到 10 个角色**。

角色必须覆盖多个部门，优先包含：

```text
产品
后端研发
前端研发
测试 / QA
安全合规
运维 / SRE
销售
客户成功
技术负责人 / TL
```

角色不是装饰字段，必须影响消息内容和冲突来源。

例如：

```text
销售倾向于提前承诺客户。
研发倾向于保守评估工期。
安全关注字段、权限、合规风险。
运维关注灰度窗口、回滚脚本和上线 checklist。
产品负责范围裁剪和口径统一。
客户成功负责同步客户诉求和客户反馈。
```

### 6.4 每个 case 必须包含冲突和状态变化

每个 case 不能是线性顺滑剧情。必须至少包含 3 类冲突或变化：

```text
旧 deadline 被后续消息修正
blocker 被发现
scope 被裁剪
owner 或责任边界变化
销售口径和研发 / 产品口径不一致
安全或运维约束导致上线风险
对外口径被 PM 修正
```

### 6.5 LLM 不能直接生成 execution_plan

LLM 只能用于生成：

```text
story.json
characters.json
conflict_timeline.json
```

`execution_plan.json` 必须由确定性 `Story-to-Command Mapper` 生成。

这样做是为了避免 LLM 直接产生命令导致：

```text
action 类型漂移
ref 不一致
depends_on 缺失
thread root 关系错误
无法稳定复现
```

### 6.6 Data Agent 不生成评测 gold

V1 不生成：

```text
query_set.json
golden_answer.json
gold_session_events.jsonl
gold_memory_blocks.jsonl
```

这些属于后续 V1.5 / V3。

## 7. Step 1：Story Generator

### 7.1 目标

生成一个企业软件需求协作故事。

这个故事需要回答：

```text
这个 case 是什么需求？
它属于哪个企业软件场景？
它为什么需要跨部门协作？
它的业务压力是什么？
它最初的项目假设是什么？
```

### 7.2 输入

输入文件：`case_spec.json`

最小字段：

```json
{
  "case_id": "case_001_sso_audit",
  "task_id": "REQ-001",
  "title": "企业版支持 SSO 登录与审计日志导出",
  "company_type": "B2B SaaS 公司",
  "departments": ["产品", "研发", "安全", "运维", "销售", "客户成功"],
  "main_goal": "评估并推进 5 月初上线",
  "difficulty": "medium",
  "seed": 42
}
```

### 7.3 输出：`story.json`

输出必须包含：

```text
case_id
task_id
title
background
business_pressure
project_goal
initial_assumption
main_conflicts
in_scope
out_of_scope
```

示例：

```json
{
  "case_id": "case_001_sso_audit",
  "task_id": "REQ-001",
  "title": "企业版支持 SSO 登录与审计日志导出",
  "background": "重点客户续约前要求补齐企业安全能力。",
  "business_pressure": "销售希望在 5 月初前给客户明确承诺，否则续约推进会受影响。",
  "project_goal": "在企业版中完成 SSO MVP，并评估审计日志导出是否进入本期范围。",
  "initial_assumption": "项目组最初把 5 月 5 日作为内部评估目标。",
  "main_conflicts": [
    "销售希望尽快承诺客户",
    "研发担心权限同步依赖旧接口",
    "安全要求审计日志字段先过评审",
    "运维要求灰度和回滚脚本先验收"
  ],
  "in_scope": ["SSO MVP", "企业版配置页", "管理员操作日志初步评估"],
  "out_of_scope": ["完整登录日志导出", "所有客户定制字段"]
}
```

### 7.4 Story Generator 限制

Story Generator 必须遵守：

1. 不能生成泛泛而谈的办公故事，必须是企业软件需求或项目交付故事。
2. 必须围绕单一 `task_id` 展开。
3. 必须给出明确业务压力，例如客户续约、上线窗口、合规要求、销售承诺、迁移 deadline。
4. 必须包含潜在冲突来源。
5. 不能直接生成聊天消息。
6. 不能生成 lark-cli 命令。
7. 不能生成 golden answer 或 query。
8. 不得引入 V1 不支持的原生入口，例如文档评论 @Agent 或日历触发事件。

## 8. Step 2：Character Generator

### 8.1 目标

根据 `story.json` 生成该 case 的企业角色表。

角色用于驱动后续消息视角、冲突来源、责任归属和口径差异。

### 8.2 输入

```text
case_spec.json
story.json
```

### 8.3 输出：`characters.json`

输出必须包含 6 到 10 个角色。

每个角色必须包含：

```text
person_id
name
department
role
responsibility
communication_style
conflict_bias
```

示例：

```json
{
  "case_id": "case_001_sso_audit",
  "characters": [
    {
      "person_id": "pm_lincheng",
      "name": "林晨",
      "department": "产品",
      "role": "产品经理",
      "responsibility": "定义需求范围、同步项目结论、统一对外口径",
      "communication_style": "谨慎、喜欢用“先按内部目标评估”保留余地",
      "conflict_bias": "会纠正销售过度承诺"
    },
    {
      "person_id": "dev_zhouyu",
      "name": "周宇",
      "department": "研发",
      "role": "后端负责人",
      "responsibility": "评估 SSO、权限同步和审计日志接口改造",
      "communication_style": "偏技术风险说明，强调依赖和工期不确定性",
      "conflict_bias": "会指出旧 IAM 接口和迁移窗口风险"
    },
    {
      "person_id": "sec_chenxue",
      "name": "陈雪",
      "department": "安全合规",
      "role": "安全负责人",
      "responsibility": "审核审计日志字段和敏感信息暴露风险",
      "communication_style": "明确、偏规则约束",
      "conflict_bias": "会阻止未经评审的日志字段上线"
    }
  ]
}
```

### 8.4 Character Generator 限制

Character Generator 必须遵守：

1. 每个 case 至少 6 个角色，最多 10 个角色。
2. 角色必须覆盖至少 5 个不同部门。
3. 角色必须与 story 的需求场景相关，不能出现无关角色。
4. 每个角色必须有明确 `responsibility`。
5. 每个角色必须有 `conflict_bias`，用于后续时间线和消息冲突。
6. 角色姓名、person_id 必须在 case 内唯一。
7. `person_id` 必须是稳定英文 snake_case，例如 `pm_lincheng`。
8. 不允许后续 execution_plan 使用未在 `characters.json` 中定义的 `sender_ref`。

## 8.5 角色与真实操作者身份

`characters.json` 中定义的是 **语义角色**，不等价于真实飞书操作者身份。

这些角色的作用是：

```text
驱动发言视角
驱动冲突来源
驱动责任边界
驱动口径差异
```

它们不直接表示“谁用真实飞书账号把这条消息发出去”。

真实执行 `lark-cli` 时，必须单独引入执行身份概念：

```text
operator_identity = user | bot
```

V1 默认推荐模式是：

```text
单一真实 operator
+ 消息文本前缀表达角色
```

例如：

```text
【产品/林晨】先按 5 月 5 日作为内部评估目标，但这个日期现在不能对外承诺。
【研发/周宇】当前真正 blocker 不是代码，而是迁移窗口还没锁定。
【安全/陈雪】审计日志字段没有过评审前，不建议承诺客户导出能力。
```

因此：

- `execution_plan.json` 中的 `sender_ref` 表示**语义角色**
- `sender_ref` 不直接等价于真实飞书登录账号
- 真正负责发消息的身份由 Executor 的 `operator_identity` 决定

如果未来支持多个真实账号分别发送消息，那属于后续增强，不属于 V1 默认能力。

## 9. Step 3：Conflict Timeline Planner

### 9.1 目标

基于 `story.json` 和 `characters.json` 生成一条有时间推进、有冲突、有状态变化的故事线。

这一层不是被测系统输入，而是 Data Agent 的生成控制层。

它用于控制：

```text
哪些信息先出现？
哪些信息后来被修正？
哪些结论是旧口径？
哪些状态发生变化？
哪些角色之间存在冲突？
```

### 9.2 为什么需要 conflict timeline

如果直接生成聊天，可能会得到一段看起来像聊天、但没有明确状态变化的数据。

而企业记忆数据集需要有：

```text
旧信息
新信息
冲突信息
后续修正
当前状态
```

因此，需要一条隐藏的冲突时间线来控制故事发展。

### 9.3 输入

```text
case_spec.json
story.json
characters.json
```

### 9.4 输出：`conflict_timeline.json`

输出必须包含 6 到 12 个 timeline event。

每个 event 必须包含：

```text
timeline_id
time_order
event_type
description
actor_refs
affected_topic
state_effect
should_surface_in_message
```

示例：

```json
{
  "case_id": "case_001_sso_audit",
  "timeline": [
    {
      "timeline_id": "tl_001",
      "time_order": 1,
      "event_type": "initial_request",
      "description": "客户成功同步重点客户希望 5 月 5 日前上线 SSO 能力。",
      "actor_refs": ["cs_zhaomin"],
      "affected_topic": "客户需求和初始目标",
      "state_effect": "形成早期上线压力",
      "should_surface_in_message": true
    },
    {
      "timeline_id": "tl_004",
      "time_order": 4,
      "event_type": "ops_blocker",
      "description": "运维指出回滚脚本还没有最终验收，所以 5 月 5 日只能算乐观日期。",
      "actor_refs": ["ops_wangyuan"],
      "affected_topic": "上线时间",
      "state_effect": "削弱 5 月 5 日确定性",
      "should_surface_in_message": true
    }
  ]
}
```

### 9.5 Conflict Timeline Planner 限制

Conflict Timeline Planner 必须遵守：

1. 时间线必须按 `time_order` 单调递增。
2. 必须包含至少 1 个早期结论和 1 个后续修正。
3. 必须包含至少 1 个 blocker 或 risk。
4. 必须包含至少 1 个对外口径或承诺风险。
5. 必须包含至少 1 个来自非产品角色的异议或约束。
6. `actor_refs` 必须来自 `characters.json`。
7. 每个 event 必须能被后续映射成至少一条 IM 消息，除非 `should_surface_in_message=false`。
8. 不能引入文档、任务、日历作为原生入口；如果提到这些内容，必须表示为“某人在群聊或 thread 中同步”。
9. 不能直接生成 `execution_plan`。
10. 不能生成最终答案或评测问题。

## 10. Step 4：Story-to-Command Mapper

### 10.1 目标

把 `story.json`、`characters.json` 和 `conflict_timeline.json` 编译成 lark-cli 可执行计划。

这一层解决的问题是：

> 自然语言故事如何落到真实飞书操作？

该模块必须是确定性的，不由 LLM 直接生成。

### 10.2 输入

```text
case_spec.json
story.json
characters.json
conflict_timeline.json
```

### 10.3 输出：`execution_plan.json`

输出必须包含：

```text
case_id
actions
```

示例：

```json
{
  "case_id": "case_001_sso_audit",
  "actions": [
```

### 10.5 Story-to-Command Mapper 限制

Story-to-Command Mapper 必须遵守：

1. 必须确定性执行，同一输入在同一 seed 下生成同一 `execution_plan`。
2. 必须先生成 `create_chat`，再生成消息动作。
3. 每个 `send_message` 或 `reply_in_thread` 必须有 `sender_ref`，且必须来自 `characters.json`。
4. 每个 action 必须有唯一 `action_id`。
5. 每个会产生飞书对象的 action 必须有唯一 `output_ref`。
6. `reply_in_thread.root_message_ref` 必须引用已有 `send_message` 的 `output_ref`。
7. 不允许引用真实 `chat_id/message_id/thread_id`，只能引用逻辑 ref。
8. `content_text` 必须来自 `conflict_timeline` 的语义，不得创造新的主事实。
9. 可以为自然度添加少量衔接语，但不能改变 timeline 的状态含义。
10. `execution_plan` 中不得出现 V1 不支持的 action 类型。
11. 必须自动追加必要的 `fetch_chat_messages` 和 `fetch_thread_messages` 动作，方便 Collector 回收。
12. 每个 timeline event 至少映射成 1 条消息；关键冲突 event 应优先映射为 thread 回复。
13. `conflict_timeline.json` 是主事实层，Mapper 只负责：

```text
选择 sender_ref
选择发到主群还是 thread
选择消息顺序
选择模板化表达方式
建立 action_id / output_ref / depends_on
```

14. Mapper 不负责：

```text
创造新的主事实
删除 should_surface_in_message=true 的关键事件
改写 timeline 的状态含义
改变结论、理由、反对意见、时间点的语义
```

15. Mapper 可以为了自然度添加少量衔接语，但不得新增、删除或改写 timeline 中的核心状态变化。事实定义权属于 `conflict_timeline.json`，Mapper 只做 surface placement 和 message templating。

```json
    {
      "action_id": "act_001",

    }
```

### 11.4 Lark Executor 限制

Lark Executor 必须遵守：

1. 必须按 `depends_on` 拓扑顺序执行 action。
2. 任何 action 失败时，必须记录失败原因，不得静默跳过。
3. 必须维护 `output_ref -> real resource id` 映射。
4. 必须维护 `thread_id_to_chat_id` 映射。
5. 不允许把真实 ID 回写到 `execution_plan.json`。
6. 真实 ID 只能写入 `execution_result.json`。
7. 必须支持 dry-run，只校验命令，不真实发送飞书消息。
8. 必须支持 resume，避免中途失败后重头执行已成功 action。
9. 执行器不负责改写故事、时间线或消息内容。
10. 执行器不负责生成 OpenClaw ingress。
11. Executor 必须显式区分真实执行身份：

```text
operator_identity = user | bot
delivery_mode = prefixed_single_operator | future_extension
```

12. 之所以必须显式区分 `operator_identity`，是因为 `lark-cli` 中 `--as user` 和 `--as bot` 会直接影响：

```text
是否可创建群
是否可发送消息
是否可拉取历史消息
返回的 sender name 是否完整
```

13. V1 默认推荐：

```text
operator_identity = user
delivery_mode = prefixed_single_operator
```

14. 在真实执行前，Executor 应执行 preflight，至少检查：

```text
当前身份是否可用
IM 相关权限是否具备
是否允许建群
是否允许发消息
是否允许拉消息
```

15. preflight 结果应进入 `build_report.json`，用于解释为什么某个 case 能或不能被完整物化到飞书。

## 13. Step 7：OpenClaw Adapter

### 13.1 目标

把 lark-cli 回收的 raw messages 转换成 OpenClaw 可回放的 Feishu message ingress 数据。

### 13.2 为什么需要 Adapter

lark-cli 返回的是 fetch response 格式，而 OpenClaw 飞书消息处理逻辑接收的是 message event 格式。

在 OpenClaw 的 message handler 中，处理逻辑会读取类似字段：

```text
event.message.message_id
event.message.chat_id
event.message.thread_id 或 event.message.root_id
event.message.create_time
event.message.chat_type
event.message.message_type
event.message.content
event.sender.sender_id.open_id
```

因此需要 Adapter 做格式转换。

### 13.3 输入

```text
lark_fetch_records.jsonl
execution_result.json
```

### 13.4 输出

```text
openclaw_message_ingress.jsonl
adapter_report.json
```

### 13.5 字段映射

| lark-cli raw 字段                       | OpenClaw message ingress 字段 | 说明                   |
| --------------------------------------- | ----------------------------- | ---------------------- |
| `message.message_id`                    | `message.message_id`          | 飞书消息 ID            |
| `message.content`                       | `message.content`             | 需要包装成 JSON string |
| `message.msg_type`                      | `message.message_type`        | text / system 等       |
| `message.sender.id`                     | `sender.sender_id.open_id`    | 发送者 open_id         |
| `message.create_time`                   | `message.create_time`         | 转成毫秒时间戳字符串   |
| `message.thread_id`                     | `message.thread_id`           | thread ID              |
| `response.data.thread_id`               | `message.thread_id`           | thread fetch 时补齐    |
| `execution_result.thread_id_to_chat_id` | `message.chat_id`             | thread 消息补 chat_id  |

### 13.6 输出示例：`openclaw_message_ingress.jsonl`

```json
{
  "case_id": "case_001_sso_audit",
  "task_id": "REQ-001",
  "event_type": "im.message.receive_v1",
  "sender": {
    "sender_id": {
      "open_id": "ou_xxx"
    },
    "sender_type": "user"
  },
  "message": {
    "message_id": "om_xxx",
    "chat_id": "oc_xxx",
    "chat_type": "group",
    "thread_id": "omt_xxx",
    "root_id": "omt_xxx",
    "parent_id": null,
    "message_type": "text",
    "content": "{\"text\":\"研发侧补充：当前真正 blocker 不是代码，而是数据迁移窗口未确认。\"}",
    "create_time": "1777284300000",
    "mentions": []
  }
}
```

### 13.7 输出示例：`adapter_report.json`

```json
{
  "case_id": "case_001_sso_audit",
  "input_fetch_records": 2,
  "input_messages": 7,
  "output_events": 7,
  "skipped_messages": 0,
  "filled_fields": [
    {
      "field": "message.chat_id",
      "source": "execution_result.thread_id_to_chat_id"
    }
  ],
  "warnings": []
}
```

### 13.8 OpenClaw Adapter 限制

OpenClaw Adapter 必须遵守：

1. 只能从 `lark_fetch_records.jsonl` 和 `execution_result.json` 读取输入。
2. 不得从 `story.json` 或 `conflict_timeline.json` 直接生成 message ingress。
3. 必须为每条非删除 text message 生成一条 ingress event。
4. system message 可以跳过，但必须在 `adapter_report.json` 中统计。
5. 必须补齐 `chat_id`；如果无法补齐，必须跳过该 message 并记录 warning。
6. `content` 必须包装成 OpenClaw message event 可消费的 JSON string。
7. `create_time` 必须转换为毫秒时间戳字符串。
8. 不允许修改消息语义或改写 message content。
9. 不生成 query、gold answer 或 Memory Engine 产物。
10. 输出必须可以按顺序回放。
11. Adapter 的输入契约应参考已安装的 `openclaw-lark` channel 实际消费字段。实际 inbound handler 依赖：

```text
event.message.message_id
event.message.chat_id
event.message.thread_id
event.message.root_id
event.message.create_time
event.message.chat_type
event.message.content
event.sender.sender_id.open_id
```

12. 对 thread / topic 的关键处理规则是：

```text
thread_id 优先
若 reply 事件没有 thread_id，则用 root_id 作为 fallback
```

13. 因此 Adapter 必须保证：

```text
能补齐 chat_id
对 thread reply 正确填充 thread_id
在需要时把 root_id 作为 fallback 保留下来
```

14. `thread_id` 存在时直接使用；`thread_id` 缺失但可由 fetch 上下文确认 reply root 时，补 `root_id`。
15. `chat_id` 必须从原始 chat fetch 或 `execution_result.thread_id_to_chat_id` 补齐。
16. 只有在 message 是非删除、可消费的文本消息时才生成 ingress event。
17. `content` 始终包装为：

```json
{ "text": "..." }
```

18. system message 可以跳过，但必须记入 `adapter_report.json`。
19. Adapter 不能从 `story.json` 或 `conflict_timeline.json` 推测消息内容，只能基于 raw fetch records 和 execution 映射表生成 ingress。
20. Adapter 输出的事件顺序必须可回放，并应保持与 raw message 时间顺序一致。

## 17. 一句话总结

**Feishu IM Dataset Builder Agent（V1）** 是一个自动化数据生成工具。

它输入企业软件需求主题，生成企业协作故事、角色表和冲突时间线，将故事线编译为 lark-cli 执行计划，真实落地到飞书群聊 / thread 中，再回收飞书 raw messages，并转换成 OpenClaw 可回放的 Feishu message ingress 数据。
