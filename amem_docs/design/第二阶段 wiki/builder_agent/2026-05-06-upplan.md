```text
四类 memory benchmark family
```

而不是：

```text
OpenClaw 专属弱点
```

OpenClaw 只是 baseline。真正要测的是**一个企业记忆系统是否具备这四类能力**。

---

# 1. 四类 family 应该这样定义

我建议正式改名成更通用的能力 family：

| Family                       | 原来叫法                  | 测试能力                                                  |
| ---------------------------- | ------------------------- | --------------------------------------------------------- |
| `context_interference`       | personal memory pollution | 抗干扰、任务隔离、只看 target task                        |
| `temporal_supersession`      | stale state               | 新状态是否能覆盖旧状态，是否区分 current / historical     |
| `evidence_traceability`      | unverifiable summary      | 记忆 claim 是否能回到原文证据，是否区分事实 / 猜测 / 转述 |
| `dependency_impact_tracking` | dependency propagation    | 上游任务变化是否能传播到下游任务影响判断                  |

这样更公平。你的 benchmark 不是“设计 OpenClaw 会失败的题”，而是：

```text
企业记忆系统必须通过的四类基础能力测试
```

---

# 2. 新原则

我建议把 builder agent 的原则写成这几条：

```text
1. family-first
   每条 case 先确定要测试哪一类 memory capability family。

2. single-family case
   单条 case 默认只测一个 family，避免评测归因混乱。

3. batch-family coverage
   批量生成时必须覆盖四类 family，每类至少有若干 case。

4. story follows family
   不是先随机生成企业故事，再分析它属于什么 family。
   而是先生成 family brief，再让故事服务这个 brief。

5. gold after collect
   collect 前只能有 probe targets / expected targets。
   真正 annotation gold 必须基于 collected messages 回标。

6. baseline separated
   OpenClaw Memory.md、OpenClaw + prompt、raw-message RAG、Task Wiki 必须作为不同 baseline mode。
```

---

# 3. builder agent 应该怎么构造

我建议改成这个核心链路：

```text
dataset-plan
-> family-selection
-> memory-capability-brief
-> case-spec
-> case-world
-> task-actor-layout
-> state-trajectory
-> conversation-plan
-> probe-targets
-> command-plan
-> execute
-> collect
-> annotation-gold
-> replay-eval
-> baseline-eval
-> benchmark-report
```

其中最关键的是前 7 步。

---

## 3.1 `dataset-plan`

只在 batch 或统一入口时使用。

作用：决定这批数据怎么覆盖四类 family。

输出：

```json
{
  "generation_mode": "batch",
  "dataset_size": 40,
  "family_quotas": {
    "context_interference": 10,
    "temporal_supersession": 10,
    "evidence_traceability": 10,
    "dependency_impact_tracking": 10
  },
  "seed": 12345,
  "difficulty_policy": "balanced"
}
```

单 case 可以不生成完整 dataset plan，只需要 family selection。

---

## 3.2 `family-selection`

作用：决定当前 case 属于哪一个 family。

规则：

```text
用户指定 family -> 用用户指定
用户没指定 + 单 case -> 按 seed deterministic 选择一个
batch -> 按 dataset-plan 分桶生成
```

输出：

```json
{
  "case_index": 3,
  "family_id": "temporal_supersession",
  "selection_reason": "selected_by_seed",
  "seed": 12345
}
```

---

## 3.3 `memory-capability-brief`

这是最重要的 artifact。

它不应该叫 `weakness_brief`，建议叫：

```text
memory_capability_brief.json
```

因为它定义的是“要测试什么能力”，不是“要打谁的弱点”。

输出：

```json
{
  "family_id": "temporal_supersession",
  "capability_under_test": "系统能否理解新状态覆盖旧状态，并把旧状态保留为历史而不是当前答案",
  "why_memory_systems_may_fail": "长期记忆系统可能同时保留多个历史状态，无法判断哪个状态是 current",
  "generation_rules": [
    "必须生成至少一个会变化的任务字段",
    "必须包含 initial state、intermediate update、final current state",
    "旧状态必须仍然真实，但不能作为当前答案"
  ],
  "required_case_structure": {
    "state_tracks": ["owner", "deadline", "blocker"],
    "min_states_per_track": 3,
    "must_have_stale_states": true
  },
  "probe_strategy": ["询问当前状态", "同时询问旧状态是否仍然有效", "要求给出证据"],
  "expected_good_system_behavior": "返回 final current state，说明旧状态已被 superseded，并引用对应消息证据"
}
```

这一步应该由 Skill 中的 `capability-families.md` 指导生成。

---

## 3.4 `case-spec`

`case_spec` 不再定义 family 语义，只保留控制字段。

输出：

```json
{
  "case_id": "case_001",
  "task_id": "FEISHU-231",
  "seed": 12345,
  "difficulty": "hard",
  "comparison_target": "memory_system_baselines",
  "family_id": "temporal_supersession",
  "brief_ref": "input/memory_capability_brief.json"
}
```

重点：

```text
case_spec 不解释 family 是什么。
family 的语义只来自 memory_capability_brief。
```

---

## 3.5 `case-world`

作用：生成企业背景。

它回答：

```text
这个企业场景是什么？
为什么这些人会讨论？
为什么信息会分散？
为什么这个 family 在这个场景里自然发生？
```

例如 temporal_supersession：

```json
{
  "enterprise_context": "团队正在推进 FEISHU-231 接入方案，负责人因为排期和审批问题多次调整。",
  "sources": ["project_group", "approval_thread", "task_comment"],
  "why_this_family_is_natural": "负责人和 blocker 在不同时间、不同 source 中被更新，容易形成旧状态和新状态并存。",
  "realism_factors": ["跨团队协作", "负责人临时交接", "审批状态变化", "多个 source 中分散更新"]
}
```

注意：`case-world` 不重新定义 family，只解释 brief 如何落在真实场景里。

---

## 3.6 `task-actor-layout`

作用：把故事里的任务和人结构化。

它不是故事正文，而是“故事骨架”。

输出：

```json
{
  "target_task": {
    "task_id": "FEISHU-231",
    "task_name": "接入方案"
  },
  "distractor_tasks": [
    {
      "task_id": "PROD-123",
      "role": "干扰任务"
    }
  ],
  "shared_actors": [
    {
      "actor": "Bob",
      "task_roles": {
        "FEISHU-231": "历史负责人",
        "PROD-123": "当前开发负责人"
      }
    },
    {
      "actor": "Alice",
      "task_roles": {
        "FEISHU-231": "中间负责人",
        "PROD-123": "产品负责人"
      }
    }
  ],
  "layout_purpose": "制造跨任务角色重叠，同时保持每个人在每个任务中的角色清晰。"
}
```

为什么需要它？

因为没有这一层，LLM 生成对话时很容易角色乱掉，后面 gold 和 eval 都会不稳。

---

## 3.7 `state-trajectory`

作用：定义任务状态如何变化。

这是 temporal_supersession 和 dependency_impact_tracking 的核心。

输出：

```json
{
  "state_tracks": [
    {
      "task_id": "FEISHU-231",
      "track_key": "owner",
      "states": [
        {
          "state_id": "owner_001",
          "value": "Bob",
          "status": "initial"
        },
        {
          "state_id": "owner_002",
          "value": "Alice",
          "status": "superseded",
          "supersedes": "owner_001"
        },
        {
          "state_id": "owner_003",
          "value": "xzy",
          "status": "current",
          "supersedes": "owner_002"
        }
      ]
    }
  ]
}
```

为什么需要它？

因为 benchmark 需要知道：

```text
什么是当前状态？
什么是历史状态？
哪个状态覆盖了哪个状态？
最终 query 的 gold answer 是什么？
```

这不能只靠自然故事临时推断，必须结构化。

# 4. 四类 family 分别怎么构造

## 4.1 `context_interference`

目标：测试系统在大量无关信息后是否还能只回答 target task。

构造规则：

```text
1 个 target task
2-3 个 distractor tasks
3-5 个 shared actors
相似字段：owner / deadline / blocker / approval / dependency
```

典型 probe：

```text
只看 FEISHU-231，不要混入 PROD-123：当前负责人、阻塞项、审批状态分别是什么？请给证据。
```

核心 artifact 重点：

```text
task-actor-layout 最重要
state-trajectory 可以较轻
```

---

## 4.2 `temporal_supersession`

目标：测试系统是否能处理旧状态被新状态覆盖。

构造规则：

```text
至少 1 个状态字段多次变化
必须有 initial / update / final current
旧状态仍然真实，但已经不是 current
```

典型 probe：

```text
FEISHU-231 当前负责人是谁？Bob 和 Alice 现在还负责吗？请说明依据。
```

核心 artifact 重点：

```text
state-trajectory 最重要
```

---

## 4.3 `evidence_traceability`

目标：测试系统是否能区分明确事实、猜测、转述和普通确认。

构造规则：

```text
verified_fact turn
ambiguous_claim turn
hearsay turn
weak_commitment turn
ordinary_ack turn
no_event turn
```

典型 probe：

```text
财务问题是谁明确提出的？这是确定阻塞、猜测还是转述？请给原文证据。
```

核心 artifact 重点：

```text
conversation-plan 的 turn taxonomy 最重要
```

---

## 4.4 `dependency_impact_tracking`

目标：测试系统是否能根据上游任务变化判断下游影响。

构造规则：

```text
1 个 upstream task
至少 2 个 downstream tasks
1 个 upstream blocker update
明确 dependency edge
```

典型 probe：

```text
FEISHU-231 的财务问题现在会影响哪些下游任务？影响依据是什么？
```

核心 artifact 重点：

```text
task-actor-layout + state-trajectory 都重要
```

# 5. 改造计划应该怎么写

我建议按三步改。

---

## Step 1：先改 Skill，不动 runner

目标：把四类 family 固化成 Skill reference。

Skill 目录：

```text
memory-benchmark-case-builder/
├── SKILL.md
└── references/
    ├── capability-families.md
    ├── workflow.md
    ├── scenario-generation.md
    ├── artifact-contracts.md
    └── baseline-policy.md
```

其中最重要的是：

```text
capability-families.md
```

它定义四类 family：

```text
context_interference
temporal_supersession
evidence_traceability
dependency_impact_tracking
```

每类写：

```text
测什么能力
为什么记忆系统可能失败
如何构造 case
必须出现哪些结构
有效 probe 是什么
无效 probe 是什么
```

---

## Step 2：改 Phase 1 的上游 artifact

新增：

```text
input/memory_capability_brief.json
```

然后让后续阶段都消费它。

Phase 1 变成：

```text
family-selection
-> memory-capability-brief
-> case-spec
-> case-world
-> task-actor-layout
-> state-trajectory
-> conversation-plan
-> probe-targets
-> command-plan
-> execute
-> collect
-> pre-annotation-validate
```

注意：`memory_failure_blueprint` 如果保留，也应该放在更后面，作为 machine-readable contract，不是最早的创意源头。

---

## Step 3：改 prompt_registry

把 prompt 分成两层：

```text
family-level prompt
stage-level prompt
```

### family-level prompt

只负责：

```text
生成 memory_capability_brief.json
```

它可以是四个固定 builder：

```text
build_context_interference_brief_prompt
build_temporal_supersession_brief_prompt
build_evidence_traceability_brief_prompt
build_dependency_impact_tracking_brief_prompt
```

### stage-level prompt

只负责消费 brief：

```text
build_case_world_prompt(brief)
build_characters_prompt(brief, world, layout)
build_conversation_plan_prompt(brief, world, layout, state)
```

硬规则：

```text
stage-level prompt 不允许重新定义 family。
```

# 7. Test Plan

最重要的测试是这些：

```text
1. 单 case 默认只选 1 个 family。
2. 同一个 seed 每次选到同一个 family。
3. batch 生成时四类 family 都有覆盖。
4. memory_capability_brief 必须包含 capability_under_test / generation_rules / probe_strategy。
5. case_world 必须消费 brief，不能重新定义 family。
6. task_actor_layout 必须满足 family 的 required_case_structure。
7. state_trajectory 必须满足 temporal / dependency family 的状态要求。
8. probe query 不能只是问显式字段，必须测 family 对应能力。
9. annotation gold 必须基于 collected messages。
10. baseline report 必须区分 baseline mode。
```

# 8. 最终结论

是的，你的测试主轴就是四类 family。

但我建议不要叫：

```text
OpenClaw weakness family
```

而叫：

```text
memory capability family
```

最终 builder agent 的构造原则是：

```text
先选 family
-> 生成 memory_capability_brief
-> 让故事、任务角色、状态轨迹、对话计划全部围绕这个 brief 生成
-> collect 后再生成 gold
-> 用同一批 probe 比较多个 baseline
```

这样测试更公平，也更容易解释。OpenClaw 只是 baseline，不是数据集设计的唯一靶子。
