# 2026-05-08 长程记忆检索中的证据重排设计

## 1. 证据重排解决什么问题

长程记忆检索里，真正难的不是“找到一批看起来相关的文本”，而是判断：

```text
哪些证据真的能支撑当前回答？
哪些证据只是相似、过期、传闻、干扰或只命中了依赖链的一段？
```

因此，证据重排不是 retrieval 的替代品，而是 retrieval 之后的判断层。

它要解决的问题包括：

- 相似文本不等于正确证据。
- 最近消息不一定是最终状态。
- 高频人物不一定和目标 task 相关。
- summary 结论如果没有原文支撑，不能作为强证据。
- 传闻、猜测和模糊判断不能被当成 verified fact。
- 依赖链问题不能只命中 upstream 或 downstream 的一个片段。

可以把它理解成：

```text
retrieval 负责找候选；
rerank 负责判断证据优先级；
answer generation 只能消费 rerank 后的 evidence package。
```

## 2. 它在长程记忆检索链路中的位置

证据重排位于 candidate retrieval 之后、answer generation 之前。

完整位置是：

```text
query
-> query understanding
-> task binding
-> candidate retrieval
-> evidence expansion
-> evidence rerank
-> answer-ready evidence package
-> answer generation
```

其中：

- `query understanding` 判断用户到底是在问 owner、deadline、blocker、current state、历史原因还是依赖影响。
- `task binding` 先确定目标 task，避免在一开始就把其他相似任务混进来。
- `candidate retrieval` 可以召回 Memory Blocks、events、message quotes 和原始消息。
- `evidence expansion` 负责沿着 event_ref、block_ref、thread root、reply、上下游 task 找到必要补充证据。
- `evidence rerank` 负责把候选证据重新排序，并标记 accepted / demoted / missing。
- `answer generation` 不再直接扫全文，而是消费 rerank 后的证据包。

这条边界很关键：answer generation 不应该自己重新决定哪些证据可信。它最多可以解释 rerank 结果，但不能绕过 rerank 去挑证据。

## 3. 输入与输出

### 3.1 Rerank 输入

证据重排的输入不是裸文本列表，而是一组带结构的候选证据。

建议输入包括：

- `query_intent`
  用户问题的意图，例如 current owner、latest deadline、true blocker、dependency impact、evidence attribution。
- `bound_task_id`
  已绑定的目标任务。
- `candidate_memory_blocks`
  从 `index.md`、`task_wiki.md`、`session_wiki.md` 召回的候选 Memory Blocks。
- `candidate_events`
  由 Memory Blocks 或 query 直接召回的 verified / candidate events。
- `evidence_quotes`
  候选 events 绑定的原文 quote、message id、source id。
- `state_changes`
  如果问题涉及 current state，需要提供状态变化序列和 supersedes 关系。
- `source_metadata`
  消息来源、发言人角色、是否系统卡片、是否正式文档、时间戳、thread/session 信息。
- `dependency_context`
  如果问题涉及依赖传播，需要提供 upstream / target / downstream 的候选关系。

### 3.2 Rerank 输出

证据重排的输出应该是 answer-ready evidence package，而不是单纯的排序列表。

建议输出包括：

```json
{
  "ranked_evidence": [],
  "accepted_evidence": [],
  "demoted_stale_evidence": [],
  "demoted_noisy_evidence": [],
  "demoted_weak_evidence": [],
  "missing_evidence_caveat": [],
  "answer_ready_evidence_package": {
    "primary_evidence": [],
    "supporting_evidence": [],
    "historical_evidence": [],
    "excluded_evidence": []
  }
}
```

这里的关键不是 JSON 形状本身，而是输出必须能解释：

- 为什么某条证据被提升。
- 为什么某条证据被降权。
- 哪些证据只能作为历史背景。
- 哪些证据不能进入最终答案。
- 是否缺少足够证据支撑强结论。

## 4. 通用 rerank signals

### 4.1 `task_relevance`

判断证据是否属于目标 task。

排序原则：

```text
same task evidence
> explicitly linked task evidence
> same actor but different task
> unrelated task evidence
```

这解决的是长程记忆里最常见的 shared actor 干扰问题。

例如 Alice 同时负责多个任务时，不能因为消息里出现 Alice 就把其他任务的 owner、blocker 或 deadline 混到目标任务里。

### 4.2 `evidence_strength`

判断证据强度。

建议强度顺序是：

```text
verified fact
> official update
> direct owner statement
> ambiguous claim
> hearsay
> ordinary ack
```

这里的目标是防止模型把“我听说”“感觉应该”“收到”这类弱证据当成正式事实。

### 4.3 `currentness`

判断证据是否代表当前状态。

排序原则：

```text
final current update
> superseding update
> historical value
> initial value
> superseded stale value
```

旧证据不应该被直接删除。它可以作为历史证据保留，但不能继续支撑 current answer。

对矛盾更新问题，rerank 必须显式标记：

- 哪条证据是最终当前口径。
- 哪条证据覆盖了旧口径。
- 哪些旧值只能作为历史背景。

### 4.4 `source_authority`

判断来源是否有权确认该事实。

排序原则：

```text
system card / official doc / approval record
> task owner / direct responsible person
> reviewer / operator with domain authority
> participant comment
> hearsay from non-owner
```

source authority 不能替代 evidence strength，但可以作为 tie-breaker。

例如审批状态更适合由审批卡片、审批负责人或正式文档确认，而不是由旁观者转述确认。

### 4.5 `dependency_completeness`

判断证据是否覆盖完整影响链。

对于依赖问题，单条证据只命中 upstream 并不一定足够。系统需要知道：

- 上游发生了什么。
- 它如何影响目标任务。
- 目标任务又如何影响下游任务。

排序原则：

```text
verified upstream blocker + target impact + downstream impact
> verified upstream blocker + target impact
> target-only statement
> downstream-only consequence
> hearsay dependency statement
```

如果 query 明确问“影响了哪些下游任务”，只给 upstream blocker 的证据不能排在最前。

### 4.6 `anti_interference_safety`

判断证据是否混入干扰任务。

高风险证据包括：

- 同一 actor 在其他 task 里的状态。
- 相似 task id 或相似 task name。
- 同一 thread 里穿插讨论的 distractor task。
- 只出现共享字段，但没有绑定目标 task 的消息。

排序原则：

```text
explicit target task evidence
> explicit scope boundary evidence
> same thread but target-linked evidence
> distractor task evidence
> shared actor only evidence
```

### 4.7 `answer_need_fit`

判断证据是否真的回答当前 query。

相似度高但不回答问题的证据应该降权。

例如：

- 用户问“当前负责人是谁”，只说明“任务很紧急”的证据不够。
- 用户问“为什么上线推迟”，只说明“有人收到消息”的证据不够。
- 用户问“这个 blocker 影响了哪些下游任务”，只说明“上游没确认”的证据不够。

## 5. 三类 family 的重排策略

当前正式 family 只有三类：

- `anti_interference`
- `contradiction_update`
- `evidence_dependency_reasoning`

`效能指标验证` 是最终评测维度，不是 family。

### 5.1 `anti_interference`

目标是抗干扰。

核心风险：

- distractor task 被误认为 target task。
- shared actor 的其他任务信息被混入答案。
- 相似字段、相似 deadline、相似 blocker 被错误合并。

重排重点：

```text
target task evidence
> explicit scope boundary
> same session target evidence
> distractor evidence
> shared actor only evidence
```

提升条件：

- 明确包含目标 task id。
- 明确说明该事实只适用于目标 task。
- 能排除相似任务或其他任务角色。

降权条件：

- 只因为同一个人出现而被召回。
- 只因为字段名相似而被召回。
- 证据属于 distractor task。

answer generation 消费时必须做到：

- 只用 accepted target evidence 回答。
- 必要时显式说明哪些 distractor evidence 被排除。

### 5.2 `contradiction_update`

目标是矛盾更新。

核心风险：

- 旧口径被当成当前状态。
- 最新消息没有显式写“覆盖”，但语义上已经覆盖。
- 模型同时引用新旧状态，造成答案含混。

重排重点：

```text
final current update
> explicit superseding update
> latest valid direct owner statement
> historical value
> initial value
```

提升条件：

- 明确出现“最终确认”“以这个为准”“之前作废”等覆盖语义。
- 时间上晚于旧状态，并且字段相同。
- 来自负责人、审批人、系统卡片或正式文档。

降权条件：

- 被后续消息覆盖。
- 只代表初始状态。
- 没有时间或 supersedes 关系支撑。

answer generation 消费时必须做到：

- 当前答案只使用 current evidence。
- stale evidence 只能作为历史说明。
- 如果证据不足以判断覆盖关系，必须给 caveat。

### 5.3 `evidence_dependency_reasoning`

目标是证据依赖和影响传播。

核心风险：

- 把 hearsay 当成 verified fact。
- 只引用下游结论，缺少上游证据。
- 只记住 blocker 名称，但没有解释影响链。
- 把 ambiguous claim 当成正式状态。

重排重点：

```text
verified upstream blocker + downstream impact
> verified upstream blocker + target impact
> direct but partial evidence
> ambiguous claim
> hearsay
```

提升条件：

- 能说明 blocker 或风险源来自 verified evidence。
- 同时覆盖 upstream、target、downstream。
- 明确说明谁确认了事实，哪条消息支撑事实。

降权条件：

- 只有传闻，没有确认。
- 只有下游结果，没有上游原因。
- 只有上游状态，没有目标任务或下游影响。
- 证据强度弱但被写成强结论。

answer generation 消费时必须做到：

- 先说明可信证据是什么。
- 再说明不可信或弱证据为什么不能作为结论。
- 最后解释依赖链如何传播。

## 6. Evidence package 结构建议

rerank 后不应该只输出一个 top-k 列表，而应该输出能直接喂给回答生成的 evidence package。

建议分成四类：

### 6.1 `primary_evidence`

最能支撑答案的证据。

要求：

- 与目标 task 相关。
- 证据强度足够。
- 能回答 query 的核心问题。
- 对 current-state 问题必须是当前有效证据。

### 6.2 `supporting_evidence`

辅助解释答案的证据。

它可以补充背景、原因、影响面或上下游关系，但不能单独支撑主结论。

### 6.3 `historical_evidence`

已经被覆盖但对解释历史变化有用的证据。

它不能支撑当前答案，但可以用于回答：

- “之前是谁负责？”
- “为什么改了？”
- “这个状态什么时候被覆盖？”

### 6.4 `excluded_evidence`

明确不进入回答的证据。

常见原因：

- wrong task
- stale
- hearsay
- ambiguous
- ordinary ack
- no answer fit
- dependency chain incomplete

`excluded_evidence` 不是垃圾桶。它是解释系统为什么没有采用某条候选证据的重要 trace。

## 7. 回答生成如何消费重排结果

回答生成必须遵守以下规则：

1. 主答案只能基于 `primary_evidence`。
2. 背景解释可以使用 `supporting_evidence`。
3. 历史变化只能使用 `historical_evidence`。
4. 不允许使用 `excluded_evidence` 生成肯定结论。
5. 如果 `primary_evidence` 不足，应该输出 caveat，而不是编造答案。

推荐回答结构：

```text
结论：
  当前答案是什么。

依据：
  引用 primary evidence。

补充：
  使用 supporting evidence 解释背景或影响。

排除：
  如有必要，说明哪些 stale/noisy/hearsay evidence 没有被采用。

不确定性：
  如果证据不足，明确说明缺口。
```

这样做的核心价值是：回答不是“看起来像总结”，而是能解释自己为什么可信。

## 8. 评测指标

证据重排应该纳入 Phase 3 的 evidence / answer / safety / efficiency 评测。

建议指标包括：

- `evidence_precision`
  输出证据中有多少属于 gold supporting messages。
- `evidence_recall`
  gold supporting messages 中有多少被覆盖。
- `current_evidence_citation_rate`
  当前状态答案是否引用最终有效证据。
- `stale_evidence_suppression_rate`
  被覆盖旧证据是否被降权或标成 historical。
- `distractor_evidence_suppression_rate`
  干扰任务证据是否被正确压低。
- `hearsay_rejection_rate`
  传闻是否没有被当成 verified fact。
- `dependency_chain_completeness`
  依赖类问题是否覆盖 upstream、target、downstream。
- `evidence_ordering_accuracy`
  排名前列证据是否比低排名证据更能支撑答案。
- `manual_lookup_reduction`
  用户是否更少需要回翻原始长 transcript。

其中 `manual_lookup_reduction` 属于效能指标验证的一部分。

再次强调：

- `效能指标验证` 是最终评测维度。
- 它不进入 formal family。
- 它用来衡量重排和证据包是否真的减少人工查找成本。

## 9. 后续实现建议

后续可以把证据重排实现成一个独立模块，但它不应该取代已有 Task Wiki 三层结构。

建议模块边界：

```text
retriever
-> evidence_expander
-> evidence_reranker
-> evidence_package_builder
-> answer_composer
-> trace_logger
```

### 9.1 `evidence_reranker`

输入候选证据和 query intent。

输出：

- ranked evidence
- accepted evidence
- demoted evidence
- rerank reasons

### 9.2 `evidence_package_builder`

把 rerank 结果整理成 answer generation 可消费的结构：

- primary
- supporting
- historical
- excluded
- caveat

### 9.3 `trace_logger`

记录每条证据被提升或降权的原因。

这对 benchmark 很重要，因为评测时不只要知道答案对不对，还要知道：

```text
系统为什么用了这条证据？
系统为什么没用另一条看起来相似的证据？
```

### 9.4 实现优先级

建议先实现三条最关键的 rerank 规则：

1. `task_relevance`
2. `currentness`
3. `evidence_strength`

然后再补：

4. `dependency_completeness`
5. `anti_interference_safety`
6. `answer_need_fit`

这样可以先解决最常见的长程记忆错误，再逐步增强复杂依赖推理能力。

## 10. 小结

证据重排的核心不是“把搜索结果再排一下”，而是把长程记忆检索从相似文本召回，推进到可验证证据选择。

它要保证：

- 抗干扰场景里，不把 distractor evidence 混进答案。
- 矛盾更新场景里，不把 stale evidence 当成 current evidence。
- 证据依赖场景里，不把 hearsay 当成 verified fact，也不漏掉上下游影响链。

最终，answer generation 应该只消费 rerank 后的 evidence package。

这样 Task Wiki 的回答才能同时具备：

- 正确答案
- 可验证证据
- 当前状态判断
- 噪声排除理由
- 可评测的 evidence trace
