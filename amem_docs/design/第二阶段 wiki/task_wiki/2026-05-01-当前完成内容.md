# 2026-05-01 Feishu Task Wiki 当前完成内容

## 1. 本轮完成目标

这轮工作的核心目标，是把原来围绕 `graph_index / canonical / decision_state_view_v2` 这一套命名和语义的记忆主链，直接重构成一套新的 **Feishu Task Wiki** 语义模型。

这次不是兼容式演进，而是按“直接重构”的思路推进，重点完成了下面几件事：

- 把 memory-core 主链的配置、表名、查询语义改成 `feishu_task_wiki` 方向
- 把旧的 `decision_claim_recorded` 主路径收缩掉，改成 8 类 typed task events
- 把当前状态、查询卡片、证据组织都改成 task wiki 语义
- 清理掉一批已经不再适合继续保留的旧 migration / projector / test

当前可以认为：**repo 内部的 memory/task wiki 主链已经切到了新语义**，但 **真正在线上运行的 Lark/Feishu channel runtime task-first session 路由还没有接上**。

## 2. 已完成的实现内容

### 2.1 配置与主命名切换

已经把 memory-core 的主配置从 `graphIndex` 切到了 `feishuTaskWiki`，并同步调整了相关 schema 常量和 trace/config 读取逻辑。

本轮已经完成：

- `graphIndex` 配置键切换为 `feishuTaskWiki`
- `resolveGraphIndexConfig` 切换为 `resolveFeishuTaskWikiConfig`
- schema/version/projection 常量改成 task wiki 语义
- CLI runtime、trace、index 导出同步改成新命名

这一步的目标，是先把系统主入口的名字从“图索引”转成“任务 Wiki”，避免后续继续在旧语义上叠新逻辑。

### 2.2 数据表语义重命名

本轮已经把 memory-core 里的主要表结构语义，改成更明确的 task wiki 命名。

当前主表已经切成：

- `task_binding`
- `task_source_session_state`
- `task_session_ingest_queue`
- `task_evidence_records`
- `task_event_type_registry`
- `task_session_events`
- `task_current_state_view`
- `task_wiki_entities`
- `task_wiki_relations`

对应关系大致是：

- 待处理 source session 候选进入 `task_session_ingest_queue`
- source 级别的增量状态进入 `task_source_session_state`
- quote-grounded 证据进入 `task_evidence_records`
- 通过校验的 typed event 进入 `task_session_events`
- 当前 task 的聚合状态进入 `task_current_state_view`
- wiki 层的辅助实体和关系进入 `task_wiki_entities / task_wiki_relations`

这一步完成之后，底层存储已经不再继续使用旧的 `projection_inbox / evidence_records / event_records_v2 / decision_state_view_v2 / graph_entities_v2 / graph_edges_v2` 那套名字。

### 2.3 Event 模型切成 8 类 typed task events

当前事件主路径已经不再以 `decision_claim_recorded` 为中心，而是切成了 8 类 typed task events：

- `conclusion_event`
- `rationale_event`
- `objection_event`
- `constraint_event`
- `commitment_event`
- `status_event`
- `time_event`
- `scope_event`

这一步的目的，是把原来偏“决策 claim”抽取的方式，升级成更适合 task wiki 的 typed 事实层。

它带来的好处是：

- 当前 task 的结论、理由、反对意见、约束、承诺、状态、时间点、范围都可以有明确事件类型
- 后续 `session_wiki.md / task_wiki.md` 可以更稳定地按 typed slots 去组织
- 查询层不再只能围绕“决策卡片”运转，而是可以围绕 task 状态、为什么、时间线、记忆卡片做统一输出

### 2.4 Store 主链已改成 Feishu Task Wiki Store

当前存储主链已经重写成新的 `FeishuTaskWikiStore`。

它现在负责：

- 管理 `task_session_ingest_queue`
- 读写 `task_source_session_state`
- 持久化 `task_evidence_records`
- 写入 `task_session_events`
- 更新 `task_current_state_view`
- 更新 `task_wiki_entities / task_wiki_relations`

也就是说，repo 内当前的主落盘路径，已经是：

`evidence -> typed task event -> task current state -> task wiki entity/relation`

这一步完成后，store 层已经不再依赖旧 migration 链，也不再以 decision/workflow state 作为主状态模型。

### 2.5 查询层已改成 Task Wiki 语义

当前查询层已经不再围绕旧的 `decision_card / state / why / timeline` 组织，而是切成 task wiki 语义：

- `task_state`
- `task_why`
- `task_timeline`
- `task_memory_card`
- `list_relation`

同时，原来 prompt/render 里围绕 `decision_card` 的输出，也已经改成围绕 `task_memory_card` 来组织。

当前 `task_memory_card` 会优先展示：

- task
- topic
- current conclusion
- statuses
- scope
- time points
- rationales
- objections
- constraints
- commitments

这意味着：**repo 内部的 query path 已经能用 task wiki 语义返回结构化内容**。

### 2.6 Projection 与 current state 路径已切到 task wiki

当前 projection/drain 持久化链已经做了几项关键切换：

- persisted trace 的表名改成 task wiki 语义
- current state context 改成从 `task_current_state_view` 读取
- 生产路径里去掉了对旧 decision state 查询的一部分直接依赖

这一层现在已经可以认为是：

- 入口仍然是 source session 的抽取与入队
- 但持久化和 current state 聚合都已经围绕 task wiki 模型运转

### 2.7 清理了旧 migration / projector / 测试包袱

这轮还删除了一批不再适合继续保留的旧文件，主要包括：

- 旧 migration 文件
- 旧 workflow/graph projector
- 绑定旧 decision/workflow 语义的测试文件

这么做的目的很明确：

- 不再继续维持旧 `graph_index` 的增量兼容链
- 减少后续继续在旧抽象上修修补补的成本
- 让后面的 task wiki 演进有更干净的基底

## 4. 当前还没有完成的部分

虽然 repo 内 memory-core 主链已经切到了 task wiki 语义，但这轮**还没有完成真正在线 runtime 的 task-first session 聚合**。

更准确地说，当前还没完成的是：

- 尚未修改用户机器上实际运行的 `openclaw-lark` channel runtime 路径

也就是说：

- **repo 内部的 task wiki 数据模型、存储模型、查询模型已经重构完成**

这是当前阶段最重要的边界。

## 6. 下一步建议

下一步最值得继续推进的不是再补 schema，而是直接接 runtime：

### 6.1 先改真实 Lark channel

重点改实际生效的 Lark channel runtime 路径，尤其是：

- inbound dispatch context
- queue key 构造
- route/session key 解析
- thread/root/chat/doc source 的 task binding lookup

目标是把 Feishu 运行时从：

- conversation-first

改成：

- task-first（已绑定 task 时）

### 6.2 把 `task_binding` 接入运行时

需要新增并打通：

- `task_id <-> thread/chat/doc/source` 的显式绑定
- `root_id` fallback 命中 task 的逻辑
- task-scoped runtime session key 生成逻辑

### 6.3 再补 task wiki 物化页面

在 runtime task session 真正打通后，再继续落：

- `session_wiki.md`
- `memory_block`
- `index.md`
- `task_wiki.md`

这样整条 Feishu Task Wiki 才会从“repo 内核完成”真正走到“运行时可用”。
