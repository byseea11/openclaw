## 1. 预期输入

第三阶段 Layer 3 的目标不是重新抽 event，也不是重新识别 task，而是：

```text
只消费第二阶段已经验证通过的 session_event，
把它们投影成：

session_wiki.md
index.md
task_wiki.md

并补齐：

lint/
forgetting/
log.md
```

### 1.1 预期最小输入对象

设计上，第三阶段应该接收一个 **已生成 source session 的 verified fact context**：

```ts
type ExpectedLayer3Input = {
  task_id: string
  source_session_id: string
  session_dir: string

  session_events_path: string
  session_markdown_path: string
  metadata_path: string

  overlay?: {
    source_revocations?: string
    event_invalidations?: string
    event_supersessions?: string
  }
}
```

### 1.2 这些字段各自的用途

- `task_id`
  - 指明当前投影属于哪个 canonical task
- `source_session_id`
  - 指明当前投影属于哪个 source session
- `session_dir`
  - 第三阶段的工作根目录
- `session_events_path`
  - verified `session_event` 的唯一正式事实输入
- `session_markdown_path`
  - 给 `Entry Ref` 和原始上下文回链
- `metadata_path`
  - 给 page metadata、participants、time range 等字段
- `overlay`
  - 第三阶段的 revoke / invalidation / supersession 生命周期覆盖层

### 1.3 预期 Layer 3 核心语义

设计上，这一层应该遵守：

1. 第三阶段只消费 verified `session_event`
2. `candidate_events.jsonl` 不进入第三阶段事实主线
3. `session_wiki.md` 是 source session 的一手页面
4. `index.md` 是 page index + memory block index + 最小 topic routes
5. `task_wiki.md` 只展示 task 当前态，不平铺历史
6. block 结构必须稳定、可追溯、可增量更新
7. revoke / invalidation / supersession 不回写第二阶段事实本体，而走 overlay sidecar

- `log.md`

## 3. 当前最终输入

当前代码里，第三阶段真正的主入口是：

- `updateTaskWikiFromVerifiedEvents(...)`

它的真实输入非常收紧：

```ts
type CurrentLayer3Input = {
  sessionDir: string
}
```

也就是说，当前第三阶段运行时只要求：

```text
给我一个已经落好第二阶段文件的 sessionDir，
我自己从里面读：

session_events.jsonl
session.md
metadata.yaml

然后自动投影到 task root。
```

### 3.1 当前 runtime 实际消费的文件

第三阶段当前真正消费的是：

```text
session_events.jsonl
session.md
metadata.yaml
```

其中：

- `session_events.jsonl`
  - 只读取 `verification.verdict = verified` 的正式事件
- `session.md`
  - 给 `Entry Ref` 与 Evidence References 回链
- `metadata.yaml`
  - 给 page metadata 和 task/source 基本信息

### 3.2 当前第三阶段对外接口

当前 `api.ts` 已经对外导出了这些接口：

```ts
projectSessionWiki({ sessionDir })
projectTaskIndex({ taskRootDir, sessionState })
projectTaskWiki({ taskRootDir, sessionState })
updateTaskWikiFromVerifiedEvents({ sessionDir })

runTaskWikiLint({ taskRootDir, appendLog? })

revokeSourceSession({ taskRootDir, sourceSessionId, reason? })
invalidateSessionEvent({ taskRootDir, eventId, reason? })
supersedeSessionEvents({ taskRootDir, supersedingEventId, supersededEventIds, reason? })
```

### 3.3 当前 block 级增量语义

当前实现已经不是简单“每次整 task 全量重建”的语义，而是：

```text
先重算受影响 session 的 block membership / slot current item / summary
然后用 marker + sidecar 做 page patch
只有 patch 失败时才 fallback 整页重建
并写 fallback_rebuild 到 log.md
```

当前内部 patch 依赖的稳定 marker 形态例如：

```html
<!-- session-summary:start -->
<!-- session-summary:end -->

<!-- block:block-发布时间口径-867908bd:start -->
<!-- block:block-发布时间口径-867908bd:end -->
```

### 4.2 当前 Markdown 主产物语义

当前实现已经明确做到：

- `session_wiki.md`
  - 有 `Session Summary`
  - 有 `Memory Blocks`
  - slot 中显式写 `Event Ref`
  - 有 `Entry Ref`

  - 有 `Task Overview`

  - block link 会落到真实 `session_wiki.md#anchor`
- `task_wiki.md`
  - 只展示当前态
  - 当前态项显式带 `Block Ref`
  - 当前态项显式带 `Event Ref`

- `forgetting/event_supersessions.jsonl`

并在投影时把 event lifecycle 解释成：

- `active`
- `historical`

## 6. 一致性判断

### 6.1 当前已经和设计稿一致的点

下面这些点，当前实现已经和第三阶段文档语义一致：

1. **第三阶段只消费 verified `session_event`**
2. **`session_wiki.md / index.md / task_wiki.md` 三页主产物已经成立**
3. **`index.md` 已经有最小版 Topic Routes**
4. **`task_wiki.md` 只展示当前态，不平铺历史**
5. **slot / block / page 都有明确的 `event_ref` / `block_link` 回链**
6. **已经有 forgetting overlay**
7. **已经有 lint/ 巡检**
8. **已经有跨第二、三阶段的统一 `log.md`**
9. **已经支持 block marker + sidecar 的增量 patch**
10. **`views/*.md` 仍然没有实现，符合当前范围收敛**

### 6.2 当前还保留的工程边界

当前第三阶段虽然已经和文档的主契约比较接近，但还保留两个工程边界：

1. **block 级 patch 依赖 marker + sidecar**
   - 外部效果已经是 block 级增量
   - 但内部不是 AST 级 patch，而是基于稳定 marker 的结构化替换

2. **真实 supersession 的 current-state 切换，取决于被 supersede 的具体 event**
   - 如果 supersede 的只是 `time_event`
   - 那旧 `conclusion_event` 仍然会继续留在 `Current Conclusions`
   - 这不是传播失败，而是 lifecycle overlay 只覆盖了对应 event
